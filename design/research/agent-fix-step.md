# Spike: a native agent/fix step, patch guard and ladder in Yukta (#1230)

Question: should Yukta offer (1) an agent/fix node, (2) a patch guard step, (3) a ladder helper, instead of the shell
fixer of `examples/11-dogfood`? No production change here.

## What exists today (origin/main)

| Piece | Where | Size |
|---|---|---|
| Launch a headless `claude -p` (model, effort, tool allow-list, system prompt, `--max-budget-usd`, JSON schema answer) | `scripts/_claude.sh`, `scripts/claude.sh` | 61 lines |
| Guard: protected paths, added suppressions, removed assertions, test-expectation-only edits, "claimed a fix but changed nothing" | `yukta-heal.sh judge` (+ `snapshot`, `changed_since`) | about 60 lines of bash, regex over `git diff -U0` |
| Cost, usage and claim of an attempt | `yukta-heal.sh claimed`, `report` | about 40 lines of jq, files in the heal dir |
| Ladder: haiku, sonnet, opus by effort, triage picks the start | `scripts/gen-heal.py` (generates the `claude`, `attempt`, `fix-from`, `heal` workflows) | 204 lines |

Yukta already has: `LLM_CALL` (providers, `tools` the model may *ask* for, `budget` with `maxTokens`/`maxCost`/`maxCalls`/`hardStop`
per execution), `MCP_TOOL_CALL`, `PROCESS_EXECUTOR`, `SUB_WORKFLOW`, `OUTCOME_TERMINAL`, engine retry and `onError` routing.

## 1. Agent/fix node: no-go for now

`LLM_CALL` returns tool *requests*; the loop that runs them is the workflow's. A coding agent needs file edit, search and
shell tools with a working directory, permission rules, context management and a prompt cache tuned to them. That is
what `claude -p` is, and the shell fixer already gets the budget cap, the tool allow-list, the schema answer and the
cost from it. A native node would mean re-implementing that agent in Java (or wrapping a CLI, which is what we do), and
it would run behind the provider abstraction, losing Claude Code's tool quality for a feature only this repo uses.

What it would buy, and cheaper ways to get it:

| Wanted | Without a new node |
|---|---|
| Cost in the execution record (UI/CLI/MCP) | The `claude` workflow's node already returns `total_cost_usd` and usage in its output; put them in node metadata (a `PROCESS_EXECUTOR` option to lift named JSON fields of stdout into metadata). Generic, small, useful to every wrapped CLI |
| A local or cheaper model | `claude.sh` takes a binary and model; any CLI with the same JSON answer works. Providers behind `LLM_CALL` can already do the *decision* steps |
| Budget in USD/turns/time | `--max-budget-usd` and the node timeout; `LLM_CALL` budgets cover model calls made by workflows |

Revisit when a second user needs an in-engine coding agent, or when `LLM_CALL` gains an edit-capable tool loop for another reason.

## 2. Patch guard: go (small, generic, deterministic)

The guard is the part that is not about Claude at all: it judges a working-tree change. As a plugin
(`processors/patch-guard`, type `PATCH_GUARD`) it would take `base` (a git ref, default `HEAD`), `protectedPaths` (globs),
`forbidPatterns` (regexes on added lines), `noTestRemoval` (boolean: removed assertions/`@Test` not matched by added ones),
`requireChange` (boolean), and a `dir`. Output: `{files, violations[]}` with ports `pass` and `reject`. Benefits over the
bash: a unit-testable Java implementation with the repo's quality gates, ports instead of an exit code and a verdict
file, violations visible in the execution, reusable after any step that edits files (a user's own formatter or codegen).
Cost: one small module; the regexes move into config, so `yukta-heal.sh judge` shrinks to a node config in `gen-heal.py`.
Keep the bash judge until the plugin has a conformance fixture (see `plugins/CLAUDE.md`).

## 3. Ladder helper: defer

The ladder is generated by `gen-heal.py` (one graph per stage, rungs from the triage). A `LADDER` node would take
`rungs: [{model, effort}]` and a `step` sub-workflow and own escalate-on-failure, but that is a loop over `SUB_WORKFLOW`
with an `OUTCOME_TERMINAL` check, which the engine can already express and the generator already writes once. One user,
200 lines; a helper that must also carry the triage start, the per-stage single-attempt rule and no-progress detection
(#1242) would be designed around today's heal and be wrong for the next. Revisit with a second ladder.

## Recommendation

- Go: patch guard plugin (follow-up issue).
- Go: lift named JSON fields of a `PROCESS_EXECUTOR` result into node metadata, so wrapped agents show cost in the UI/CLI/MCP (follow-up issue).
- No-go for now: agent/fix node; defer: ladder helper.
- `yk` keeps working throughout; nothing here changes it.
