**Use this when** a step needs an AI agent to work on a task and you want to stay in control of what it does.

`AGENT_SESSION` starts the agent CLI as a process (through the [process executor](/reference/plugins/external-io), so its limits apply), shows what the agent does in the run log as it works, and ends on the port `success`, `failure` or `incomplete`. Which agent is configuration: a **harness preset** says how to start it and read its output.

## Steps

<Steps>
  <Step title="Enable it and allow the executable">
    `AGENT_SESSION` starts a process, so it is off by default:

    ```bash
    YUKTA_PLUGINS_ENABLED=AGENT_SESSION YUKTA_PROCESS_ALLOWED_COMMANDS=claude \
      YUKTA_PROCESS_PASS_ENV=HOME yukta start
    ```

    A process gets only `PATH` from the server's environment. The agent reads its login from `HOME`, so pass it; add `ANTHROPIC_API_KEY` (or `OPENAI_API_KEY` for Codex) to `YUKTA_PROCESS_PASS_ENV` if it signs in with a key.
  </Step>

  <Step title="Read the options from the server">
    `GET /api/plugins` (and the `get_plugin_details` MCP tool) lists the option names, defaults, the harnesses and what each can do (resume, approvals). You do not need anything else to configure it.
  </Step>

  <Step title="Run a prompt">
    ```json
    { "nodeId": "agent", "type": "AGENT_SESSION", "config": { "harness": "claude-code", "prompt": "${payload.task}", "maxTurns": 20, "args": ["--allowedTools", "Read,Grep,Glob"] } }
    ```

    The payload is `{status, reason, text, sessionId, turn, exitCode}` and, with Claude Code, `costUsd`, `numTurns`, `structured` (the answer to `--json-schema`) and `usage` (the token counts). `args` are extra command-line arguments for the agent: give it the tools it may use without asking. Each argument may be an expression such as `${start.budget}`, resolved per message; a plain one stays as written (`timeout` is still a fixed number).
  </Step>

  <Step title="Approve its tool use">
    Add `"approvals": "ASK"`. Each tool use the agent needs permission for becomes an `APPROVAL` request that a person, a supervisor or an agent answers (see [Ask for input](/guides/ai/ask-for-input)). `approvalRisk`, `approvalTimeout` and `approvalAudience` shape it. No answer in time, a rejection or any failure refuses the tool, and the agent sees the refusal.
  </Step>

  <Step title="Continue a conversation">
    Add `"session": "${payload.ticket}"`. Messages with the same key continue one conversation; one turn runs at a time per key, and `onBusy` says whether the next one waits (`WAIT`) or goes to `failure` (`FAIL`). Sessions are kept in memory and are lost on restart.
  </Step>
</Steps>

## Watch and talk to the agents

Every `AGENT_SESSION` message opens a **conversation**: a stored record of what the agent said and did, with a state (`RUNNING`, `WAITING`, `IDLE`, `ENDED`). Three ways to follow and steer all the agents of a run in one place, all over the same API:

- **The Agents tab** of the dock on the workflow page: the agents beside one timeline, with a box to talk to the selected one (Enter sends, Shift+Enter adds a line), **Interrupt** and **End**. A request an agent waits on is answered in place. A `pty` agent shows its terminal.
- **`yukta-cli attach <execution-id>`**: the same timeline in a terminal, with `/agents`, `/agent`, `/approve`, `/reject`, `/interrupt`, `/end`. See the [CLI reference](/reference/cli#conversations-with-ai-agents).
- **REST, MCP and supervisors**: the [conversations API](/api/conversations), the `*_agent_*` [MCP tools](/reference/mcp-tools) and the `AgentMessage`, `AgentInterrupt` and `AgentEnd` commands of a [rules supervisor](/guides/supervise/write-a-rules-supervisor).

What a harness lets you do shows in its capabilities: `message` (it takes a message), `steer` (during its turn), `interrupt`, `ask` (approvals), `resume`, `terminal`. A message to an agent that cannot take one during its turn waits for the turn to end and is marked **queued**.

Two options of the node set how it lives. `mode` is `TASK` (the default: the node ends with the agent's turn) or `CONVERSATION` (the node stays open, idle, for more messages until someone ends it, `idleTimeout` (900 s) passes or `conversationTimeout` (14400 s) does). `steerAudience` says who may send a message, interrupt, end or type into a terminal: the default is `role:OPERATOR`; add `key:<name>`, `supervisor:<id>` or `supervisor:*` to let a key or a supervisor steer it.

<Warning>
  A message to an agent is an instruction to something that can act on your server. Keep `steerAudience` as narrow as the node needs, and remember that the agent runs with the permissions of the server's user.
</Warning>

An agent needs its login and settings in its environment, which a process does not inherit: list them in `yukta.process.pass-env` (`HOME`, and the API key variable the agent reads). A missing variable looks like a failed login. Conversations are kept in memory, and are lost on a restart, unless the server uses PostgreSQL (Plus): see `yukta.agents.store-type` in the [configuration reference](/reference/configuration).

## Add a harness

A harness is a JSON file in `agent-harnesses/` on the classpath, or in the directory `yukta.ai.presets-dir` names (a file there replaces a shipped one with the same id). It gives the command (`{prompt}`), how a `model`, `maxTurns` and a session are passed, which lines mean "the result" or "failed", which values to keep from earlier lines, which lines to show live, and optionally the conversation used for approvals. Start from `claude-code.json` or `codex.json` in the `agent-session` module.

## Agents that speak ACP

A preset with `"protocol": "acp"` runs an agent over the [Agent Client Protocol](https://agentclientprotocol.com) (JSON-RPC on standard input and output). The preset needs no `output` block: the adapter reads the protocol. `antigravity` ships (`agy acp`; put the folder of `agy`, usually `~/.gemini/bin`, on `PATH` and log in once). Such an agent takes messages and an interrupt, asks for approval when `approvals` is `ASK` (approve picks the agent's `allow_once` option, refuse its `reject_once`; with `approvals` off every request is refused), and resumes a session by key when the preset declares `resume`. It never steers: a message sent during a turn waits for the turn to end. Yukta declares no file or terminal capability, so the agent uses its own tools. `acp.authMethod` in the preset names a method to `authenticate` with; leave it out when the agent is logged in already.

Adapters for agents with no ACP of their own are not shipped, because they need `npx`. Put one in `yukta.ai.presets-dir` as a file like this (names are from the adapters' documentation and were not run here):

```json
{
  "id": "claude-acp",
  "protocol": "acp",
  "description": "Claude Code through the claude-code-acp adapter.",
  "command": ["npx", "-y", "@zed-industries/claude-code-acp"],
  "capabilities": { "ask": true, "interrupt": true, "resume": true }
}
```

Change `id` and `command` for Codex (`codex-acp`) or pi (`pi-acp`) and allow the executable in `yukta.process.allowed-commands`.

## Any program in a terminal

The harness `terminal` runs a program of your choice in a pseudo-terminal, for an agent with no JSON or ACP mode. It is **off** until you set `yukta.agents.pty.enabled=true`, because a terminal takes any keystroke and nothing can review what is typed. It also needs the `yukta-cli` binary on the server's `PATH` (`yukta.agents.pty.host` names another), which hosts the terminal.

```json
{
  "type": "AGENT_SESSION",
  "config": {
    "harness": "terminal",
    "command": ["some-agent", "--task", "{prompt}"],
    "prompt": "Fix the failing test",
    "terminalSize": { "cols": 120, "rows": 40 }
  }
}
```

- `command` is the program and its arguments. Allow the **program** (`some-agent`) in `yukta.process.allowed-commands`, not `yukta-cli`. `{prompt}` may be an argument but not the program itself.
- A `{prompt}` in the arguments passes the prompt on the command line. Without one, the prompt is typed into the terminal once it is ready (the harness waits 1.5 s; a custom preset can name a `readyPattern`).
- A message sent to the conversation is typed followed by Enter; an interrupt types Ctrl-C. A person with the role `OPERATOR` can also type into the terminal with the [terminal endpoints](/api/conversations).
- The node ends when the program exits (exit code 0 is `success`, anything else `failure`), when a screen matches the preset's `donePattern`, or when the conversation is ended. `text` is the last screen.
- The run log gets two lines (start and end), not the bytes; the conversation keeps the output and the screen.

### Claude Code, Codex and Antigravity in their own terminal

The presets `claude-tui`, `codex-tui` and `antigravity-tui` run `claude`, `codex` and `agy` in their interactive terminal UI rather than headless. The Agents tab shows the screen as the program draws it: colours, menus you move through with the arrow keys, and its own prompt box. Click the terminal and type. A tab opened mid-run draws the current screen in its colours.

```json
{
  "type": "AGENT_SESSION",
  "config": { "harness": "claude-tui", "prompt": "Fix the failing test", "timeout": 3600 }
}
```

- The server needs `yukta.agents.pty.enabled=true`, the program (`claude`, `codex` or `agy`) in `yukta.process.allowed-commands`, and `HOME` (and `XDG_*` if you use them) in `yukta.process.pass-env` so the program finds its login. Log in to each CLI once as the user the server runs as.
- The prompt is pasted (bracketed paste, so a prompt of several lines stays one message) and Enter follows half a second later, once the program is ready: `claude-tui` waits for its prompt box, the other two wait four seconds. It is never typed into a screen that waits for a person, such as the trust dialog of a folder the program has not seen: answer it in the tab, and the prompt follows.
- The node runs until the program exits (`/exit`), someone presses **End**, or `timeout` passes. `text` is the last screen. There is no cost, usage or structured output: use `claude-code` or `codex` for those.
- `model` works (`--model`). Interrupt types Esc (Ctrl-C for `agy`).

A custom preset (`yukta.ai.presets-dir`) with `"protocol": "pty"` sets `pty.type`, `readyPattern`, `readyDelayMs`, `submit`, `submitDelayMs` (above 0: the pause before `submit` is typed on its own, after the prompt and each message, for a program that takes a fast burst of keys as a paste and drops an Enter in it; `type` then leaves the submit out), `interruptKeys`, `attentionPattern` (a matching screen sets the conversation `WAITING`) and `donePattern`, and may give its own `command`.

## Limits

- The agent is a process on the server with the permissions of the server's user. Allow only the executables you mean to, and give it a `workingDir` that holds nothing you mind it reading.
- No sandbox, secret handling or output redaction yet; they are planned as a separate hardening step.
- Claude Code supports sessions and approvals. The Codex preset reads `codex exec --json`; against codex-cli 0.169.0 its **failure** path was checked (an expired API key ends the node with the CLI's own message), the success path has not been run. It has neither sessions nor approvals.
- The `pi` preset runs `pi --mode rpc` (pi 1.5.2): messages and interrupt, no approvals, no resume. Only its failure path was recorded (a provider that refuses the request); the rest is written from pi's event names and has not been run on a funded account.
