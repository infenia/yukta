Yukta is a multi-module Gradle build. Each module has one job, and the pages in this tab explain how that job is done: what the module is for, its components and scenarios, what it guarantees and where the guarantee stops, and the decisions behind its design.

<Note>
  Yukta is pre-beta. Module internals change faster than the user-facing pages in the rest of this site.
</Note>

## The modules

| Module | What it owns |
|---|---|
| [`boot`](/contributing/modules/boot) | The Spring Boot application, its profiles, static serving and the GraalVM native image |
| [`core`](/contributing/modules/core) | The DAG orchestration engine: admission, execution, control, checkpoints and the MCP tools that sit on them. Also see the [core reference](/contributing/core-reference) |
| [`plugin-api`](/contributing/modules/plugin-api) | The contracts a plugin implements: triggers, processors, terminals, supervisors and control planes |
| [`plugins`](/contributing/modules/plugins) | The built-in node types, supervisors and control planes |
| [`messaging`](/contributing/modules/messaging) | The message envelope that travels along every edge, and the node message channel hook |
| [`web`](/contributing/modules/web) | The HTTP front door: REST calls and event streams, validation, and the standard response envelope |
| [`mcp`](/contributing/modules/mcp) | The MCP server that lets AI agents build and run workflows |
| [`ui`](/contributing/modules/ui) | The React single-page web UI for building, running and watching workflows |
| [`workers`](/contributing/modules/workers) | Optional (AGPL, Plus) remote workers: a processor node can run on another machine over RSocket |
| [`plus`](/contributing/modules/plus) | The AGPL Plus edition: file stores, the PostgreSQL and workers modules nested in it, and the integration layer for extension modules |
| [`persistence-postgres`](/contributing/modules/persistence-postgres) | Optional (AGPL, Plus) PostgreSQL stores for definitions, sessions, run history and node outputs, plus a leader lease so two servers can share one database |
| [`cli`](/contributing/modules/cli) | The Go command line client for a remote server |
| [`build-logic`](/contributing/modules/build-logic) | Gradle conventions: Java, Checkstyle, PMD, SpotBugs, OpenGrep, JaCoCo and dependency scanning |

## How they fit together

<img className="yk-diagram block dark:hidden" src="/images/diagrams/module-map.light.svg" alt="Clients reach the web, mcp and ui modules, which call core. Core uses plugin-api and plugins, messaging, persistence-postgres and workers. The boot module wires them into one Spring Boot app." loading="lazy" />
<img className="yk-diagram hidden dark:block" src="/images/diagrams/module-map.dark.svg" alt="Clients reach the web, mcp and ui modules, which call core. Core uses plugin-api and plugins, messaging, persistence-postgres and workers. The boot module wires them into one Spring Boot app." loading="lazy" />

Clients talk to `web`, `mcp` or `ui`, which translate requests into calls on `core`. The engine runs each node by calling a plugin through the contracts in `plugin-api`. State goes to the stores in `core` (files or memory) or `persistence-postgres`, and nodes can run on other machines through `workers`. `boot` wires everything into one application.

## Reading a module page

Every module page follows the same shape:

1. **At a glance and Primer.** The problem the module solves, the vocabulary, and one example traced end to end.
2. **Components and Scenarios.** The parts of the module and what happens inside them in typical and failing cases.
3. **Capabilities.** What the module does, with its guarantee and limit for each capability.
4. **Guarantees and limits and Reference.** What is enforced, what is only advice, what survives a restart, and the settings and lists behind them.
5. **Architecture decisions and Glossary.** Why it is built this way, and what each term means.

Each module page links to that module's open risks, bugs and issues on GitHub, and to its assessment (evolution path and quality lenses) in the repository's `design/` folder.

## Reporting bugs and tracking work

All work on Yukta is tracked in [GitHub issues](https://github.com/infenia/yukta/issues) on the Yukta Roadmap project; this site documents the product only.

- **Found a bug?** Open a [bug report](https://github.com/infenia/yukta/issues/new?template=bug_report.yml). Report a security vulnerability privately through a [security advisory](https://github.com/infenia/yukta/security/advisories/new) instead.
- **Want a feature?** Open a [feature request](https://github.com/infenia/yukta/issues/new?template=feature_request.yml), or start with a [discussion](https://github.com/infenia/yukta/discussions).
- **Sending a pull request?** Link the issue it resolves with `Fixes #<number>`. The [contributing guide](https://github.com/infenia/yukta/blob/main/CONTRIBUTING.md) covers the rest.

The [project guide](https://github.com/infenia/yukta/blob/main/.github/PROJECT.md) explains the issue types, labels, fields and triage.
