Each module section lists the risks that are still open in the code, ordered by impact (high first), then by effort (low first). **Impact** and **effort** are judgements on a 1 to 5 scale, not estimates: impact 1 is cosmetic and 5 is data loss, a security hole or an outage; effort 1 is hours and 5 is a design change. A risk id in brackets, such as (G1), is a finding number from the module's review notes; ids without brackets come from reading the code. Reviewed against `main` on 2026-10-15.

Confirmed defects are tracked on the [Bugs](/internal/bugs) page and the way forward on the [Improvements](/internal/improvements) page.

<Accordion title="Default JVM profile is dev">
**Id** `profileDefault` · **Category** Security · **Impact** 4 · **Effort** 2 · **Components** Launcher, Layered Configuration

**Why it matters.** A jar started with no flags uses dev: DEBUG logs, TRACE for the orchestrator stream package (message payloads) and extra management endpoints. Example: an operator copies the jar to a server and forgets --spring.profiles.active=prod.

**Option.** Make prod the default and keep dev opt-in for developers (bootRun can pass dev); or have main() refuse to bind a non-loopback address under dev.

**Question to settle.** Which users run the JVM jar rather than the native binary or container, and can we change the default for them?

</Accordion>
<Accordion title="Dev exposes loggers, mappings and threaddump, and logs payloads">
**Id** `devExposure` · **Category** Security · **Impact** 2 · **Effort** 2 · **Components** Layered Configuration, Management Surface

**Why it matters.** loggers lets a caller read and change log levels over HTTP; threaddump and mappings reveal internals. The TRACE stream logger writes message payloads, which may hold secrets from workflow inputs. Update: a configured key now guards these endpoints (ADMIN only), so the exposure is limited to keyless loopback use; the TRACE payload logging is unchanged.

**Option.** Trim dev exposure to health and info plus what is needed; put payload tracing behind its own flag rather than a profile.

**Question to settle.** Does anyone rely on /actuator/loggers in dev, and is payload TRACE needed as often as it is on?

</Accordion>
<Accordion title="Swagger and /v3 are outside any key; the dev profile opens more">
**Id** `openOps` · **Category** Security · **Impact** 3 · **Effort** 2 · **Components** Management Surface, Assembled Application

**Why it matters.** Done (PR #373): with a key set, the key filter now covers /actuator (except /actuator/health) and requires an ADMIN key, and `/mcp` is guarded by the same keys. Still open: the Swagger UI and the OpenAPI document have no check, so with a public bind anyone can read the API description; and with no key on a loopback bind the actuator (in dev: loggers, mappings, thread dumps) is open to every local caller.

**Option.** Guard the docs with the same filter, or switch springdoc off under the prod profile; or put management on a loopback-only port.

**Question to settle.** Should operations endpoints use the same key as the API, a different one, or network isolation?

</Accordion>
<Accordion title="Prod profile choice is split between main() and the build">
**Id** `profileForce` · **Category** Operability · **Impact** 2 · **Effort** 2 · **Components** Launcher, Native Image

**Why it matters.** main() forces prod in native images and the build passes -Dspring.profiles.active=prod. The old review said main()'s rule was removed; it is still there. Two mechanisms, and it is unverified whether the build flag reaches the running binary. The env var SPRING_PROFILES_ACTIVE is not considered.

**Option.** Keep one mechanism, test the native binary's profile at run time, and document the order of precedence.

**Question to settle.** Which of the two did we intend to keep?

</Accordion>
<Accordion title="Plugins are fixed at build time">
**Id** `buildFixed` · **Category** Functionality · **Impact** 3 · **Effort** 4 · **Components** Plugin Selection

**Why it matters.** A user cannot add or remove a plugin without rebuilding. Teams that want a custom set must run their own build, including a slow native compile. Update: there is now one built-in variant switch (`-Pyukta.plugins=default` leaves out script-js), and native images with the workers module must be built as their role (`-Pyukta.workers.native=control-plane|worker`).

**Option.** Offer prebuilt variants (full, minimal), or a plugin directory loaded by the JVM build for users who do not need native.

**Question to settle.** Do we want third parties to ship plugins, and if so how do they get them onto a binary?

</Accordion>
<Accordion title="Tests need an optional plugin">
**Id** `testsNeedPlugin` · **Category** Correctness · **Impact** 2 · **Effort** 2 · **Components** Acceptance Harness, Plugin Selection

**Why it matters.** WorkflowAcceptanceTest and SupervisorAcceptanceTest use PROCESS_EXECUTOR. A build with -Pyukta.plugins=none or a list without it cannot pass :boot:test, and the failure looks like a workflow bug.

**Option.** Make the tests skip with a clear message when the plugin is absent, or always add it to testImplementation.

**Question to settle.** Which plugin combinations must CI cover?

</Accordion>
<Accordion title="Native build heap of 16 GB is unmeasured">
**Id** `xmx8g` · **Category** Operability · **Impact** 2 · **Effort** 1 · **Components** Native Image

**Why it matters.** `-J-Xmx16g` is set for the native build (it was 8 GB in the first guide, and 16 GB before that); neither value was measured. On a smaller runner the build can run out of memory, and on a larger project it may need more. The repository's CI workflows contain no native build job, so the figure is only exercised on a developer's or release machine.

**Option.** Measure peak use once, record it next to the flag, and fail with a clear message if memory is too small.

**Question to settle.** What is the smallest runner we want to support for native builds?

</Accordion>
<Accordion title="Native binary is not exercised by tests">
**Id** `nativeGap` · **Category** Reliability · **Impact** 3 · **Effort** 4 · **Components** Native Image, Acceptance Harness

**Why it matters.** All tests run on the JVM. Missing reflection or resource entries show up only when the binary runs. Plugin loading, JSON binding of records and the MCP tools are typical places.

**Option.** Add a smoke test that starts the built binary and runs one workflow, perhaps in CI after nativeCompile.

**Question to settle.** How often does a native-only failure reach users compared with JVM issues?

</Accordion>
<Accordion title="Everything is a single process with in-memory defaults">
**Id** `singleProc` · **Category** Availability · **Impact** 4 · **Effort** 5 · **Components** Assembled Application, Engine Tuning Defaults

**Why it matters.** A restart loses definitions, sessions and history unless files are configured. Update: boot can now include the PostgreSQL stores (`-Pyukta.persistence=postgres`, with `yukta.session.store-type=postgres`), and a control-plane/worker split with `-Pyukta.workers=true`; a leader lease allows an active/standby pair. The default build is still one process with in-memory state, and no persistent profile is documented as the default.

**Option.** Ship a documented persistent profile (file stores or PostgreSQL) and say which build flag it needs.

**Question to settle.** Is a persistent profile expected for production or is Yukta single-use per install?

</Accordion>
<Accordion title="Health show-details: when-authorized with no security">
**Id** `healthDetails` · **Category** Operability · **Impact** 2 · **Effort** 1 · **Components** Management Surface, Layered Configuration

**Why it matters.** Boot has no Spring Security, so in our view no caller can be authorised and detail fields are probably never shown. Operators then see only UP or DOWN. This was not run to confirm.

**Option.** Set show-details explicitly (never or always on loopback), or add the security that makes the rule meaningful.

**Question to settle.** What do operators expect to see at /actuator/health?

</Accordion>
<Accordion title="Config keys that nothing reads or that mislead">
**Id** `deadKeys` · **Category** Operability · **Impact** 2 · **Effort** 1 · **Components** Layered Configuration, Engine Tuning Defaults

**Why it matters.** The comment on yukta.logs.store.backend says memory | file, but only the memory store is registered. control.bus.\* repeats the code's own defaults, so the two can drift. A key with no reader is ignored in silence.

**Option.** Remove or implement them; keep one source for each default; test that every key in the files is read.

**Question to settle.** Who owns the list of supported keys?

</Accordion>
<Accordion title="Unhashed top-level assets cached for a year">
**Id** `staticStale` · **Category** Functionality · **Impact** 2 · **Effort** 2 · **Components** SPA Host

**Why it matters.** Patterns like /\*.json, /\*.svg, /\*.ico and /\*.webmanifest get the 365-day cache but are not content-hashed, so a changed icon or manifest can stay stale in browsers for a long time.

**Option.** Use a shorter cache or ETag for unhashed names and keep the year only for /assets/\*\*.

**Question to settle.** Which top-level files do we actually ship and how often do they change?

</Accordion>
<Accordion title="Unknown non-/api path returns 200 HTML">
**Id** `apiPath200` · **Category** Correctness · **Impact** 1 · **Effort** 1 · **Components** SPA Host

**Why it matters.** A mistyped REST path, for example /apis/workflows, returns index.html with 200. A client expecting JSON gets HTML and a confusing parse error.

**Option.** Limit the fallback to paths that look like screens (no file extension, no /api prefix), or return 404 for Accept: application/json.

**Question to settle.** Do external clients call the server with typos often enough to matter?

</Accordion>
<Accordion title="CSP covers only the fallback page and allows inline styles">
**Id** `cspScope` · **Category** Security · **Impact** 2 · **Effort** 3 · **Components** SPA Host

**Why it matters.** The policy is only on index.html. It allows style-src 'unsafe-inline' because React Flow needs inline styles. No other security headers (for example X-Content-Type-Options, HSTS) are set in boot.

**Option.** Use style nonces if the UI library allows, and add standard headers through a filter.

**Question to settle.** Is the UI exposed to untrusted content, such as plugin-supplied node designs?

</Accordion>
<Accordion title="Beans are found by package scan">
**Id** `scanBroad` · **Category** Governance · **Impact** 2 · **Effort** 2 · **Components** Assembled Application

**Why it matters.** Anything under com.infenia.yukta on the classpath becomes a bean. A plugin or test dependency that adds a component changes behaviour without any line in boot.

**Option.** List modules' configuration classes explicitly, or add a test that prints and checks the set of beans.

**Question to settle.** Do we want a single list of what is switched on?

</Accordion>
<Accordion title="The start-up guard accepts the MCP key alone and leaves /api open">
**Id** `guardMcpKeyOnly` · **Category** Security · **Impact** 4 · **Effort** 1 · **Components** Layered Configuration, Launcher

**Why it matters.** `ExposureGuard` refuses a non-loopback address only when `ApiKeys.read(environment, "yukta.mcp.api-key")` is empty. That call counts the MCP key as a key. The REST filter reads its keys with `ApiKeys.read(environment, null)`, which does not. So a server started with `YUKTA_SERVER_ADDRESS=0.0.0.0` and only `yukta.mcp.api-key` passes the guard, protects /mcp, and leaves /api and the actuator open to the network, which is exactly what the guard is meant to prevent. This looks unintended; confirm before changing.

**Option.** Make the guard read the same keys as the REST filter (or require both), and add a test for the MCP-key-only case to ExposureGuardTest.

**Question to settle.** Which setting should a single 'secure it' switch in the image set: one key for REST and MCP, or two?

</Accordion>
<Accordion title="A 4,386-line reflection config is checked in with no documented way to regenerate it">
**Id** `nativeMetaStale` · **Category** Evolvability · **Impact** 2 · **Effort** 3 · **Components** Native Image

**Why it matters.** `META-INF/native-image/com.infenia.yukta/boot/reflect-config.json` was added with the native-image fixes (PRs #368 and #370). Its entries register whole classes (all constructors, fields and methods) of libraries such as Caffeine. Neither `boot/build.gradle.kts` nor boot's CLAUDE.md says how it was produced or when to regenerate it. When a dependency or a plugin changes, a missing entry shows up only when the binary runs (see `nativeGap`), and stale entries are never noticed.

**Option.** Document the command that produced it (the tracing agent run), add a CI step that regenerates and diffs it, or prefer Spring's AOT hints over a hand-kept file.

**Question to settle.** Who will notice if a new dependency needs one more reflection entry?

</Accordion>

<Accordion title="Netty: the catalog wins now, but a stale 4.2.16 line remains and nothing asserts it">
**Id** `nettyTwoSources` · **Category** Security · **Impact** 2 · **Effort** 1 · **Components** Catalog & Root Build, Dependency Platform

**Why it matters.** Done (PR #373): `spring-conventions` now assigns `netty.version` from the catalog and imports the Netty BOM from it, and `:boot:dependencyInsight` on 2026-10-15 shows netty-codec-http at 4.2.18.Final, so a Dependabot bump of the catalog reaches the application. Still open: `gradle.properties` still contains `netty.version=4.2.16.Final` with its CVE comment, which misleads a reader and would win again if the assignment were removed; and no check fails when the resolved version differs from the catalog.

**Option.** Delete the gradle.properties line; add a small check (or test) that compares the resolved Netty with the catalog.

**Question to settle.** Which of the two numbers did we intend to ship, and who owns re-checking the other after a Dependabot bump?

</Accordion>
<Accordion title="Dependency locking is declared but no lock files exist">
**Id** `noLockfiles` · **Category** Security · **Impact** 3 · **Effort** 3 · **Components** Catalog & Root Build, CI Pipeline

**Why it matters.** The root build runs lockAllConfigurations() for every project, and the CI step 'Verify dependency lock files are up-to-date' exits at once because no gradle.lockfile is tracked (git ls-files finds none). Resolved versions can drift between builds, and the SBOM and Trivy documentation refers to lock files that do not exist.

**Option.** Generate and commit lock files (the CI step already shows the command), or remove the locking line and the lock-file docs until the team wants it. A middle path: lock only the boot runtime classpath.

**Question to settle.** Is reproducibility of resolved dependencies a goal today, or is the BOM pinning enough?

</Accordion>
<Accordion title="OpenGrep is skipped silently when the program is not installed">
**Id** `opengrepSilentSkip` · **Category** Operability · **Impact** 3 · **Effort** 2 · **Components** OpenGrep Gate

**Why it matters.** The task probes opengrep --version and skips on failure without a message. A developer gets a green local check and a red CI. Worse, a team that never installs it checks nothing locally. The skip exists so first-time contributors can build, but it hides the gate.

**Option.** Print a visible warning when skipped; add an opt-in flag that makes absence an error (for the pre-push hook); provide a wrapper that downloads the pinned binary like the Gradle wrapper does.

**Question to settle.** Is a contributor without OpenGrep better served by a warning, by a hard failure, or by an automatic download?

</Accordion>
<Accordion title="OpenGrep is cacheable now but still starts once per module">
**Id** `opengrepEveryModule` · **Category** Performance · **Impact** 1 · **Effort** 2 · **Components** OpenGrep Gate

**Why it matters.** Done: the task declares the SARIF report as an output and is cacheable, so a module whose sources and rules did not change is skipped. Still open: a changed module starts its own scan (one at a time, through the shared build service), and each module first starts `opengrep --version` to see whether the program exists.

**Option.** Run one root-level scan over all src/main folders, or probe for the program once per build.

**Question to settle.** Would one repository-wide scan lose anything we rely on per module, such as report location or --error behaviour?

</Accordion>
<Accordion title="Modules can disable quality tasks and nothing prevents it">
**Id** `disabledTasks` · **Category** Governance · **Impact** 3 · **Effort** 2 · **Components** Format & Static Analysis

**Why it matters.** Only jacocoTestCoverageVerification is guarded. mcp and plugin-api disable pmdTest; internal-core disables pmdMain, pmdTest and checkstyleTest; and constant-source disables pmdMain and pmdTest, each with a 'temporarily disabled' comment (four modules, up from three). internal-core is the module where untested plugin logic sits, so the weakest checks are on the code that benefits most from them.

**Option.** Extend the afterEvaluate guard to every quality task with an allow-list of dated, reasoned entries like coverage exceptions; then fix or burn down the three temporary disables.

**Question to settle.** Should disabling a quality task require the same written reason as lowering coverage, and should it expire?

</Accordion>
<Accordion title="Coverage verification passes when a module has no test data">
**Id** `coverageNoData` · **Category** Correctness · **Impact** 3 · **Effort** 1 · **Components** Coverage Policy

**Why it matters.** Both the report and the verification task have onlyIf \{ execution data exists \}. If a module's tests are deleted, filtered out or never run, verification is skipped and check passes with no coverage at all. The guard against disabling verification does not cover this.

**Option.** Fail when a module has main classes but no execution data (with an explicit opt-out for pure-API modules); or compare against a minimum test count.

**Question to settle.** Which modules legitimately have no tests, and can that list be written down?

</Accordion>
<Accordion title="Copyleft exception for the native image still lacks legal sign-off (L5)">
**Id** `legalSignoff` · **Category** Governance · **Impact** 4 · **Effort** 2 · **Components** Licence Gate

**Why it matters.** nashorn-core 15.4 (GPL-2.0 with Classpath Exception) is allowed by name, but the GraalVM native image links libraries statically. The improvements note marks sign-off as a human task still open. The written reason also names the wrong source: the library arrives via Handlebars in internal-core, not via GraalVM JS.

**Option.** Get a legal opinion and record it next to the exception; or drop the dependency by replacing Handlebars or excluding nashorn if it is not used at run time; fix the because() text.

**Question to settle.** Does the native image really ship nashorn-core, and who owns the legal decision before a first release?

</Accordion>
<Accordion title="Per-class 100% line and branch rule is very strict">
**Id** `strict100` · **Category** Evolvability · **Impact** 3 · **Effort** 3 · **Components** Coverage Policy

**Why it matters.** In our view, requiring every class to be fully covered pushes teams toward tests that only execute code to hit a branch, and makes each defensive branch cost a test. Only one exception exists today, so the rule seems livable, but generated code, reactive lambdas and rarely taken error paths are common sources of friction. Git history shows the default was lowered to 90/85 on 2026-10-10 (to stop exception sprawl) and raised back to 100/100 on 2026-10-11 in the 'full coverage' commit, which also deleted the exceptions; the docs were not updated.

**Option.** Keep 100% with the exception mechanism; or set 95% per class for lines and require 100% only for new code; add mutation testing to check test quality.

**Question to settle.** What is the policy's real purpose: preventing untested code, or preventing slippage, and is 100% per class the cheapest way to get that?

</Accordion>
<Accordion title="Docs say coverage is 90/85 and list exceptions that no longer exist">
**Id** `docDrift` · **Category** Operability · **Impact** 2 · **Effort** 1 · **Components** Plugin Hierarchy, Coverage Policy

**Why it matters.** build-logic/CLAUDE.md, the improvements note (L3) and the old guide say LINE 90% / BRANCH 85%; the code enforces 100/100. The old guide's exception table lists eight modules; only an empty block and one web exception exist. The root CLAUDE.md names Gradle 9.0 while the wrapper is 9.8.0. Wrong docs lead developers to expect exceptions they will not get.

**Option.** Correct the docs from the code now; add a test or script that reads the default from jacoco-conventions and prints it for docs.

**Question to settle.** Should rule values be documented once in code comments only, and linked from the docs?

</Accordion>
<Accordion title="build-logic and the root build scripts are not formatted or linted">
**Id** `selfUnchecked` · **Category** Governance · **Impact** 2 · **Effort** 2 · **Components** Format & Static Analysis

**Why it matters.** Spotless is applied per module through quality-conventions. Its Kotlin target `build-logic/**/*.gradle.kts` is relative to each module folder, so it never matches the included build; the root project applies Spotless with apply false. The convention scripts and root build scripts therefore get no header or format check (by reading the configuration; not run). The one place that decides every rule has the least checking.

**Option.** Apply Spotless in the root project for build-logic and root scripts; add a kotlinGradle target with an absolute path; or add ktlint.

**Question to settle.** Do we want the rule files treated like product code, with review and formatting checks?

</Accordion>
<Accordion title="Error Prone and SpotBugs run at default strength">
**Id** `advisoryTools` · **Category** Correctness · **Impact** 2 · **Effort** 2 · **Components** Format & Static Analysis

**Why it matters.** Error Prone has no -Werror or severity overrides, so its warnings print but pass. SpotBugs has no effort or report-level setting; only a small exclude file exists for reviewed false positives. Real findings can scroll by in the log. In our view this is a calibration gap, not a bug: the tools run, but their strictest useful settings have not been chosen.

**Option.** Choose a list of Error Prone checks to promote to error; set SpotBugs effort and threshold; keep exclusions in exclude.xml with a reason each.

**Question to settle.** Which three Error Prone or SpotBugs findings have caused real incidents or review comments here, and should those fail the build?

</Accordion>
<Accordion title="JDK 25 is required but not provisioned">
**Id** `noToolchainResolver` · **Category** Operability · **Impact** 2 · **Effort** 1 · **Components** Java & Test Setup

**Why it matters.** The toolchain requests Java 25 and neither settings file configures a toolchain resolver (such as foojay), so a machine without JDK 25 cannot build and the error is Gradle's generic one. CI installs Temurin 25 itself. New contributors hit this first.

**Option.** Add the foojay toolchain resolver plugin to settings; or document the JDK in the README and add a friendlier check.

<Accordion title="Tool permission is decided by a second parse of the request body">

<Accordion title="About eight envelope fields are carried but never acted on">
**Id** `unenforced` · **Category** Functionality · **Impact** 3 · **Effort** 3 · **Components** Envelope Contract, Header & History Ops, Port Routing (core)

**Why it matters.** The envelope offers expiration, reply-to, format indicator, retry count, control flag and the sequence fields, and gives them real accessors and withers. Nothing reads them to change behaviour. A plugin author who sets `expiration` expects the message to be dropped when late; it is delivered anyway. Whoever reads `retryCount` sees zero because the engine counts attempts in a header instead. Each unused field is a promise the code does not keep. Update: core now writes some of them on its own messages: Splitter fills in the sequence fields, correlation id, reply-to, expiration and format indicator for its children, and the engine adds `failure.*` headers. Still nothing reads expiration, format indicator, retry count or the control flag.

**Option.** Enforce the ones that matter (an expiry check in the inbound hook; a sequence-aware aggregate) and delete or mark the rest as reserved. Or document each as informational in the interface.

**Question to settle.** Which of these fields do you want as real features in the next year, and which should be deleted so nobody trusts them?

<Accordion title="The channel SPI is unproven for remote or durable transport">
**Id** `remoteSpi` · **Category** Evolvability · **Impact** 4 · **Effort** 4 · **Components** Channel SPI, Direct Channel

**Why it matters.** The SPI takes a Reactor stream of in-process objects and returns one. There is no acknowledgement, no redelivery, no serialisation rule and no signal for 'the other side is slow'. The only implementation does nothing. If a team plugs a network or disk transport into this hook, they will discover the missing contract the hard way.

**Option.** Write the contract first: what a channel must do on failure, whether it may drop, how it signals back-pressure, how messages are encoded. Build one real channel (for example a durable file channel) to test it.

**Question to settle.** Is this SPI meant to carry messages between machines, or only to decorate local streams? The answer decides how much contract it needs.

<Accordion title="The default-provider override depends on Spring bean order">
**Id** `conditionalOrder` · **Category** Reliability · **Impact** 3 · **Effort** 2 · **Components** Default Wiring, Channel SPI

**Why it matters.** The default provider is guarded by `@ConditionalOnMissingBean`, a condition built for auto-configuration classes that Spring processes last. Here it is on a normal class found by component scanning, with no auto-configuration registration. A custom provider declared in a class that Spring reads later could end up registered next to the default. Core would then see two providers and the server would not start. In our view the tests only prove the easy order.

**Option.** Register the default through `AutoConfiguration.imports`, or make the provider injection tolerate several beans with a clear rule, or add a startup check that fails with an explicit message.

**Question to settle.** Has any team actually added a custom provider in a scanned class, and in which order did Spring read it?

<Accordion title="No payload size limit or claim check">
**Id** `payloadSize` · **Category** Performance · **Impact** 4 · **Effort** 4 · **Components** Envelope Record, Header & History Ops

**Why it matters.** The payload is any Java object and nothing here limits its size. Each message is carried through memory and copied into checkpoint files by core. A 50 MiB payload is passed by reference between nodes but is also serialised to JSON for the checkpoint, and cannot be replayed once it passes core's cap. This is the messaging side of core's large-payload risk.

**Option.** Add a claim-check pattern: store the large body elsewhere and carry only a reference in the message. Add an optional size check in the inbound hook.

**Question to settle.** What is the largest message you expect within a year, and who should refuse it: the envelope, the channel or the plugin?

<Accordion title="Payload is an untyped Object with no schema">
**Id** `untypedPayload` · **Category** Correctness · **Impact** 3 · **Effort** 4 · **Components** Envelope Contract, Envelope Record

**Why it matters.** `Message<T>` has a type parameter, but every stream in the engine is `Flux<Message<?>>`, so the type is erased at the boundary. Producers and consumers agree only by convention. A checkpoint read-back turns the payload into plain JSON values, so a plugin that stored a Java record gets a map after a resume. The `formatIndicator` field was meant to carry this information, but nobody uses it.

**Option.** Add an optional schema or type hint that is checked by the inbound hook; or define a canonical payload model (JSON tree) and say so.

**Question to settle.** Should the engine promise that a payload survives a resume with its original type, or only as a JSON tree?

**Id** `wideContract` · **Category** Evolvability · **Impact** 2 · **Effort** 3 · **Components** Envelope Contract, Envelope Record, Build & Tests

**Why it matters.** The interface has 22 accessors and 18 withers, and only one class implements it. Every new field means edits in the interface, the record, two copy paths and the tests. In our view the interface adds change cost without the benefit of alternative implementations, and the 22-slot record is already large.

**Option.** Keep the interface small (read-only accessors plus a few core withers) and let the record carry the rest; or accept the width and add a test that fails when a field is not copied.

<Accordion title="Two hand-written copy paths must list all 22 fields">
**Id** `copyDrift` · **Category** Correctness · **Impact** 3 · **Effort** 2 · **Components** Envelope Record, Factories

**Why it matters.** The instance `withPayload` and the static `from` each copy every field one by one. If a new field is added to the record and one path is forgotten, derived messages silently lose it. One test checks `from` field by field today. Nothing prevents the paths from drifting.

**Option.** Implement both through `toBuilder()` (which copies all fields) and change only the payload; or generate the copy.

**Question to settle.** Would a test that compares all record components by reflection be enough, or should the copy be done by the compiler?

<Accordion title="Immutability is shallow: payload and header values are shared">
**Id** `shallowImmutable` · **Category** Correctness · **Impact** 3 · **Effort** 3 · **Components** Envelope Record, Header & History Ops, History Stamp (core)

**Why it matters.** The envelope itself cannot change, but the payload object and every object stored in metadata are shared by reference. Core fans out the same message to every child. If one plugin edits a list inside the payload, a sibling branch sees the edit, possibly half-way through its own work. Bugs of this kind show up rarely and are hard to reproduce.

**Option.** Document 'payloads are read-only'; add defensive copies in plugins that edit; or provide a payload copier or freeze step for collections in the inbound hook.

**Question to settle.** Would you pay a copy per fan-out to make payloads safe, or rely on plugin discipline?

<Accordion title="History capped at 64 loses lineage in long chains and loops">
**Id** `historyCap` · **Category** Operability · **Impact** 2 · **Effort** 2 · **Components** Envelope Record, History Stamp (core)

**Why it matters.** Only the last 64 node ids are kept and nothing records that older entries were dropped. A message that loops or passes through many nodes loses the beginning of its journey. A reader cannot tell 'started at node 1' from 'the first 40 were dropped'. The trace id and checkpoints remain, so lineage can still be rebuilt elsewhere.

**Option.** Keep a counter of dropped entries, or the first entry plus the last N. Or move lineage to the tracker and keep only a short window in the message.

**Question to settle.** What question do you want history to answer, and is a sliding window enough for it?

</Accordion>
<Accordion title="Split and aggregate restart history and identity">
**Id** `lineageReset` · **Category** Correctness · **Impact** 3 · **Effort** 3 · **Components** Factories, History Stamp (core)

**Why it matters.** Splitter and Aggregate build their outputs with `create`. A split child has a new id and an empty history. An aggregate keeps only the trace id of the first message in the batch and drops metadata, correlation and sequence. After either node, lineage questions ('where did this come from?') can be answered only through the trace id and the child's correlation id. The behaviour is deliberate but not written down as a rule.

**Option.** Carry the parent's history (or a link to it) into children and a list of source ids into an aggregate. Document the rule either way.

**Question to settle.** After a split, is a child 'the same message' or 'a new one with a parent'? The answer decides what lineage means.

</Accordion>
<Accordion title="Channel errors are outside the node's retry and error-port policy">
**Id** `channelErrors` · **Category** Reliability · **Impact** 3 · **Effort** 3 · **Components** Channel SPI

**Why it matters.** Core's per-message retry and error routing wrap the plugin call. The channel wraps the stream around it. An exception thrown in `inbound` or `outbound` therefore fails the node's stream instead of being retried or sent to the error port, and one bad message can stop the node. The default channel cannot throw, so this is untested.

**Option.** Define the failure contract for channels. For example, run the channel inside the policy for per-message channels, or document that it must never throw.

**Question to settle.** If a channel fails on one message, should that message dead-letter, or should the whole node stop?

</Accordion>
<Accordion title="The message id is logical, not unique per node output">
**Id** `idNotUnique` · **Category** Correctness · **Impact** 2 · **Effort** 2 · **Components** Envelope Contract, Factories

**Why it matters.** Because `from` keeps the id, the same id appears on the output of every node that derives from it, and on retries. A store or log that uses the id alone as a key will overwrite. The interface says so, but the field is called 'id' and invites misuse. Core's checkpoint store keys by (execution, node, id) for this reason.

**Option.** Add a separate per-output sequence or a 'lineage id' field; or rename the accessor to make the meaning obvious.

**Question to settle.** Do you need a unique id per output, for tracing a single hop?

</Accordion>
<Accordion title="Identity and control fields are unverified">
**Id** `forgeable` · **Category** Security · **Impact** 3 · **Effort** 3 · **Components** Header & History Ops, Envelope Contract

**Why it matters.** A plugin can set trace id, correlation id, workflow id, priority and the control flag on any message it emits. Core overwrites only the source node. Today the control flag is not read and the control bus ignores data messages, so the exposure is small. Another consumer could one day trust one of them. In our view the module should say which headers are trusted. The engine's own `failure.attempts`, `failure.exception` and `failure.time` headers are ordinary metadata too: a plugin can overwrite them on a message it emits.

**Option.** Define which headers are engine-owned and re-stamp them in core, as with the source node; or sign engine-owned headers.

**Question to settle.** Which headers should a plugin never be able to set?

</Accordion>
<Accordion title="Every header change copies the whole metadata map">
**Id** `metadataCopy` · **Category** Performance · **Impact** 2 · **Effort** 2 · **Components** Envelope Record, Header & History Ops

**Why it matters.** `withHeader` copies the map into a mutable one, changes it, then the constructor copies it again into an unmodifiable one and scans it for nulls. A plugin that sets ten headers one by one does it ten times, each time a bit bigger. Fine for a handful of headers; a cost for metadata-heavy flows like LLM usage or HTTP response headers.

**Option.** Offer a bulk `withHeaders(map)`, or make plugins use `toBuilder().metadata(...)`. Measure first.

**Question to settle.** How many headers does a typical message carry by the end of a workflow?

</Accordion>
<Accordion title="Null header values vanish silently">
**Id** `nullSilent` · **Category** Correctness · **Impact** 2 · **Effort** 1 · **Components** Header & History Ops, Envelope Record

**Why it matters.** Setting a header to null removes it, and a map with null values has those entries dropped, without a log or an error. A plugin that sets a header to null to mean 'unknown' will see the key disappear and may then treat it as 'never set'. The rule is documented and tested, but it differs from how a plain map behaves.

**Option.** Keep the rule but add a sentinel for explicit absence, or log at debug level when entries are dropped.

**Question to settle.** Is 'unset' and 'null' the same thing for your headers?

</Accordion>
<Accordion title="The envelope is now a wire format for remote workers">
**Id** `wireFormat` · **Category** Evolvability · **Impact** 3 · **Effort** 3 · **Components** Envelope Contract, Envelope Record

**Why it matters.** Remote workers (core `workers` module, `WorkerNodeExecutor`) send every message as JSON and rebuild it with `mapper.convertValue(frame.message(), DefaultMessage.class)`. So the 22 record components are now a network contract: adding, renaming or retyping a field changes what an older worker or control plane understands, and nothing in the record or the frame carries a version. The payload and metadata values come back as plain JSON values (Map, List, String, Number), not the Java types the sender held. A plugin that stores a `Duration` or a POJO in a header sees a different type on a placed node than on a local one.

**Option.** Decide the wire shape on purpose: a version field on the frame, a test that round-trips every field and checks metadata types, and a rule 'headers are JSON values only'. Check this together with the claim-check decision for large payloads.

**Question to settle.** Which header values do your plugins store that are not plain JSON, and would they survive a trip to a worker?

</Accordion>
<Accordion title="Edge-buffer drops happen before the channel sees the message">
**Id** `edgeDropsUnseen` · **Category** Operability · **Impact** 2 · **Effort** 1 · **Components** Channel SPI, Direct Channel

**Why it matters.** A node with `engine.edgeBuffer` gets a bounded buffer in front of it, and core builds it as the argument to `channel.inbound` (ProcessorNodeAssemblerStrategy). A message dropped by the buffer therefore never reaches the channel. The only trace is the counter `yukta.edge.dropped{type}`, which has no node or execution tag. An audit, signing or metering channel that is meant to see every message cannot see these, and the SPI has no way to be told.

**Option.** Document that a channel sees only what the buffer let through, or move the buffer inside the channel hook, or add a node tag to the counter. The first is enough while only the direct channel exists.

**Question to settle.** Is a dropped message something an audit channel must record?

</Accordion>
</AccordionGroup>

<AccordionGroup>
<Accordion title="The startup log rewrite is not atomic">
**Id** `logReplaceAll` · **Category** Reliability · **Impact** 4 · **Effort** 2 · **Components** Execution log, Leader lease

**Why it matters.** Startup recovery and takeover recovery call `ExecutionLogStore.replaceAll` with the runs to keep. In this module it runs `DELETE FROM execution_log` and then one `INSERT` per kept event, each waited for up to 30 s, with no transaction. A crash, a lost connection or a leader change after the delete leaves the log empty or partial. The log is what tells recovery which runs were interrupted and what their start payload was, so every run that could have been resumed is lost at once. With up to 500 runs of many events each, the window is also long (one round trip per event). The previous leader, if still alive, may append while the delete is running.

**Option.** Do the rewrite in one transaction, or delete only the rows that fall outside the kept runs instead of replacing everything; batch the inserts.

**Question to settle.** What would you lose if the server died while recovery was rewriting the log, and how would you know?

</Accordion>
<Accordion title="Execution log events can be lost without the run knowing">
**Id** `logDropsEvents` · **Category** Reliability · **Impact** 3 · **Effort** 3 · **Components** Execution log

**Why it matters.** `append` puts the event in a queue of 10,000 and returns. If the queue is full the event is dropped and an error line is logged. A batch that fails is retried one event at a time, and an event that still fails is logged and skipped. Events still in the queue die with the process. The run itself is told nothing, so a lost `RUN_STARTED` means the run cannot be resumed and a lost `RUN_FINISHED` makes a finished run look interrupted.

**Option.** Count dropped and failed events in a meter and alert on it; for the start and end events wait for the insert (or retry) before the run continues; raise the queue only if the cause is bursts.

**Question to settle.** Is a lost run-end event acceptable, given that recovery then marks a finished run ABORTED?

</Accordion>
<Accordion title="The fencing number is produced but never checked">
**Id** `fencingUnused` · **Category** Reliability · **Impact** 3 · **Effort** 3 · **Components** Leader lease

**Why it matters.** The lease row carries a fencing number that grows with every change of holder, and `fencingToken()` returns it, but no write in this module or in core uses it. A leader that was paused longer than the lease (a long stop-the-world pause, a suspended VM, a network stall after it checked `isLeader()`) can still finish a write after another server has become leader. The local validity check protects against a server that cannot reach the database, not against one that is stuck between the check and the write.

**Option.** Pass the token with the writes that matter (the log append, checkpoint writes, definition saves) and refuse a write whose token is older than the one in the lease row, for example by comparing in the same statement.

**Question to settle.** Which write would hurt most if an old leader finished it after a takeover?

</Accordion>
<Accordion title="Multi-step operations are not transactional">
**Id** `noTransactions` · **Category** Correctness · **Impact** 3 · **Effort** 3 · **Components** Definitions & sessions, Node checkpoints

**Why it matters.** These operations are several statements with no transaction: removing a workflow (versions, then the current row), removing all workflows of a session, applying a session config (the row, then each workflow), a save followed by the prune of old versions, and a checkpoint save followed by the end marker. A failure in between leaves a workflow with versions and no current row, a half-applied session, 21 versions, or a node with all its output and no stamp (which a resume handles by running the node again). There are no foreign keys either, so nothing in the database notices.

**Option.** Wrap the multi-step methods in a transaction with Spring's `TransactionalOperator` (R2DBC supports it), or merge them into single statements; add foreign keys with cascading deletes where the tables are parent and child.

**Question to settle.** After a failed apply, would an operator be able to tell which workflows of the session were saved?

</Accordion>
<Accordion title="Several store calls wait for the database on the calling thread">
**Id** `blockingCalls` · **Category** Performance · **Impact** 3 · **Effort** 3 · **Components** Connections & drivers, Node checkpoints, KV and chat history

**Why it matters.** `isComplete` and `isFinished` (30 s), `clear` (30 s), the history `load` and `save` (10 s) and the lease release (10 s) convert a Mono to a future and wait. The interfaces they implement are blocking by design, so the module cannot make them non-blocking by itself. On a Reactor or event-loop thread a slow database holds that thread for the whole wait, once per node on a resume, and a timeout is silently treated as 'unfinished' or 'empty'.

**Option.** Make the interfaces reactive (see the plugin-api guide) or have the callers run these methods on the blocking scheduler; meter the wait time.

**Question to settle.** How many nodes does your largest run have, and what is the database latency on a bad day?

</Accordion>
<Accordion title="Trimming the log scans the whole table">
**Id** `compactionCost` · **Category** Performance · **Impact** 3 · **Effort** 3 · **Components** Execution log

**Why it matters.** Every 10,000 appended events the writer runs a delete whose subqueries group the whole `execution_log` by execution id (ordering by the maximum sequence) and test each run for a start without an end with `bool_or` over the JSONB `type`. There is no index on the event type, so it reads every row. It runs on the single writer thread, so appends queue up behind it, and the queue holds only 10,000 events.

**Option.** Store the event type (and an 'open run' flag) in real columns with an index; trim by a time or sequence bound instead of grouping everything; run the trim in a separate task.

**Question to settle.** How long does the trim take with 500 runs of 2,000 events each, and what happens to the queue meanwhile?

</Accordion>
<Accordion title="Reads load whole sets into memory">
**Id** `readsWholeSets` · **Category** Scalability · **Impact** 3 · **Effort** 3 · **Components** Execution log, Node checkpoints

**Why it matters.** `readAll` loads every row of the execution log (up to 500 runs) at start and at every takeover; `get` on a checkpoint reads every row of the node to return the last one; `getAll` collects a node's output on resume; `findAll` loads all definitions of a session. Memory use and latency grow with the amount of history, and a very large node output is held in memory on resume (the table has no size cap on purpose).

**Option.** Read the log in a cursor and process run by run; fetch only the last row for `get` (order by sequence descending, limit 1); stream node output into the replay.

**Question to settle.** What is the largest node output you expect to replay?

</Accordion>
<Accordion title="The chat-history ttl is a table scan on every save">
**Id** `historyTtlScan` · **Category** Performance · **Impact** 2 · **Effort** 1 · **Components** KV and chat history

**Why it matters.** With `yukta.session-memory.ttl` set, each save runs `DELETE FROM session_history WHERE updated_at < now() - ...`, and the table has no index on `updated_at`, so every chat turn scans the table. The delete happens only on a save, so with no traffic expired sessions stay, and `load` does not check the ttl, so an expired session is still returned until some other session is saved.

**Option.** Add an index on `updated_at` (a V7 migration); delete at most every N seconds, or in a scheduled task; check the age in `load`.

**Question to settle.** Is a conversation older than the ttl allowed to reappear?

</Accordion>
<Accordion title="The KV size cap is not exact and counts all rows on each new key">
**Id** `kvCapRace` · **Category** Correctness · **Impact** 2 · **Effort** 2 · **Components** KV and chat history

**Why it matters.** A new key is inserted only if `count(*)` of the table is below `maxEntries`. Two concurrent statements can both read a count below the cap (the default isolation does not serialise them) and both insert, so the cap can be passed by the number of concurrent writers. The count is also taken for every new key. The table is shared by every KV_STORE node of every workflow, and keys are only separated by the optional namespace.

**Option.** Document the cap as approximate, or serialise new-key inserts with an advisory lock; keep a counter row instead of counting.

**Question to settle.** Does anything depend on the cap being exact?

</Accordion>
<Accordion title="Sessions can never be deleted from the database">
**Id** `noDelete` · **Category** Functionality · **Impact** 2 · **Effort** 3 · **Components** Definitions & sessions

**Why it matters.** The `SessionConfigStore` interface has no delete, so rows in `session_config` stay for ever. `WorkflowDefinitionStore.removeAll` exists in every store but has no caller in core. Run history of a deleted session is trimmed only by the global 500-run rule. Anyone who needs to remove a tenant's data (a customer asks) must delete from nine tables by hand.

**Option.** Add a session delete to the interface and implement it for all stores (definitions, config, log events of the session's runs, checkpoints, history) in one transaction.

**Question to settle.** How would you answer a request to delete everything about one session?

</Accordion>
<Accordion title="Nothing expires rows apart from the log trim and the optional chat ttl">
**Id** `noRetention` · **Category** Operability · **Impact** 2 · **Effort** 3 · **Components** Schema migrations

**Why it matters.** Checkpoints are cleared when core evicts a run from its archive of retained executions (10 by default) and for runs dropped at recovery, but a run that never reaches either path leaves its rows. `kv_entry` grows with distinct keys. `session_config` and its definitions only grow. `workflow_definition_revision` is bounded to 20 per workflow, but not the number of workflows. There is no sweep, no size alert and no documented clean-up job.

**Option.** Add a periodic clean-up of checkpoint rows whose run is not in the log, document the sizes to watch, and add them to the metrics.

**Question to settle.** Which table will be the largest after a year, and who looks at it?

</Accordion>
<Accordion title="Migration and run time use two sets of connection settings, often the same account">
**Id** `twoConnections` · **Category** Security · **Impact** 2 · **Effort** 2 · **Components** Connections & drivers

**Why it matters.** Flyway needs a JDBC URL, user and password; the application needs an R2DBC URL. Nothing in the module separates the two accounts, and the simplest setup uses one account for both, so the running application can alter or drop tables, and an SQL injection somewhere else in the application would have the same reach. The settings are two places that can drift (a changed host or database name in one).

**Option.** Document two accounts (migrator with DDL rights, application with data rights only) and show the grants; fail at start if the application account can create tables, as an option.

**Question to settle.** Who holds the password of the database owner, and where is it written?

</Accordion>
<Accordion title="Each store has its own switch, so a deployment can be half durable">
**Id** `halfDurable` · **Category** Operability · **Impact** 3 · **Effort** 2 · **Components** Auto-configuration, KV and chat history

**Why it matters.** Five properties select five groups of stores, and nothing checks that they agree. PostgreSQL definitions with in-memory checkpoints look durable but cannot resume a run; `yukta.ha.mode=postgres` without PostgreSQL checkpoints lets a standby take over but not continue a run from its recorded output (auto-resume then reruns everything); a typo in a `store-type` value silently selects the default.

**Option.** At start, log one line listing which store is in use for each kind of data; warn when HA is on and checkpoints are not in PostgreSQL; refuse unknown store-type values.

**Question to settle.** Can an operator tell from the running server which stores are durable?

</Accordion>
<Accordion title="The stores report almost nothing about themselves">
**Id** `noStoreMetrics` · **Category** Operability · **Impact** 2 · **Effort** 2 · **Components** Connections & drivers, Execution log

**Why it matters.** The module registers one meter, `yukta.leader`. There is no health indicator, no meter for the log queue depth, dropped or failed events, statement time, retries or lock waits. The only signals are log lines. Combined with the silent defaults ('unfinished', 'empty', 'event dropped') a degraded database can look healthy from outside.

**Option.** Add meters (queue depth, drops, failed batches, statement latency) and a health indicator that runs a trivial query with a short timeout.

**Question to settle.** What would page you if the log writer stopped inserting?

</Accordion>
<Accordion title="The checkpoint byte counter is per JVM and mixes units">
**Id** `heldBytesDrift` · **Category** Operability · **Impact** 1 · **Effort** 1 · **Components** Node checkpoints

**Why it matters.** `bytesHeld()` (shown as the core meter `yukta.checkpoint.bytes`) adds the length of the JSON text in characters on save and subtracts the database's byte count on clear, in this JVM only. It starts at zero after a restart although the table holds data, and on a standby it stays zero. With non-ASCII payloads characters and bytes differ.

**Option.** Compute the value from the table on demand (a sum of octet_length), or label the meter as 'written by this process'.

</Accordion>
<Accordion title="Session settings are partly not stored and read with many queries">
**Id** `sessionConfigGaps` · **Category** Functionality · **Impact** 2 · **Effort** 2 · **Components** Definitions & sessions

**Why it matters.** The execution timeout and the log directories returned for a session come from the global `SessionConfigProperties`, not from the table, so a per-session setting cannot be kept. `getAllConfigs` runs about seven queries for one session, and `getSessionIds` lists only sessions that have a config row, so a session that has definitions but no row is invisible. Initiator, description, initiated time and tags are written only while empty, but an apply replaces the initiated time each time.

**Option.** Store the per-session values or drop them from the interface; read a session in one query; list ids from the union of both tables.

</Accordion>
<Accordion title="Migrations are forward-only and never tested on data">
**Id** `noMigrationPlan` · **Category** Evolvability · **Impact** 2 · **Effort** 3 · **Components** Schema migrations, Tests & build

**Why it matters.** Six migrations exist and the test support runs them on an empty database. There are no down scripts, and no test upgrades a database that already holds data written by an older version. The stored JSON documents have no version field, so a renamed record component changes what old rows mean without any migration noticing.

**Option.** Add an upgrade test that loads rows written by the previous release and migrates them; add a version field to stored documents; document how to roll back (restore a backup).

**Question to settle.** How would you roll back a release that includes a bad migration?

</Accordion>
</AccordionGroup>

<AccordionGroup>
<Accordion title="A hung reviewer blocks commands, including a human stop">
**Id** `reviewNoTimeout` · **Category** Availability · **Impact** 4 · **Effort** 2 · **Components** Supervisor SPI, Control commands

**Why it matters.** review() has no time limit in the SPI, and core's reviewer does not add one. Core runs the commands of one run one after another, and the review is part of each command's turn. If one supervisor's review never completes (an external call stalls), later commands for that run wait behind it, including a StopWorkflow from a person. All runs are affected if the reviewer hangs on every call. The same wait now also covers the two commands added for the scheduler (SetLimitsCommand, SetPriorityCommand), which pass through review too, so a hung reviewer can block an operator who is trying to change the limits during an overload.

**Option.** Add a timeout to each review in core and define the outcome (deny, or allow for stop); exempt StopWorkflow from review or give it a short-circuit; require implementers to use a timeout and test for it.

**Question to settle.** When a safety check cannot answer, should the command be allowed or denied, and should a stop ever be vetoable?

</Accordion>
<Accordion title="decide() has no enforced time bound">
**Id** `decideStall` · **Category** Reliability · **Impact** 3 · **Effort** 2 · **Components** Supervisor SPI

**Why it matters.** ControlPlanePlugin.supervise handles events one at a time (concatMap). The Javadoc asks decide() to finish in bounded time, but nothing enforces it. A model call that hangs stalls every later event for that plugin, so the plugin stops reacting while looking healthy.

**Option.** Apply a default timeout in the default supervise (timeout counts as no opinion); expose the limit as a setting; surface a stalled-plugin metric.

**Question to settle.** Is a single stuck decision better handled by skipping to the next event or by failing the whole supervisor so it resubscribes?

</Accordion>
<Accordion title="Two opposite ordering rules">
**Id** `orderOpposite` · **Category** Evolvability · **Impact** 2 · **Effort** 1 · **Components** Supervisor SPI, Command processing

**Why it matters.** Supervisor order(): lowest runs first. ControlSignalProcessor getPriority(): highest wins. A developer who sets 'priority 1 = most important' on both gets the reverse of what they meant on one of them. Built-ins use 10-20 for processors, so a wrong guess is easy.

**Option.** Rename to make direction obvious (reviewOrder, overridePriority); or align both to one rule; add a startup log of the effective order.

**Question to settle.** Would aligning the two rules be worth a breaking change, given how few external implementers exist today?

</Accordion>
<Accordion title="Expression sandbox: allow-list done, still no time budget and a shared lock">
**Id** `spelLimits` · **Category** Security · **Impact** 3 · **Effort** 2 · **Components** Expression sandbox

**Why it matters.** Done: expressions can call only a short allow-list of methods (SafeMethodResolver: about 40 names such as length, contains, substring, plus every type in java.time), so repeat, getClass and the methods of a payload object are not found; tested. Also done: an evaluation now stops after `yukta.spel.timeout-ms` (1 s by default); method calls, property reads and the text a `matches` or `split` regex reads check the clock, so a regex with catastrophic backtracking is cut off, and Spring itself stops selections and projections after 10,000 operations. Still open: (1) there is no size budget, so a call on a very large string still runs; (2) the parsed-expression cache is a synchronized LinkedHashMap, so `computeIfAbsent` parses while holding its one lock and a slow parse delays every other plugin; (3) no expression length limit was found in the validators.

**Option.** Add a size budget; parse outside the lock (a concurrent cache); limit expression length at validation.

**Question to settle.** Who writes expressions today: only trusted authors, or any API caller? That decides how much of this matters.

</Accordion>
<Accordion title="Statelessness of the shared instance is documented, not enforced">
**Id** `sharedInstance` · **Category** Correctness · **Impact** 3 · **Effort** 3 · **Components** Plugin contract, Graph context, liveness, Expression sandbox, Failure & config helpers

**Why it matters.** One object serves every node, workflow and session, and initialize and prepare run again for each node on that same object. A plugin that stores config in a field works in a demo with one node and mixes up settings with two. Nothing in the interface or the tests catches it.

**Option.** A conformance test plugins can run (two nodes, different configs, interleaved); an instance-per-node factory option; or pass a per-node context object into each call.

**Question to settle.** Should the contract move state into an explicit per-node object, accepting a larger interface, or keep the shared instance and add enforcement tests?

</Accordion>
<Accordion title="shutdown(config) is on the contract but never called">
**Id** `shutdownNever` · **Category** Operability · **Impact** 2 · **Effort** 2 · **Components** Plugin contract

**Why it matters.** The interface advertises a cleanup hook, and the Javadoc says the engine does not call it. An author who skims the interface leaks a connection pool or scheduled task, and nothing warns.

**Option.** Remove the method, or call it for each plugin once at application stop; mark it deprecated with a clear message in the meantime.

**Question to settle.** Is any plugin relying on it today, and would a once-per-plugin lifecycle hook (not per node) be more honest?

</Accordion>
<Accordion title="No SPI version marker">
**Id** `noVersion` · **Category** Evolvability · **Impact** 3 · **Effort** 2 · **Components** Plugin contract, Build & test setup

**Why it matters.** The contract has no version constant or capability flag. A plugin built against an older plugin-api can fail with an obscure link error at runtime, and the engine cannot say which plugin is incompatible. This matters once plugins ship separately from the server.

**Option.** Add an SPI version constant and a Plugin.apiVersion() default; check at startup and name the plugin; adopt semantic versioning of the module with a compatibility test.

**Question to settle.** Do we expect plugins built outside this repository, and if so how long must an old plugin keep working?

</Accordion>
<Accordion title="WorkflowDirective has only Stop">
**Id** `directiveOnlyStop` · **Category** Evolvability · **Impact** 2 · **Effort** 3 · **Components** Command processing

**Why it matters.** The directive layer is meant as the place where processors hand an action to the dispatcher, but only Stop exists. Every other built-in processor performs its work itself and returns nothing, so a custom processor cannot express 'pause' as a directive and the sealed hierarchy adds ceremony without extension room.

**Option.** Either grow the directive set (pause, resume, restart, and so on) and make built-ins return them, or simplify the SPI to a plain apply function.

**Question to settle.** Is the directive layer the intended extension seam, or a leftover from an earlier design?

</Accordion>
<Accordion title="Unused optimiser hooks on the contract">
**Id** `deadHooks` · **Category** Functionality · **Impact** 2 · **Effort** 1 · **Components** Plugin contract

**Why it matters.** isComputationallyHeavy and suppressOptimizationHint are documented as used by validators for performance hints. Nothing in core or web calls them; one built-in plugin reads its own. Authors implement them for no effect, and the old guide's claim that they are 'used' is misleading.

**Option.** Either implement the validator hint they were meant for, or remove them from the interface.

**Question to settle.** Is a graph optimisation hint something users want, or should the filter plugin keep its own check?

</Accordion>
<Accordion title="Node signals are untyped">
**Id** `onSignalLoose` · **Category** Functionality · **Impact** 2 · **Effort** 3 · **Components** Plugin contract, Control commands

**Why it matters.** onControlSignal takes a raw Message and returns one. A caller must know by convention which payloads a plugin understands. The 16 typed commands go to the engine, not to plugins, so plugin-specific actions have no typed shape, no schema in the descriptor and no discovery. Update: the approval flow now has a convention (SignalWaits: a payload map with executionId, nodeId, name, decision, data, answered ACCEPTED, QUEUED or NOT_WAITING), and a typed SignalNodeCommand carries it to the plugin. That fixes the shape for approvals only; another plugin still has no way to declare the signals it accepts.

**Option.** Let a plugin declare the signals it accepts in its descriptor (name and payload schema); validate before delivery; consider a typed plugin-command record.

**Question to settle.** Do callers need to discover a plugin's signals at run time, or are they always scripted per plugin?

</Accordion>
<Accordion title="Supervisors can miss events">
**Id** `eventsBestEffort` · **Category** Reliability · **Impact** 3 · **Effort** 3 · **Components** Supervisor SPI

**Why it matters.** The feed drops events for a slow subscriber and has no replay. A supervisor that must react to every failure (or every ControlOutcome) cannot be sure it saw them. Drops are counted in a metric, but the supervisor itself is not told.

**Option.** Tell the supervisor how many events it missed; offer a durable cursor-based feed from the execution log; mark which supervisors need reliable delivery and size their buffer.

**Question to settle.** Is it acceptable for an automated safety rule to miss an event under load, or should critical rules read from the durable log?

</Accordion>
<Accordion title="Some checkpoint calls are synchronous">
**Id** `storeSync` · **Category** Performance · **Impact** 3 · **Effort** 3 · **Components** Store SPIs

**Why it matters.** clear, isComplete and isFinished return plain values, while save and get return Monos. This is no longer only a prediction: `R2dbcNodeCheckpointStore` now answers isComplete and isFinished by querying the database on the calling thread (its Javadoc says they are blocking in the interface), on the path that decides what a resume skips. The new `SessionHistoryStore` SPI is blocking by design as well (load and save return plain values; the PostgreSQL implementation waits up to 10 s on the calling thread). `KeyValueStore` is reactive, so the newest store SPI shows the intended shape.

**Option.** Add reactive versions (clear returns Mono, isComplete and isFinished return Mono&lt;Boolean&gt;, SessionHistoryStore returns Mono) with the current ones deprecated; or document that stores must answer from local memory and mark the plugins that call them as blocking.

**Question to settle.** Will the database-backed store cache these answers locally, or should the contract become fully non-blocking?

</Accordion>
<Accordion title="Secret lookup has no caller identity or scope">
**Id** `secretThin` · **Category** Security · **Impact** 3 · **Effort** 3 · **Components** Store SPIs

**Why it matters.** getSecret(key) takes only a key. The provider cannot tell which plugin, workflow or session is asking, so it cannot grant one team's secrets only to that team, and it cannot audit who read what. In our view this limits multi-tenant use.

**Option.** Pass a context (session, workflow, plugin type) to the provider; log access; support per-session allow lists.

**Question to settle.** Are secrets expected to be global to the server, or per session or tenant?

</Accordion>
<Accordion title="No test kit for plugin authors">
**Id** `noTestKit` · **Category** Operability · **Impact** 3 · **Effort** 3 · **Components** Build & test setup

**Why it matters.** The java-test-fixtures plugin is applied but the module has no fixtures. Every plugin author re-creates message builders and a way to run a plugin like the engine (context keys, heartbeat, subscribeOn). Mistakes there make unit tests pass for plugins that fail in a real run.

**Option.** Ship fixtures: a message factory, a harness that sets the Reactor context and runs the validation hooks, and a conformance suite (statelessness, ports, config checks).

**Question to settle.** What is the smallest harness that would have caught the bugs we saw in plugins so far?

</Accordion>
<Accordion title="PMD is disabled for the test sources">
**Id** `pmdOff` · **Category** Governance · **Impact** 1 · **Effort** 2 · **Components** Build & test setup

**Why it matters.** pmdTest is switched off with a note to re-enable it. The module's tests are the only guard on the sandbox and the defaults, and they are not held to the same rules as the main code.

**Option.** Fix the test-source violations and re-enable the task.

**Question to settle.** Is the backlog small enough to clear in one change?

</Accordion>
<Accordion title="UiDesign is raw HTML from plugin code (G22)">
**Id** `uiHtml` · **Category** Security · **Impact** 2 · **Effort** 2 · **Components** Metadata & schema

**Why it matters.** A plugin returns a block of HTML with width and height, which the UI draws. Many plugins repeat nearly identical HTML. A plugin from another team could inject script into the page that shows it. Today all plugins are in the repository, which limits the risk.

**Option.** Replace the HTML with a small data record (colour, icon, label) that the UI renders; or sanitise or sandbox the HTML.

**Question to settle.** Will third parties supply plugins that appear in the same UI as trusted ones?

</Accordion>
<Accordion title="Run budgets are per JVM, in memory, and can overshoot">
**Id** `budgetLedger` · **Category** Governance · **Impact** 3 · **Effort** 3 · **Components** Failure & config helpers, Store SPIs

**Why it matters.** `RunBudgets.shared()` is one static ledger that LLM_CALL and MCP_TOOL_CALL use to stop a run that loops on a model. Four limits follow from its code. (1) The check and the add are separate steps: `exceeded` runs before a call and `add` after it, so calls running at the same time (a node's default concurrency is 256) all pass the check and the run can spend far more than the limit, not just one call more. (2) It keeps the newest 10,000 keys (each agent name is a key of its own), so on a busy server an old but still running run is forgotten and starts again from zero. (3) It is in memory: a resumed run, a restarted server or a new leader starts at zero. (4) It lives in the JVM that runs the plugin, so a node placed on a worker counts against that worker's ledger, not the run's.

**Option.** Reserve before the call (add an estimate, then correct it) so concurrent calls see each other; keep a run's entry until the run ends instead of evicting by count; write the totals to the checkpoint store, or at least log them, so a resume restores them; decide whether budgeted plugins may be placed on workers.

**Question to settle.** Is a budget a hard guarantee or an estimate? Which one does your finance team expect?

</Accordion>
<Accordion title="Approval waits are one static, in-memory, size-capped object">
**Id** `signalWaitsShared` · **Category** Reliability · **Impact** 2 · **Effort** 2 · **Components** Control commands, Command processing

**Why it matters.** `SignalWaits.shared()` serves every plugin and run in the JVM. Waits and early signals live in memory only, so a restart or a leader change loses them (the core guide lists this). The cap of 100 early signals is global: one run that fills it makes an early signal for any other run answer NOT_WAITING for up to ten minutes, which core turns into HTTP 409. The signal payload is read with `String.valueOf`, so a missing executionId, nodeId or name becomes the text 'null' and is matched as a key.

**Option.** Cap early signals per execution as well as in total; reject a payload that lacks the three key fields; list open waits from a store when one exists (core F2).

**Question to settle.** How many approvals can wait at once on your busiest server, and how long?

</Accordion>

<Accordion title="MAPPER SCRIPT: sandboxed, but no heap limit (G1)">
**Id** `scriptHostAccess` · **Category** Security · **Impact** 2 · **Effort** 3 · **Components** Transform & script, Selection & gates

**Why it matters.** Done (PR #373): the GraalJS class lookup accepts only 12 value classes (Math, String, the number and boolean wrappers, UUID, Base64, ArrayList, HashMap, List, Map) and java.time.\*; Class objects are denied, so no reflection; a script is cancelled after 50 million statements or 10 s (`yukta.script.max-statements`, `yukta.script.timeout-ms`). Also done: the script is given plain-data copies of message, payload and metadata (polyglot proxies; other values as text) instead of live Java objects, `HostAccess.ALL` and its 'nosem' comment are gone, a script may be given and return at most 1,000,000 values (64 levels deep), and builds strings of at most 10,000,000 characters (the experimental GraalJS option `js.string-length-limit`, which needs `allowExperimentalOptions`). Still open: (1) there is no heap limit (the Community runtime has no heap option; it needs Oracle GraalVM), so a script can still allocate within its statement budget until the JVM is under pressure; (2) the 'nosem' comment for the class-lookup rule remains; (3) one shared watchdog thread cancels every script.

**Option.** Run scripts on a bounded pool and watch their heap use from the watchdog, or use Oracle GraalVM's heap limit; add a test that fails if the lookup list grows; keep script-js out of builds that do not need it (-Pyukta.plugins).

**Question to settle.** Do you trust every workflow author with the CPU and memory of the server for ten seconds at a time?

</Accordion>
<Accordion title="Host allow-list for HTTP_REQUEST, MCP_TOOL_CALL is opt-in (G7)">
**Id** `ssrf` · **Category** Security · **Impact** 3 · **Effort** 2 · **Components** External I/O, Terminals, Selection & gates

**Why it matters.** HTTP_REQUEST and MCP_TOOL_CALL send to any url in config, and the url can be built from the message ($\{payload.url\}). That reaches the cloud metadata address (169.254.169.254), localhost admin ports and anything on the internal network. NOTIFY_TERMINAL requires https but accepts any host. The MCP session cache is keyed by url and credentials, so many different urls also mean many cached sessions. Update: MCP_TOOL_CALL now has tool-level controls (`allowedTools`, `yukta.mcp-client.allowed-tools`, argument limits and deny patterns, `requireApproval`), but they decide which tool is called, not which host: an empty allow-list still allows any tool and any url.

**Update.** The operator can now list the hosts the server may call (`yukta.http.allowed-hosts` for HTTP_REQUEST, `yukta.mcp-client.allowed-hosts` for MCP_TOOL_CALL and MCP_LIST_TOOLS; names, IP addresses or `*.domain`). A URL on another host, or without a host, is refused before a request is made. It is opt-in: with no list every host is still allowed, so cloud metadata and the internal network stay reachable until the operator sets one. The check is on the name in the URL, so it does not stop a listed name that resolves somewhere unintended, and NOTIFY_TERMINAL webhooks are not covered. Redirects are not followed, so none need checking.

**Option.** Block loopback and link-local addresses by default and check the resolved address after DNS resolution; apply the same list to webhooks.

**Question to settle.** Should the allow-list be per deployment, per session (team), or per workflow? And is a network egress policy outside the application a cleaner place for it?

</Accordion>
<Accordion title="Secrets can still be stored literally in workflow config (G5)">
**Id** `plaintextSecrets` · **Category** Security · **Impact** 3 · **Effort** 3 · **Components** Contract & variables, External I/O, AI processors

**Why it matters.** A default secret provider exists (decrypted:key reads YUKTA_SECRET_&lt;KEY&gt;), but nothing forces its use. apiKey (LLM_CALL, decision plugins, model plane), authToken (MCP), SQL passwords and webhook urls can still be typed into the config, and then sit in the stored definition and its files. Done: the REST config and workflow endpoints and the MCP get_workflow_details tool now mask literal secrets (SECRET-typed fields and keys named like secrets), a definition that holds the mask is refused when saved, and SQL_QUERY now resolves decrypted: and variables in url, username and password. Still open: a literal secret is stored as typed; LlmGateway keeps the key inside its client cache key; other places that show config (for example logs) are not masked.

**Option.** Consider rejecting plain-text values for SECRET fields so a literal cannot be stored at all; keep the key out of the cache key.

**Question to settle.** Is it acceptable for a workflow definition to be a secret-bearing document, or must it be safe to share like source code?

**Id** `shellModel` · **Category** Security · **Impact** 2 · **Effort** 2 · **Components** External I/O

**Why it matters.** Done (PR #373): nothing runs unless `yukta.process.allowed-commands` lists the executable (or `yukta.process.allow-any=true`), and `useShell` is refused while the list is set. <Accordion title="A timeout kills the child but not its children (G9)">
**Id** `orphans` · **Category** Reliability · **Impact** 3 · **Effort** 2 · **Components** External I/O

**Why it matters.** On timeout the plugin now stops the whole tree it started (sh -&gt; mvn -&gt; java): descendants are listed first, asked to end, and killed if still alive after 2 seconds, which also closes the output pipes. <Accordion title="Concurrency per node: only a default and a few plugins have a setting (G8)">
**Id** `fanout256` · **Category** Scalability · **Impact** 3 · **Effort** 2 · **Components** External I/O, AI processors

**Why it matters.** PROCESS_EXECUTOR, HTTP_REQUEST, MCP_TOOL_CALL, LLM_CALL and the decision plugins now take a per-node `concurrency` setting (defaults: 4 for processes, 16 for the others), and SESSION_MEMORY handles one message at a time, so a trigger or splitter that emits 1,000 messages no longer starts hundreds of calls together. <Accordion title="File sandbox protects a path, not an author">
**Id** `fileSandbox` · **Category** Security · **Impact** 3 · **Effort** 2 · **Components** External I/O

**Why it matters.** baseDir is a plain config value, so the author who writes the workflow also chooses the sandbox: baseDir '/' reads anything the server can read. In our view the sandbox therefore only helps when the path comes from the message (untrusted input) and baseDir from a trusted author. Also, the link check and the open are separate steps (the code has a 'ponytail' note), so a link swapped in between is not caught.

<Accordion title="Several caches and maps never evict (G11)">
**Id** `unboundedMaps` · **Category** Scalability · **Impact** 3 · **Effort** 2 · **Components** Transform & script, Routing & EIP, Triggers, AI processors, External I/O, Supervisors & planes

**Why it matters.** MAPPER's template and script caches, the SIMPLE expression cache, LlmGateway's model clients and the MCP session cache are now bounded (least recently used first: 1,000 templates, scripts and expressions, 100 models, 100 MCP sessions; an evicted MCP session is also ended on the server, and anything dropped is rebuilt when next used). <Accordion title="SESSION_MEMORY: durable now; memory cache never evicts and no owner">
**Id** `sessionMemory` · **Category** Reliability · **Impact** 3 · **Effort** 2 · **Components** AI processors

**Why it matters.** Done: the history can be kept in a file per session (`yukta.session-memory.dir`) or in PostgreSQL (`yukta.session-memory.store-type=postgres`, table session_history; `yukta.session-memory.ttl` deletes sessions not written for that long), so a restart no longer erases it. <Accordion title="KV_STORE: PostgreSQL option added; default still memory-only, namespace optional">
**Id** `kvVolatile` · **Category** Reliability · **Impact** 3 · **Effort** 2 · **Components** Flow & state

**Why it matters.** Done: with `yukta.kv.store-type=postgres` the store is the `kv_entry` table (`R2dbcKeyValueStore`), survives a restart, is shared by servers and increments a counter in one statement, behind the new `KeyValueStore` SPI. <Accordion title="Untrusted text goes into model prompts">
**Id** `promptInjection` · **Category** Security · **Impact** 3 · **Effort** 3 · **Components** AI processors, Supervisors & planes

**Why it matters.** Decision plugins send the 'state' (default the whole payload) to the model along with the question, and the model plane sends event details, including log lines if enabled. Text inside that content can say 'ignore the question and answer yes'. A GATE that decides 'safe to send?' or a control plane that decides 'pause?' can then be steered by the very data it judges. Probabilities from a chat model are its own estimate, not a measurement. Update (PR #373): `LlmGateway` can now refuse a prompt or an answer that matches `yukta.llm.deny-input-patterns` or `deny-output-patterns` and cut prompts at `yukta.llm.max-input-chars`; this applies to LLM_CALL and to LLM-backed decisions, and MCP tool calls can require a human approval or an allow-list. **Option.** Treat model verdicts as advice for low-risk routing; keep rules and deny rules authoritative for anything harmful; keep untrusted fields out of 'state' or mark them as data; prefer System One's calibrated probabilities where it is available.

**Question to settle.** Which decisions in your workflows would be harmful if an attacker could choose the answer?

<Accordion title="Open on loopback; docs outside the key; the start-up guard accepts the MCP key alone">
**Id** `openByDefault` · **Category** Security · **Impact** 3 · **Effort** 2 · **Components** Settings & exposure, Filter chain

**Why it matters.** Done (PR #373): `ExposureGuard` (boot) refuses to start on a non-loopback address without a key; the actuator (except health) needs an ADMIN key; without a key `HostOriginFilter` answers 403 to a Host that is not loopback and to a cross-origin write, which stops DNS rebinding and cross-site requests from a browser. Still open: (1) the guard counts `yukta.mcp.api-key` as a key, so a non-loopback server with only the MCP key set starts and leaves /api and the actuator open (see boot `guardMcpKeyOnly`); (2) the key filter guards only /api and /actuator, so the Swagger UI and the OpenAPI document stay open; (3) on loopback with no key, any local process or user can call the API, because the Host/Origin checks only stop browsers.

**Option.** Make the guard check the same keys the REST filter uses; guard or switch off the docs in prod; consider generating a key at first start.

**Question to settle.** Should the server refuse to listen on a non-loopback address without a key, even if that breaks a quick demo?

<Accordion title="The bundled UI cannot send the API key">
**Id** `uiNoKey` · **Category** Functionality · **Impact** 3 · **Effort** 2 · **Components** Filter chain, Settings & exposure

**Why it matters.** The UI's API client sets only Content-Type; it has no way to add Authorization or X-API-Key. With a key configured, its calls would be 401 unless a proxy adds the header. So the safe configuration is awkward for the main client, which pushes operators towards leaving the key off. The CLI can send a bearer token. Update: the new Host/Origin protection works only while no key is set, so with the UI the choices are still 'no key, loopback only' or a proxy that adds the header.

**Option.** Add key (or login) support to the UI; or serve the UI and API behind a reverse proxy that injects the header; or have the server serve the UI with its own session cookie.

**Question to settle.** What should authentication look like for a browser user: a pasted key, a login, or a gateway in front?

</Accordion>
<Accordion title="Ownership: limited keys are enforced by the filter; controller checks stay uneven">
**Id** `ownershipGap` · **Category** Security · **Impact** 2 · **Effort** 2 · **Components** Ownership check, Run control API, Run lifecycle API, Streams (SSE), Catalogue & control bus

**Why it matters.** Done: a key can be limited to sessions (`yukta.api-keys[].sessions`). The key filter checks the session of /api/sessions/\{s\}/\*\* and /api/workflow/\{s\}/\*\*, finds the session of /api/executions/\{id\}/\*\* from the tracker, and refuses the events stream, the run search and the control audit to a limited key. Still open: (1) the controllers' own checks are still uneven (canonical routes check existence only), which matters for any key without session limits; (2) the filter finds an execution's session only through the live tracker, so once a run has left it (restart, eviction) even its own limited key gets 403; (3) the legacy aliases are still the only routes that check inside the controller.

**Option.** Resolve the session from the execution store as well as the tracker; move the check into one place; then retire the aliases.

**Question to settle.** Is a session meant to be a security boundary (tenant) or only a convenience grouping?

</Accordion>
<Accordion title="Node config returned as stored, including literal secrets">
**Id** `configUnredacted` · **Category** Security · **Impact** 3 · **Effort** 3 · **Components** Session & config API

**Why it matters.** GET /api/sessions/\{sid\}/config and /workflows/\{wid\} return node config unchanged. Core supports secret references (the decrypted: prefix, secrets from YUKTA_SECRET_ environment variables), so a careful author keeps tokens out of the definition. Nothing stops someone writing a literal API token into an HTTP node's headers. Then any reader of the API, and anything that logs responses, sees it. This is our judgement of a design weakness, not a confirmed leak.

**Option.** Mask values of keys that look secret (the way core already blocks env names containing KEY or TOKEN) in read APIs; warn on save when a config contains a likely literal secret; document that secrets must be references.

**Question to settle.** Should the read API ever return a secret-looking value, or should editors work with masked values and send them back unchanged?

</Accordion>
<Accordion title="Paging slices a full list and finds the cursor by linear search">
**Id** `pagingLinear` · **Category** Performance · **Impact** 3 · **Effort** 3 · **Components** Run lifecycle API, Session & config API

**Why it matters.** History pages load the entire history from core and then walk it to find the cursor. Listing sessions loads and sorts every id for each page. Cost per page grows with the total, so reading a long history in pages of 100 costs roughly n pages times n items. An unknown cursor (for example the run was trimmed from history) silently restarts from the first item, so a client looping until there is no next cursor can see page 1 again, which looks like an endless loop.

**Option.** Push the cursor into core and the stores (seek by id), keep the id-based cursor; return 400 or 410 for an unknown cursor instead of restarting; cap per-call work.

**Question to settle.** How long can a session's history realistically become, and does anyone page through all of it?

</Accordion>
<Accordion title="Event and log streams drop events for slow readers">
**Id** `slowReader` · **Category** Reliability · **Impact** 3 · **Effort** 3 · **Components** Streams (SSE)

**Why it matters.** The live parts use best-effort multicast feeds: if a reader does not keep up, events are dropped for that reader instead of slowing the engine. That protects the engine but means a UI can silently miss a status change or a log line. The events stream has no replay at all, and it ignores Last-Event-ID, so a reconnect cannot recover what was missed. A UI that treats the stream as complete can show a stale state.

**Option.** Tell the client when it missed events (a gap marker or a lag counter) so it can refetch; add replay by sequence number for the events stream; document that streams are hints and status endpoints are the truth.

**Question to settle.** Is a missed event acceptable for the UI (it can refetch) but not for programmatic clients like the CLI or scripts?

</Accordion>
<Accordion title="Log stream joins history and live by text and timestamp; ids are positions">
**Id** `logSeam` · **Category** Correctness · **Impact** 2 · **Effort** 3 · **Components** Streams (SSE)

**Why it matters.** The seam between stored lines and live lines is closed by a heuristic: match by message text and a timestamp not after the snapshot, drop once. Two genuinely different lines with identical text in the seam window can lose one. The live buffer holds 1024 lines; a burst larger than that during the history read is lost. Event ids are positions in a stream that is rebuilt on every connect, so resuming with Last-Event-ID is exact only if history was not changed or trimmed meanwhile (for example by log retention).

**Option.** Give every log line a durable sequence number in the log store and use it as the SSE id; join history and live on that number instead of text.

**Question to settle.** How much does a perfectly exact log stream matter, compared with the cost of changing the log store?

</Accordion>
<Accordion title="Deprecated /api/workflow/... aliases still in use">
**Id** `legacyAliases` · **Category** Evolvability · **Impact** 2 · **Effort** 2 · **Components** Run lifecycle API, Run control API, Ownership check

**Why it matters.** 14 routes are aliases of canonical /api/executions/... routes. The CLI calls almost all of them and the UI still calls the two status aliases. Two route families mean double the tests and docs, and clients that never move. The aliases are also the only ones that check session ownership, so removing them without fixing the check lowers protection.

**Option.** Move the CLI and UI to the canonical routes, fix the ownership check on them, announce a removal date and log alias use to see who remains.

**Question to settle.** When can we retire the aliases, and who owns migrating the CLI?

</Accordion>
<Accordion title="Three places catch errors themselves">
**Id** `localCatch` · **Category** Operability · **Impact** 2 · **Effort** 1 · **Components** Session & config API, Catalogue & control bus, Errors & envelope

**Why it matters.** The rule is that controllers never catch errors, so one handler decides what clients see. Three places break it. The validate endpoint turns every error into valid:false plus e.getMessage(), so an unexpected failure shows exception text in a 200. The plugin list turns a failure into a 500 whose message includes the exception text, which the central handler would have hidden. The session summaries endpoint logs and skips a session it cannot read, so a corrupt session simply vanishes from the table with a 200.

**Option.** Let unexpected errors reach the central handler (catch only the validator's own validation exception); for summaries, return a marker row or a count of skipped sessions.

**Question to settle.** Is hiding an unreadable session from a table ever the right behaviour, or should it show as broken?

</Accordion>
<Accordion title="No 409: state conflicts become 500">
**Id** `noConflict` · **Category** Correctness · **Impact** 2 · **Effort** 2 · **Components** Errors & envelope, Run lifecycle API, Run control API

**Why it matters.** Partly done: a `ConflictException` now maps to 409 and the recover endpoint uses it. The restart race is not converted: core's `RestartCommandProcessor` still throws `IllegalStateException('Restart already in progress...')`, and the handler maps that type to 500 with no message. Monitoring that counts 5xx will flag it as an incident, and any new core failure type is a 500 until someone adds a handler.

**Option.** Throw ConflictException for the restart race and review the other IllegalStateException uses that are client conflicts.

**Question to settle.** Which core failures are client-correctable, and should the web layer classify them or core?

</Accordion>
<Accordion title="Execution limits can be changed or removed by anyone, unvalidated">
**Id** `limitsEndpoint` · **Category** Governance · **Impact** 2 · **Effort** 1 · **Components** Run control API

**Why it matters.** Done: the endpoint needs an ADMIN key, the change goes through the reviewers and is audited with the actor, and it is restored from the log at startup. Still open: the controller takes two integers with no range check, and a negative value is treated as 0 and 0 means no limit, so one call can still remove the caps that protect the server. It changes the two global limits, not per-session ones.

**Option.** Reject negative values and require an explicit flag (or a configured ceiling) for 0.

**Question to settle.** Should a runtime call be allowed to raise a limit above what the operator configured at startup?

</Accordion>
<Accordion title="Rejected requests (400, 401, 403) leave no trace">
**Id** `silent401` · **Category** Operability · **Impact** 2 · **Effort** 1 · **Components** Filter chain

**Why it matters.** The key filter runs before the request-id and access-log filters and ends the exchange itself. A 401 therefore has no X-Request-ID and no access-log line. A brute-force attempt or a mis-set client key is invisible in the log, and a caller cannot quote an id when reporting the problem. Update: the same filter now also ends requests with 400 (ambiguous path) and 403 (role, session, host or origin), and none of them is logged or counted either.

**Option.** Log (and count) rejections in the key filter with the source address and path; generate the request id before the key check.

**Question to settle.** Do we want failed-auth attempts counted and alertable, and by what source identifier?

</Accordion>
<Accordion title="No rate limit, stream cap or body-size setting in this module">
**Id** `noLimits` · **Category** Availability · **Impact** 3 · **Effort** 3 · **Components** Filter chain, Streams (SSE), Binding & mapping

**Why it matters.** Done: request bodies above `spring.codec.max-in-memory-size` (1 MiB, `YUKTA_LIMITS_MAX_BODY`) get 413. Still open: nothing limits how fast a client can call or how many streams it opens. Each log stream keeps a subscription and up to 1024 buffered lines; each events stream stays open indefinitely. A client (or a UI tab that reconnects in a loop) can consume memory and connections. Start and control endpoints can be hammered, though core's execution limits cap actual runs.

**Option.** Per-client rate limits at a gateway or a filter, a cap on concurrent streams per key, and a maximum stream lifetime.

**Question to settle.** Do we run behind a gateway that already provides limits, or must the server protect itself?

</Accordion>
<Accordion title="Two mappers disagree on the default edge port">
**Id** `mapperDrift` · **Category** Correctness · **Impact** 2 · **Effort** 2 · **Components** Binding & mapping, Session & config API

**Why it matters.** SessionMapper (used when saving a session) turns a missing edge sourcePort into 'default'. AppConfigMapper (used by the dry-run validator) leaves it null. A draft can therefore be validated with a null port and saved with 'default'. If core treats these differently, a draft that validates could behave differently after saving. We did not confirm that core treats them differently, so this is a drift risk, not a known bug.

**Option.** Use one mapper for request-to-definition conversion (or share the edge conversion) and cover it with a test that saves and validates the same payload.

**Question to settle.** Does core treat a null source port and 'default' as the same thing everywhere?

</Accordion>
<Accordion title="Eleven response records in web are not used by web">
**Id** `deadDtos` · **Category** Evolvability · **Impact** 1 · **Effort** 1 · **Components** Binding & mapping

**Why it matters.** ControlBusStatus, SystemHealthMetrics, ErrorExample, SessionCreationGuide, PluginCreationGuide, SessionInfo, ExecutionRecord, SessionExecutionInfo, PluginRegistryEntry, PluginReference and SessionCreationResponse have tests but no use in web's main code; the mcp module has its own copies of most. They make the module look like it offers things it does not, and two copies can drift.

**Option.** Delete the unused records and their tests, or move the shared ones to one module both use.

**Question to settle.** Are any of these part of a public contract (for example a client library) that makes deleting them a breaking change?

</Accordion>
<Accordion title="Keys are static configuration: no expiry, no revocation, coarse roles">
**Id** `staticKeys` · **Category** Security · **Impact** 2 · **Effort** 3 · **Components** Filter chain

**Why it matters.** The first guide's biggest risk (one shared key for everything) is closed: keys have names, roles (VIEWER, OPERATOR, ADMIN), optional session limits, a `sha256:` form and several can be active for rotation. What remains: (1) a key has no expiry and cannot be revoked without changing configuration and restarting; (2) roles are matched by method and path prefix, so an OPERATOR can POST anything under /api/workflow/ and /api/executions/ (including starts and raw control); (3) only control commands carry the actor, so reads and starts are not attributed anywhere; (4) there are no per-key rate limits.

**Option.** Keys from a store that can be changed at run time, an expiry date per key, the key name in the access log, and a per-key rate limit; delegate to an identity provider when users, not services, call the API.

**Question to settle.** How quickly must you be able to cut off one leaked key, and can you do that today without a restart?

</Accordion>
<Accordion title="Run search scans every session's history on each call">
**Id** `searchScan` · **Category** Performance · **Impact** 2 · **Effort** 3 · **Components** Run lifecycle API

**Why it matters.** `GET /api/executions` (ExecutionSearchController) loads the history of every session (or of one), filters it in memory, sorts all hits and then takes `limit`. The cost per call grows with sessions times retained runs (`yukta.execution-log.retained-runs`, default 500 per session), and nothing caps it. The same full-load pattern as the history paging, now across sessions.

**Option.** Push the filters and the limit into the execution log store (a query by time, status and workflow), or keep a small index of recent runs.

**Question to settle.** How many sessions and retained runs do you expect, and how often will a dashboard poll this?

<Accordion title="A control plane that lost the lease keeps its workers">
**Id** `deposedKeepsWorkers` · **Category** Availability · **Impact** 3 · **Effort** 2 · **Components** Registration & leases, Failover & drain, Tests

**Why it matters.** The leader check runs only when a worker registers. `WorkerSessionHandler.answer` replies `ACK` to every `LEASE` if the registry knows the worker, without asking whether this server is still the leader. If the leader loses the database lease but keeps running (a network split to the database, a long pause), its worker connections stay open and keep being renewed, while the new leader has no workers. Placed nodes on the new leader fail with 'No connected worker' until the old process stops. A crash of the old leader is handled (the connections close); this case is not, and no test covers it.

**Option.** Answer a LEASE with `REJECT 'not the leader'` when `election.isLeader()` is false, so the agent reconnects to the next address; and close the connections when leadership is lost.

**Question to settle.** What do your workers do when the leader is alive but cannot reach the database?

</Accordion>
<Accordion title="Plain TCP is the default, and the wire carries tokens, configs and payloads">
**Id** `plainTokenDefault` · **Category** Security · **Impact** 4 · **Effort** 2 · **Components** Transport & TLS, Control-plane executor

**Why it matters.** Without `yukta.workers.ssl-bundle` (worker) and an SSL bundle on the RSocket server (control plane) the connection is plain TCP. The shared token travels in the REGISTER frame, `START` carries the node config as written (including any literal API key, password or webhook url in it), and every input and output message is sent as JSON. Anyone on the path can read them, and can also play the control plane to a worker and send it START frames for the plugin types it runs. Mutual TLS is built and tested, but nothing requires it, even for a non-loopback address.

**Option.** Refuse a non-loopback worker connection without TLS unless an explicit 'insecure' flag is set; document the two SSL bundles in the setup text; keep secrets out of placed nodes' configs.

**Question to settle.** Would you accept your LLM API key crossing this link in clear text?

</Accordion>
<Accordion title="One shared token, and workers choose their own identity">
**Id** `sharedTokenIdentity` · **Category** Security · **Impact** 3 · **Effort** 3 · **Components** Registration & leases

**Why it matters.** Every worker uses the same token, and the worker id, pools and plugin types are whatever the REGISTER frame says. Anyone with the token can register as any id: `registry.register` replaces an existing entry and the connection map is overwritten, so the new connection receives that worker's jobs. A token cannot be revoked for one worker, and rotating it means restarting the control plane and every worker. Two live workers with the same id also renew the same registry entry.

**Option.** A token or certificate per worker, mapped to the ids and pools it may use; refuse a second registration for an id that is still alive.

**Question to settle.** How do you remove one compromised worker without touching the others?

</Accordion>
<Accordion title="Slot accounting is not atomic and the worker enforces no limit">
**Id** `capacityRace` · **Category** Correctness · **Impact** 2 · **Effort** 2 · **Components** Placement & selection, Node runner

**Why it matters.** `pick` reads free slots and the caller increments the in-flight counter afterwards, in a separate step, so two attempts chosen at the same moment can both take the last slot. The worker's `NodeRunner` starts every attempt it receives, so the worker runs more than its capacity. The control plane also counts only its own sends; a second control plane (a standby that takes over) starts from the lease's used-slot value, which is up to 5 s old.

**Option.** Reserve the slot inside the pick (compare-and-set on the counter) and have the runner refuse an attempt beyond its capacity with a retryable error.

**Question to settle.** What happens to a worker with capacity 4 that gets 12 attempts at once?

</Accordion>
<Accordion title="Placed nodes lose their live log stream">
**Id** `liveLogsLost` · **Category** Operability · **Impact** 3 · **Effort** 2 · **Components** Node runner

**Why it matters.** The control plane puts a log sink into the Reactor context of a local node so that a plugin can write log lines while it runs (PROCESS_EXECUTOR streams every output line this way). `NodeRunner` puts only the execution id, node id and the heartbeat into the context, so on a worker the sink is absent and the plugin uses its no-op default. A placed PROCESS_EXECUTOR node shows its output only in the final result message, not live in the log feed, `logs` and `controlbus watch`. The worker's own application log has the lines, on the worker.

**Option.** Add a LOG frame (or reuse MESSAGE) from worker to control plane and give the runner a sink that sends it; or document the limit.

**Question to settle.** Does anyone watch a placed build step live?

</Accordion>
<Accordion title="START carries no trace context, deadlines or attempt number">
**Id** `noTraceContext` · **Category** Operability · **Impact** 2 · **Effort** 3 · **Components** Control-plane executor, Wire frames

**Why it matters.** The design lists trace context, an attempt number and deadlines in `START`. The implemented START has only execution id, node id, plugin type and config. A worker's spans therefore do not join the run's `yukta.run` trace, the node's deadline is enforced only on the control plane (which cancels the channel), and the plugin's meters (for example token counters) are recorded in the worker's own registry and need their own scraping.

**Option.** Add the trace headers to START and open the worker-side observation as a child; document that plugin meters must be collected from workers.

**Question to settle.** Where would you look for the cost of a placed LLM_CALL node?

</Accordion>
<Accordion title="The reconnect pause is not reset after a healthy connection">
**Id** `reconnectBackoff` · **Category** Availability · **Impact** 2 · **Effort** 1 · **Components** Worker agent, Failover & drain

**Why it matters.** The agent retries with `Retry.backoff(Long.MAX_VALUE, 1 s).maxBackoff(30 s)` on a Mono that only ever ends in an error. Without `transientErrors(true)` Reactor counts every failure of the process, not failures in a row, so after a few reconnects each new pause is already near 30 s (with jitter). A failover then costs a worker up to about 45 s of idle time on top of the lease, for as long as the process lives. This follows from Reactor's rules and is not measured here; the failover test covers a first failover only.

**Option.** Add `transientErrors(true)` and reset on a successful REGISTER; log the pause.

**Question to settle.** How long can a worker sit idle after the fifth control-plane restart?

</Accordion>
<Accordion title="Errors lose their class on the way back, so a hard stop becomes a normal failure">
**Id** `abortLostAcrossWire` · **Category** Correctness · **Impact** 3 · **Effort** 1 · **Components** Control-plane executor

**Why it matters.** An `ERROR` frame carries the class name and message. The executor rebuilds only `IllegalArgumentException`; every other class becomes a `WorkflowExecutionException` with the class in its text and no cause. The engine decides retry, drop and dead-letter by exception class and cause, and treats `RunAbortedException` (an LLM or MCP budget with `hardStop`) as an order to end the run. On a worker that exception arrives as a plain failure, so the budget stop can be retried or routed to a dead letter instead of ending the run, and `retryOn` / `noRetryOn` lists naming an original class do not match.

**Option.** Map known classes back (at least RunAbortedException) and put the class chain in the error frame so the engine can match it; test a hardStop budget on a placed node.

**Question to settle.** Does a budget stop mean the same thing on a worker as on the control plane?

</Accordion>
<Accordion title="Messages cross as plain JSON with no size limit">
**Id** `payloadAsJson` · **Category** Scalability · **Impact** 3 · **Effort** 4 · **Components** Control-plane executor, Transport & TLS, Wire frames

**Why it matters.** Each message is converted to a JSON map with the application's `ObjectMapper` and back to `DefaultMessage`. Java types in the payload and in headers (dates, byte arrays, POJOs) come back as maps, lists, numbers and text. The module sets no frame or message size limit, and there is no reference for large bodies (the design leaves the payload limit as an open decision), so a large file or a long model output goes through the control plane as one frame. The boot mapper rejects unknown properties, so a field added to the message on one side and not the other fails to convert.

**Option.** Decide a payload limit and a claim-check reference above it; test a 50 MiB message and a header holding a date.

**Question to settle.** What is the largest message a placed node will see?

</Accordion>
<Accordion title="The wire protocol has no version and is not tested across builds">
**Id** `wireVersion` · **Category** Evolvability · **Impact** 3 · **Effort** 3 · **Components** Wire frames, Tests

**Why it matters.** `WorkerFrame` and `NodeFrame` are the whole protocol and neither carries a version. A control plane and a worker built from different commits must agree on the record components and on `DefaultMessage`; a mismatch shows up as a conversion error or a field silently ignored, depending on the mapper settings. Rolling upgrades of a pool, which are the normal case, have no rule and no test.

**Option.** Send a protocol version in REGISTER and refuse an incompatible worker with a clear reason; add a test that pairs the previous release's frames with the current handler.

**Question to settle.** Can you upgrade the control plane before the workers?

</Accordion>
<Accordion title="The 'local only' list is a fixed set of four types">
**Id** `statefulPlacement` · **Category** Correctness · **Impact** 2 · **Effort** 2 · **Components** Placement & selection

**Why it matters.** `RemoteNodes` refuses SESSION_MEMORY, KV_STORE, WAIT_FOR_SIGNAL and SUB_WORKFLOW. Other plugins that keep state in memory per node or per process are allowed: the ANOMALY and DEDUPE windows, AGGREGATE's partial batch, the MCP session cache. On a worker that state lives in whichever worker ran the attempt, and with per-message policies each message is its own attempt, so windows and batches see partial data and a retry on another worker starts empty. A new stateful plugin is placeable until someone adds it to the list.

**Option.** Make 'local only' a flag on the plugin (as the design says) instead of a list in core, and mark the window-based plugins.

**Question to settle.** Which of your plugins keep anything between messages?

</Accordion>
<Accordion title="A connection that ended with a REJECT is not closed by the agent">
**Id** `staleConnections` · **Category** Reliability · **Impact** 2 · **Effort** 2 · **Components** Worker agent

**Why it matters.** On a REJECT the agent throws, and the retry calls `connect` again for a new connection; only the latest requester is stored in `current`, and only that one is disposed at stop. The control plane ends the response stream but nothing closes the underlying RSocket connection, so each rejection ('lease expired, register again', or 'not the leader' from a standby) can leave a connection open on both sides until a process ends. This looks like a leak from reading the code; it was not observed.

**Option.** Dispose the previous requester before reconnecting and when the session stream ends; add a test that counts open connections after repeated rejections.

</Accordion>
<Accordion title="Initialise and prepare run for every attempt on the shared plugin instance">
**Id** `perAttemptInit` · **Category** Correctness · **Impact** 2 · **Effort** 3 · **Components** Node runner

**Why it matters.** For each attempt the runner calls the plugin's `initialize(config)` and `prepare(config)`; with per-message policies that is once per message. Plugins are one shared object per type on the worker, so a plugin that stores config in a field (see the plugin-api risk about shared instances) mixes up settings between two placed nodes on the same worker. `shutdown` is never called on a worker either.

**Option.** Pass the config into each call instead of keeping it in fields, and prepare once per node and config; call shutdown at worker stop.

</Accordion>
<Accordion title="Run budgets and provider rate limits are counted per worker">
**Id** `budgetPerJvm` · **Category** Governance · **Impact** 3 · **Effort** 3 · **Components** Node runner

**Why it matters.** The shared run-budget ledger (`RunBudgets.shared()`) and the provider rate limiter in `LlmGateway` are static, in-memory objects of the JVM in which the plugin runs. A placed LLM_CALL or MCP_TOOL_CALL node therefore counts tokens, cost, calls and requests per minute in the worker, keyed by execution id, and each worker has its own totals. A run spread over three workers can spend three times its budget, and a provider limit of 60 requests per minute becomes 60 per worker.

**Option.** Count budgets and limits on the control plane (reserve before sending START, settle with the result), or keep them out of placeable plugins.

**Question to settle.** Who enforces the budget when two workers serve one run?

</Accordion>
<Accordion title="The native worker is not verified, and the role is fixed at build time">
**Id** `nativeUnverified` · **Category** Operability · **Impact** 3 · **Effort** 3 · **Components** Roles & auto-configuration, Native image

**Why it matters.** The module's own notes say both native roles build and start, that a native control plane reports no workers, and that a native worker did not register because the frame records had no reflection hints. The hints (`@RegisterReflectionForBinding`) have been added but not checked in a native image because the rebuild ran out of memory. Spring decides property-conditioned beans at image build time, so a native image built without the role switch starts but never takes workers, and one image cannot be both roles.

**Option.** Run a native registration test in CI on a machine with enough memory; fail the build or start when the role switch is missing.

**Question to settle.** Do you need native workers, or is a JVM worker enough for now?

</Accordion>
