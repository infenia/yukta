## Goal

A person can install and run Yukta without installing a JDK or building anything:

1. **Docker:** `docker run` works on `linux/amd64` and `linux/arm64` from one image tag.
2. **Installable binaries:** native server and CLI for Linux (amd64, arm64), macOS (arm64, and amd64 if wanted) and Windows (amd64), with checksums and signatures, installable by package manager or one command.
3. **Docs:** the quickstart and deployment pages lead with those, and "run from source with a JDK" becomes the last option.

Non-goals for the first release: Windows on ARM, FreeBSD, a Kubernetes chart, an apt/yum repository, auto-update.

## Where we are

| Area | Today |
|---|---|
| Server | `./gradlew :boot:nativeCompile` produces one GraalVM native binary named `yukta`. The build asks the native-image builder for `-J-Xmx16g`. The UI is built with Node and pnpm inside the same Gradle build |
| CLI | Go, `make build-all` already cross-compiles `linux/amd64`, `linux/arm64`, `darwin/amd64`, `darwin/arm64`, `windows/amd64` (static, `CGO_ENABLED=0`). Its binary is also named `yukta` |
| Docker | One `Dockerfile`: native compile inside the build, optional UPX, distroless `cc-debian12:nonroot` runtime. It builds for the host architecture only and is built locally, not in CI |
| Release workflow | `release.yml` on a `v*` tag builds only the CLI binaries, writes `SHA256SUMS`, attests provenance and creates the GitHub release. `workflow_dispatch` is a dry run. Its `IMAGE` variable is unused |
| Version | `0.0.1-SNAPSHOT` in `gradle.properties`; `ui/package.json` must match (checked in the build). No tags exist |
| Distribution | Nothing is published. README, Quickstart and Deployment all say to run from source with JDK 25 |

## Facts that shape the plan

1. **GraalVM native-image cannot cross-compile.** A Linux amd64 machine can build only Linux amd64 native binaries. Linux arm64, macOS and Windows binaries each need a host of that OS and architecture (or an emulated one).
2. **The native build is heavy.** The builder is given 16 GB of heap. A 32 GB Ryzen machine is comfortable; a 16 GB machine is marginal; a 7 GB machine will not do. Peak memory and time have never been measured here (this planning environment has no GraalVM, 4 cores and 15 GB), so Phase 0 measures them.
3. **The CLI is free.** Go cross-compiles all five CLI targets from any Linux machine in under a minute.
4. **Server and CLI share the name `yukta`.** They cannot sit in the same install directory. See the naming decision below.
5. **Multi-architecture Docker needs one binary per architecture**, so the arm64 image needs an arm64 native server binary.
6. **macOS signing and notarization need macOS and an Apple Developer ID.** Windows signing needs a code-signing certificate. Without them, binaries run but users see Gatekeeper or SmartScreen warnings.

## Build strategy: build anywhere, publish from one place

The central question is whether GitHub-hosted runners are reliable enough. The repository is public, so hosted runners cost nothing, but a native build that needs about 16 GB can fail for reasons that have nothing to do with the code: out-of-memory kills, runner image changes, network blips while Gradle and pnpm download. So the plan does not make the release depend on one place.

**Principle:** every artifact is produced by a script in `release/` that behaves the same on any machine. CI and your release machine both call those scripts. The release is then **assembled, signed and published from the release machine**, from artifacts that were built either locally or by CI. If a runner fails, you rebuild that one artifact elsewhere and carry on.

### Who builds what

| Artifact | Built on | Why |
|---|---|---|
| Server `linux/amd64` | **Release machine** (Ryzen, 32 GB) | Native host, enough memory, fastest iteration |
| Docker image `linux/amd64` | **Release machine** | Wraps the binary above |
| CLI, all 5 platforms | **Release machine** | Cross-compiles, trivial |
| `.deb`, `.rpm`, `.tar.gz`, checksums, SBOM, signatures | **Release machine** | Pure packaging from Linux. Signing keys stay on your machine, not on GitHub |
| Server `linux/arm64` + Docker `linux/arm64` | **arm64 host**, see options | Needs native arm64 |
| Server `windows/amd64` | **Windows host** | Needs native Windows and the MSVC toolchain |
| Server `macos/arm64` (and `macos/amd64`) | **macOS host** | Needs macOS |

### Options for the hosts the release machine cannot be

| Option | Pros | Cons |
|---|---|---|
| **A. GitHub-hosted runners** (`ubuntu-24.04-arm`, `windows-latest`, `macos-latest`) | Free for public repos, nothing to maintain, clean machine every run | Memory is the risk, especially macOS (about 7 GB on the standard hosted runner, to be confirmed). Needs a lower builder heap or a larger paid runner. Occasional infrastructure failures |
| **B. Self-hosted runners** you control | Predictable memory and cache | You run and secure them. A self-hosted runner on a public repo must be restricted to release tags only |
| **C. QEMU emulation of arm64 on the release machine** | No extra hardware | Native-image under emulation is very slow and often fails. Fine for *running* an arm64 image in a smoke test, not for compiling |
| **D. Bundled runtime instead of a native binary** (`jlink` runtime plus the Spring Boot jar) | Buildable for every OS from one Linux machine; no GraalVM; no JDK needed by the user | Larger download (roughly tens of MB more), slower start, no native-image behaviour, extra work to keep module lists right |

**Recommendation:** use the release machine for everything it can build natively (A is used only for what it cannot), prove in Phase 0 whether hosted runners can finish the native build, and keep **D as the escape hatch** for a platform whose native build is too flaky to ship. Because publishing is separate from building, a failed runner delays one artifact and never blocks or corrupts the release.

**Decision 1:** what do you have for arm64 and macOS? An Apple Silicon Mac, a spare arm64 box, or only hosted runners? This changes whether option A, B or D is used for those targets.

| Artifact | Platforms | Contents |
|---|---|---|

| `yukta-<ver>-darwin-arm64.tar.gz` (+ `amd64` if wanted) | macOS | same |

| `yukta_<ver>_amd64.deb`, `_arm64.deb`, `.rpm` x2 | Debian, Ubuntu, Fedora, RHEL | Binaries in `/usr/bin`, a `systemd` unit, a `yukta` system user, `/etc/yukta/yukta.env`. Built with `nfpm` from Linux. The service listens on loopback and starts disabled |
| `ghcr.io/infenia/yukta:<tag>` | `linux/amd64`, `linux/arm64` | One multi-architecture manifest |
| Homebrew formula, Scoop manifest, winget manifest | macOS/Linux, Windows | Point at the archives above and their checksums |
| `install.sh`, `install.ps1` | Unix, Windows | Download the right archive, verify its checksum, install. Hosted at the docs domain |
| `SHA256SUMS`, `*.sig` or `*.bundle`, SBOM (CycloneDX) | all | Verification material |

**Decision 3:** native `.pkg` (macOS) and `.msi` (Windows) installers are **deferred** in this plan. They need a Mac, a Windows host, an Apple Developer account and a signing certificate. Archives plus Homebrew, Scoop and winget cover most users without them. Confirm, or ask for them in v0.1.0.

**Decision 4:** are macOS and Windows required for v0.1.0, or does v0.1.0 ship Linux and Docker first and add the other two when their builds are proven? Splitting the release this way is the lowest-risk path.

## Docker plan

Changes to `Dockerfile`:

1. **Split building from packaging.** Keep today's full build as a dev target, and add a **runtime target** that only copies a prebuilt binary chosen by `TARGETARCH` (`dist/linux-amd64/yukta-server` or `dist/linux-arm64/yukta-server`) into the distroless image. The image and the downloadable archive then contain the *same* binary, built once.
2. **Multi-arch assembly.** Build or load each architecture's image, push them by digest, then create the manifest with `docker buildx imagetools create`. Either architecture can come from a different machine.
3. **Tags.** `X.Y.Z`, `X.Y`, and `latest` only for stable releases; `X.Y.Z-rc.N` for prereleases, which never move `latest`.
4. **Metadata and supply chain.** OCI labels (source, version, licence, revision), an SBOM and provenance attached to the image, `cosign` signature, and a Trivy scan that fails the release on unignored high findings (the repo already has `.trivyignore`).
5. **Smoke test per architecture** before the manifest is published: start the container with an API key, wait for `/actuator/health`, run the quickstart workflow. The arm64 smoke test can run under QEMU on the release machine, because it runs rather than compiles.
6. **UPX:** the current build tries to compress the binary with UPX. For releases, drop it unless Phase 0 shows a clear benefit; compressed binaries start slower, can trip antivirus scanners, and add a failure mode on arm64.
7. **Registries.** GHCR is already implied by `release.yml`.

**Decision 5:** also publish to Docker Hub? It is where most people look first, but needs an account, a namespace and rate-limit-friendly pulls. Recommended: GHCR first, mirror to Docker Hub once the release flow is stable.

## Release flow

Run on the release machine as `release/release.sh vX.Y.Z` (and a `--dry-run` that publishes nothing):

1. **Preflight:** clean tree on `main`, version in `gradle.properties` and `ui/package.json` match the tag, CI green on that commit, tag format valid. Prereleases use `-rc.N`.
2. **Quality gate:** the existing `./gradlew check` (or the staged `yukta-check.sh`) passes.
3. **Build locally:** server linux/amd64, CLI x5, packages, image amd64.
4. **Collect remote builds:** trigger the CI jobs for arm64, Windows and macOS (or build on your own hosts) and download their artifacts. Each job uploads checksums.
5. **Verify:** checksums match, each native binary passes `--version`, and a smoke test starts it and runs a workflow on its own OS and architecture (hosted runners run these tests).
6. **Sign and attest:** `cosign`/GPG signatures and SBOM from the release machine. Build provenance attestation is only available for artifacts built in GitHub Actions, so locally built artifacts carry your signature instead, and the docs say which is which.
7. **Publish as a draft:** upload to a draft GitHub release, push image digests, create the manifest, update the Homebrew and Scoop repositories.
8. **Promote:** after a final install test from the *published* artifacts on a clean machine or container, publish the release, then move tags and `latest`.
9. **Rollback:** a draft can be deleted; a published image tag is never overwritten, so a bad release is superseded by the next patch and the release notes say so.

CI keeps `release.yml` for the parts that run well there (CLI, the arm64, Windows and macOS builds, provenance) and gains `workflow_dispatch` inputs so a single platform can be rebuilt without redoing the rest.

## Risks

| Risk | Mitigation |
|---|---|
| Native build runs out of memory on hosted runners | Phase 0 measurement, configurable heap, or build that target on a bigger host; fall back to the `jlink` bundle |
| Windows or macOS native builds fail for reasons in the code (paths, UI build) | Spike in Phase 0 before promising them; ship Linux and Docker first |
| Unsigned macOS and Windows binaries trigger warnings | Document the warnings and the checksum check; add signing when certificates exist |
| Locally built artifacts have no GitHub provenance | Sign with your own key and say so in the docs; use GitHub-built artifacts where provenance matters |
| A secret or signing key leaks via a public repo's CI | Keys stay on the release machine; self-hosted runners only for tags |
| Name clash between server and CLI | Decision 2 |
| One bad image tag overwritten | Tags are immutable by policy; digests pinned in the manifest step |
