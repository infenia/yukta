## The goal in one paragraph

Yukta becomes a freemium product with three tiers. **Community** (Apache-2.0) is what you can run today, minus the durable, clustered and enterprise-security parts. A **source-available Plus tier** keeps selected features readable and free to use, but under a licence (ELv2) that stops others from reselling them as a hosted service. **Enterprise** is closed source, lives in a separate private repository, and plugs into the same server through published extension points, so the open server never needs to contain, or know about, enterprise code.

## Good news first: the code is already split along the right lines

A look at the current repository shows that most of the work is moving things, not redesigning them.

| Fact in the code today | Why it helps |
|---|---|
| `persistence-postgres` and `workers` are separate Gradle modules. Each depends only on `core` and `plugin-api`, and nothing in `core`, `web`, `mcp` or `boot` imports them (only two YAML files in `boot` mention their settings) | They can be lifted out whole |
| The seams are interfaces owned by `core` and `plugin-api`: `SessionConfigStore`, `WorkflowDefinitionStore`, `ExecutionLogStore`, `NodeCheckpointStore`, `KeyValueStore`, `SessionHistoryStore`, `LeaderElection` (with `SingleServerLeader` as the default) and the `RemoteNodeExecutor` family | Enterprise implementations of these are exactly the "adapter" you describe |
| Defaults are Spring beans guarded by `@ConditionalOnMissingBean` and property conditions; add-on modules register through `AutoConfiguration.imports` | A jar on the classpath can replace a default with no change to the server |
| The build already has per-edition switches (`-Pyukta.persistence=postgres`, `-Pyukta.workers=true`, `-Pyukta.plugins=...`) and the default build leaves the optional modules out | The first release can already be the Community edition |

What is **missing** is a public, versioned contract (the interfaces live inside the large `core` module, and no artifact has ever been published), an "edition" concept so the server can say "this needs Enterprise" clearly, and the licensing paperwork.

## The three tiers

| Tier | Licence | Source | Who it is for |
|---|---|---|---|
| **1. Community** | Apache-2.0 | Public, this repository | Everyone: try it, embed it, run single-server workloads |
| **2. Plus** (name to decide) | **Elastic License 2.0 (ELv2)**, source-available, see below | Public, this repository, in its own directory | Teams that want durable single-node storage, free to use for their own purposes, and the route by which hosting vendors learn they need a commercial licence |
| **3. Enterprise** | Proprietary commercial licence | Private repository `infenia/yukta-enterprise` | Organisations that need durability, availability, scale and enterprise security |

### The tier-2 licence: ELv2

You first asked for an "open-source" licence that protects proprietorship, and then asked whether ELv2 can be used. **It can, with one consequence you must accept: ELv2 is a source-available licence, not an open-source one.** It is not approved by the Open Source Initiative, so the Plus tier must never be described as "open source" in the docs, the README or marketing. Community stays open source (Apache-2.0).

What ELv2 says, in short (the licence text is the authority):

| ELv2 allows | ELv2 forbids |
|---|---|
| Use, copy, modify and redistribute the code, including commercially and inside a company | Providing the software to others **as a hosted or managed service** that gives them access to a substantial set of its features |
| Distribute your own changes, keeping the licence | Moving, disabling or circumventing **licence-key functionality**, or removing licence and copyright notices |
| No obligation to publish your own changes, and no copyleft | Using the licensor's trademarks beyond what the licence permits |

How the options compare for this product:

| Licence | OSI open source | Stops a hosted competitor | Corporate adoption | Dual licensing leverage |
|---|---|---|---|---|
| **ELv2 (chosen)** | No | Yes, directly and by name | Easy: no copyleft, internal use is free | Commercial licence needed only by hosting vendors |
| AGPL-3.0-only (previous recommendation) | Yes | Indirectly, through copyleft | Many companies ban AGPL | Strong: also sells to anyone who cannot accept AGPL |
| MPL-2.0 | Yes | No | Easy | Weak |

Why ELv2 fits here: your stated concern is protection of the product, not forcing users to share changes. ELv2 addresses that concern directly, and it does not frighten away the enterprises that you also want as paying Enterprise customers.

What you give up compared with AGPL: the "open source" label; automatic acceptance by organisations and distributions that allow only OSI licences (some Linux distributions will not package it, and GitHub shows it as "other"); and the AGPL's ability to push every corporate user toward a commercial licence.

Consequences to know before accepting:

1. **Mixing with Apache code.** Apache-2.0 allows Apache code to be included in an ELv2 work. A binary that contains Community and Plus code is therefore offered under ELv2's terms for the Plus parts, and the Apache parts stay Apache. As before, the **Plus build is a separate artifact** from the Community build, and Community must never depend on Plus, so the Community binary stays purely Apache and open source.
2. **Enterprise code that you own can use Plus code** freely, since you are the copyright holder and are not bound by your own licence.
3. **Ownership is still essential.** Offering a commercial licence to hosting vendors needs Infenia to own all Plus code, so the contributor agreement is still required, see [Legal groundwork](#legal-groundwork).
4. **Ask counsel one specific question:** whether the "hosted service" and licence-key clauses are worded as you intend for a workflow orchestrator, since Yukta is often itself run as a service inside a customer's own organisation.

### Everything else

The engine, DAG validation, REST and MCP interfaces, web UI, CLI, playground, built-in triggers, terminals, flow, transform and external-I/O plugins, rule supervisor and rule control plane, run controls, observability, the `LLM_CALL` and MCP tool plugins, and the install scripts all stay in **Community**.

**D5 (decided):** the AI features stay in **Community**: `LLM_CALL`, the MCP tool plugins, `SESSION_MEMORY`, the decision plugins and System One backend, and the model and rules-first control planes. They are central to how the product is positioned, so Plus contains only the single-node file persistence.

### The honest cost of the free-tier cut

Today Community can write sessions to disk. Removing that means a free user loses all workflows on restart. Mitigations that keep Community useful without persistence, all small:

- **Declarative start-up:** a `yukta.bootstrap.dir` that applies every session JSON file in a folder when the server starts, so definitions live in git, not in the server. Users already have `yukta-cli session apply`.
- **Export:** `GET` endpoints already return definitions; the docs would show a one-line backup.
- **Clear messaging:** the server logs once at startup that state is in memory, and the docs say so on the first page a user sees.

## Architecture: how Enterprise plugs in

```text
        public repository (infenia/yukta)                   private repository (infenia/yukta-enterprise)
 ┌────────────────────────────────────────────┐        ┌───────────────────────────────────────────────┐
 │ spi      (Apache) interfaces + test kit    │◄───────│ persistence-postgres   implements the stores  │
 │ plugin-api, messaging (Apache)             │◄───────│ ha                     implements LeaderElection│
 │ core, web, mcp, ui, plugins (Apache)       │        │ workers                implements remote nodes │
 │ plus/    (ELv2)  optional                  │        │ security-sso, security-rbac, audit, secrets    │
 │ boot            Community build            │        │ license                verifies the licence file│
 │ boot-plus       Community + Plus build     │        │ boot-enterprise        Community + Enterprise  │
 └────────────────────────────────────────────┘        └───────────────────────────────────────────────┘
          published to Maven Central ───────────────────► consumed as ordinary dependencies
```

### 1. A small public contract: the `spi` module

Extract the interfaces now buried in `core` into a new Apache-2.0 module `spi`, and publish it with a stability promise:

- **Storage:** `SessionConfigStore`, `WorkflowDefinitionStore`, `ExecutionLogStore`, `ExecutionControlStore`, and (already in `plugin-api`) `NodeCheckpointStore`, `KeyValueStore`, `SessionHistoryStore`.
- **Availability:** `LeaderElection`.
- **Scale:** the node-execution seam behind `RemoteNodeExecutor`.
- **Security:** new `Authenticator`, `Authorizer` and `AuditSink` interfaces. Today `ApiKeyFilter` and `ApiKeys` do all three jobs in one place; they would become the Community implementation of those interfaces.
- **Edition:** an `Edition` value and a `FeatureGate` (see below).
- **A test kit (TCK):** a set of tests that any store or election implementation must pass, published as a test jar. Enterprise runs it in its CI against its own adapters, so a change to the contract that breaks Enterprise fails in the open repository first.

The public repository's `core` depends on `spi`. Enterprise depends on `spi` and never on `core` internals. This extraction is mechanical (moving interfaces and their DTOs) and changes no behaviour.

### 2. Extension by Spring auto-configuration

Enterprise modules register through `AutoConfiguration.imports`, exactly as `persistence-postgres` and `workers` do today. Each declares `@ConditionalOnMissingBean` against Community defaults, so putting the jar on the classpath replaces the in-memory store, the single-server leader and the API-key filter with Enterprise versions. No `if (enterprise)` code is needed in the open source.

### 3. Edition and feature gate

- An `Edition` bean (`COMMUNITY`, `PLUS`, `ENTERPRISE`) reports what is installed. `GET /actuator/info` and a new `GET /api/edition` show the edition, the enabled features and, for Enterprise, licence expiry. The web UI uses it for "available in Enterprise" hints.
- A start-up check turns silent misconfiguration into a clear error. Today, a Community build given `yukta.session.store-type=postgres` has no matching bean; instead it should stop with: *"yukta.session.store-type=postgres requires Yukta Enterprise (https://...)"*. The same applies to `yukta.ha.mode`, `engine.placement`, and a second API key. Features are listed in one table, so adding a gate is one line.
- Gates only refuse to start or to enable a feature. They never delete or hide user data.

### 4. Packaging: the native-image constraint

The main distribution is a GraalVM native binary, and a native binary is a closed world: it cannot load extra jars at run time. So Enterprise cannot be "download a plugin jar and drop it in". Two ways to ship:

| Approach | How | Fit |
|---|---|---|
| **A. Compose at build time (recommended)** | `yukta-enterprise` has its own `boot-enterprise` module that depends on the published Yukta artifacts plus the Enterprise modules, and builds its own native binary and Docker image (`yukta-enterprise`) with the same `release/` scripts used for Community | Works for native and for Docker; matches how `boot` already picks plugins with `-P` switches |
| **B. JVM with run-time plug-ins** | Enterprise jars in a `plugins/` directory loaded by Spring Boot's `PropertiesLauncher` | Only for the JVM distribution, which the docs treat as the last resort |

Recommendation: A for everything, B only if a customer needs to add their own adapters without a rebuild. In either case the Enterprise binary is delivered from a private registry or a customer portal, not from the public GitHub release.

### 5. Licence enforcement for Enterprise

- A signed licence file (for example a JWT signed with Ed25519): customer, edition, enabled features, node limit, expiry. The Enterprise build embeds the public key and verifies offline.
- **No phone-home**, which keeps today's promise that the server contacts nobody, and works in air-gapped networks.
- Behaviour on expiry: a grace period with warnings, then the Enterprise features refuse to *start*. A running instance and its stored data are never deleted or locked.
- Honest limits: closed source and a contract do the real protection; the key check is a speed bump, not DRM. Avoid obfuscation.

## Moving the existing code

1. **Copy with history.** Use `git filter-repo` to export `persistence-postgres/` and `workers/` (and their tests, `application-postgres.yaml`, Flyway migrations and the module docs) into the private repository with their history.
2. **Remove from the public `main`.** Delete the two modules and the `-Pyukta.persistence` and `-Pyukta.workers` switches from `boot/build.gradle.kts` and `settings.gradle.kts`. Replace them with the feature gate messages above.
3. **Leave the public history alone.** The code is in the public Git history under Apache-2.0, and that grant is irrevocable for anyone who already has it (there is at least one fork). No release was ever tagged, so nothing was distributed as a product, but the old snapshot stays Apache forever. Rewriting public history would not recall clones or the fork and would break everyone's checkouts, so the plan does not do it. New work happens only in the private repository.
4. **Docs.** The user-facing pages for persistence, high availability, remote workers and parts of security stay public as *product* pages with an "Enterprise" tag (that is what sells it), but their configuration detail and the module pages `contributing/modules/persistence-postgres` and `workers` move to private documentation.
5. **File persistence.** Per D3, either remove the `File*Store` classes from Community and re-create them in `plus/`, or move them to Enterprise.

## Legal groundwork

Do these before moving any code. They are the part most likely to cause trouble later.

| Item | Why |
|---|---|
| **Confirm who owns the copyright.** Almost all commits are by one author plus the `engineering-infenia` account and Dependabot. Confirm that the author's work is assigned to Infenia Private Limited (employment or contractor terms) | Dual licensing and a closed Enterprise repository both require Infenia to own the code it relicenses |
| **Add a Contributor Licence Agreement** (a Developer Certificate of Origin alone is not enough, because Infenia must be free to license Plus code commercially) **before accepting outside contributions.** `CONTRIBUTING.md` has neither today | Without it, one outside contribution to a Plus file can make dual licensing impossible for that file |
| **Choose and register a trademark policy** for the name "Yukta" and the logo | A licence on the code does not stop others using your name |
| **Write the Enterprise licence (EULA)** and a commercial licence for Plus | The contracts that actually enforce the tiers |
| **Update licence metadata**: SPDX headers (`Apache-2.0` vs `Elastic-2.0`), per-directory REUSE annotations, `LICENSES/Elastic-2.0.txt`, `NOTICE`, and the `licensee` allow-list so dependencies for Plus are checked correctly | The repository already enforces licence hygiene; the tiers must fit into it |
| **Counsel review** of all of the above, including how the `boot-plus` build combines Apache and ELv2 code, and the wording questions in [the tier-2 licence](#the-tier-2-licence-elv2) | This plan is not legal advice |

## Risks

| Risk | Mitigation |
|---|---|
| Relicensing code that was contributed by others | Confirm ownership and the CLA first; do not move anything until done |
| The Enterprise adapters drift from the public contract | The test kit runs in both repositories; strict compatibility rules for `spi` |
| Native-image closed world prevents drop-in plug-ins | Build-time composition (approach A); a JVM plug-in directory only if needed |
| Community feels crippled without persistence and drives users away | Bootstrap directory and export; keep a generous Community in every other respect |
| ELv2 is not open source, so some users and distributions will skip Plus | Keep everything else in Community under Apache-2.0; describe Plus accurately as source-available; Plus only holds file persistence, so little depends on it |
| The old Apache snapshot of the moved code stays available | Accept it; the value is in ongoing development, support and the new Enterprise features, not in hiding old code |
| Two repositories double the release effort | Reuse the `release/` scripts; one compatibility table; automated cross-repository CI |
| Licence key checks annoy honest customers | Offline verification, long grace period, never touch data |
