## Boot

### Evolution path

Boot's path is mostly about making the safe choice the default and proving the shipped artifact works.

1. **Today.** One process, loopback by default with a start-up guard, dev default on the JVM, prod forced on native, all plugins except script-js by default, in-memory state unless a persistence or workers build is chosen.
2. **Safer defaults.** Done: refuse to bind publicly without a key, guard /actuator. Next: fix the guard for the MCP-key-only case, guard or switch off Swagger, prod as the default profile, trim dev exposure. Risks: `guardMcpKeyOnly`, `profileDefault`, `devExposure`, `openOps`.
3. **Verify the shipped artifact.** Smoke-test the native binary and its profile; measure the build heap; make tests independent of plugin choice. Risks: `nativeGap`, `xmx8g`, `testsNeedPlugin`, `profileForce`, `nativeMetaStale`.
4. **Persistent profile.** A documented profile with file stores or a database, and clean-up of dead keys. Risks: `singleProc`, `deadKeys`.
5. **Flexible packaging.** Prebuilt plugin variants or a plugin directory for JVM builds. Risks: `buildFixed`, `scanBroad`.

### Quality lenses

<AccordionGroup>
<Accordion title="Scalability">
Boot adds nothing that scales: one process, one port. All scaling questions belong to core. It does not block scale-out, but it offers no help either.

**Ceilings today**

- One JVM, one Netty server, one port for API, MCP and management
- In-memory defaults mean copies share nothing
- Native image fixes the plugin set
- Management traffic shares the API pool

**Levers today**

- Virtual threads for blocking work
- Gzip in prod
- Long cache for hashed assets

**Needs design work**

- A documented multi-instance setup, or an explicit statement that it is single-node
- A separate management port
- A CDN or ETag strategy for assets if traffic grows

</Accordion>
<Accordion title="Performance">
Start-up and memory are the performance topics here. Native image gives the best start-up; the JVM is easier to build.

**Ceilings today**

- The native build needs a big heap and time
- index.html is read per request
- Debug logging with payloads in dev costs CPU and disk

**Levers today**

- Native image with AOT
- 365-day cache of hashed assets
- Eager start-up that finds faults early

**Needs design work**

- Measured start-up and memory numbers per mode
- Cache the index file in memory
- A budget for build time and heap

</Accordion>
<Accordion title="Availability">
Nothing in boot restarts, replicates or drains. Availability comes from the platform that runs the process, and from core's recovery after a restart.

**Ceilings today**

- No graceful shutdown setting is configured here
- Defaults lose state on restart
- Health detail is probably hidden

**Levers today**

- Health endpoint in every profile
- Eager start-up so bad config never half-starts
- Fail-fast build for plugin typos

**Needs design work**

- Readiness vs liveness split
- A shutdown grace period set explicitly
- A persistent-state profile

</Accordion>
<Accordion title="Security">
The strongest lens for this module. Since the first guide the start-up guard, a guarded actuator and Host/Origin checks were added; what is left is the dev default, the open docs, and one gap in the guard.

**Ceilings today**

- Swagger and /v3 are outside any key
- The guard accepts yukta.mcp.api-key alone, which leaves /api open
- Default JVM profile is dev
- Keys are optional on loopback

**Levers today**

- Loopback by default, and a start-up refusal on other addresses without a key
- Actuator guarded by an ADMIN key; no heapdump or env exposure
- CSP and no-cache on index.html
- Profile test guards prod config

**Needs design work**

- Prod-by-default or a refusal to bind publicly in dev
- Guard the docs, or switch them off in prod
- A guard that checks the keys the filters use

</Accordion>
<Accordion title="Operability">
Good basics: three profiles' worth of logging, request ids in log lines, a health URL. Missing is guidance and guard rails for production.

**Ceilings today**

- Config split across YAML, environment and build flags
- Keys that nothing reads
- Which plugins are in a given binary is not visible at run time

**Levers today**

- Console logs with request id
- Health, info and metrics
- Documented run commands

**Needs design work**

- Expose the build's plugin list in info
- Remove or implement dead config keys
- A production example config

</Accordion>
<Accordion title="Evolvability">
Adding a module or plugin is one line in the build file, which is cheap. The weak spot is that behaviour is spread across the build flag, YAML and a launcher rule.

**Ceilings today**

- Plugin list is a hand-kept map in the build script
- Profile forcing is in code and in the build
- Legacy /sse name lingers

**Levers today**

- Single place to add modules
- Tests for config and launcher rules
- Fail-fast validation of plugin names

**Needs design work**

- Derive the plugin list from the module tree
- Decide and document the profile policy
- Retire the /sse alias on a schedule

</Accordion>
</AccordionGroup>

### Questions to settle

- **Security.** The server is exposed on 0.0.0.0 with an API key and no profile. List what a stranger can read (hint: the docs), and what changes if only yukta.mcp.api-key is set. (risk `openOps`)
- **Security.** Which of our default settings would you change first to be safe in production, and what breaks for developers? (risk `profileDefault`)
- **Scale.** You must run three copies behind a load balancer. What does each copy hold that the others cannot see? (risk `singleProc`)
- **Packaging.** A customer wants a build without shell execution and without JavaScript. What do they type and what can they not change later? (risk `buildFixed`)
- **Reliability.** A native-only crash appears after a release. How would we have caught it? (risk `nativeGap`)
- **Operability.** An operator asks which plugins are in the binary. Where do they look? (risk `scanBroad`)
- **Web.** A client calls /apis/workflows by mistake. What does it get and is that fine? (risk `apiPath200`)
- **Caching.** We replace favicon.ico. When do users see it? (risk `staticStale`)
- **Config.** How would you prove every key in application.yaml is read by something? (risk `deadKeys`)
- **Testing.** Someone builds with -Pyukta.plugins=none. What tells them tests can't pass? (risk `testsNeedPlugin`)

## Build logic

### Evolution path

Order is by cheap trust gains first: make what the build says true, then close bypasses, then make it reproducible, then speed it up.

1. **Today.** Six plugins, one catalog, 27 modules. Gates fail the build; OpenGrep needs the program installed; one coverage exception; no lock files; Netty now comes from the catalog; CI builds in four shards.
2. **Make the docs and versions honest.** Correct the docs from the code, delete the stale Netty line, fix the nashorn reason text, and decide whether pull requests should block on vulnerabilities. Risks: `nettyTwoSources`, `docDrift`, `legalSignoff`, `trivyPrGate`, `cvePins`.
3. **Close the escape hatches.** Guard every quality task against being disabled, fail on missing coverage data, burn down the three temporary disables, check build-logic itself. Risks: `disabledTasks`, `coverageNoData`, `selfUnchecked`.
4. **Reproducible and visible.** Commit lock files and turn on the CI check; warn when OpenGrep is skipped; add a toolchain resolver; align Node and pnpm in CI. Risks: `noLockfiles`, `opengrepSilentSkip`, `noToolchainResolver`, `nodeDrift`.
5. **Faster and sharper.** Run OpenGrep once with declared outputs, tune Error Prone and SpotBugs, generate the CI module map, and decide whether 100% per class stays. Risks: `opengrepEveryModule`, `advisoryTools`, `ciManualMap`, `strict100`, `fullBuildOnRoot`.

### Quality lenses

<AccordionGroup>
<Accordion title="Scalability">
Scales with module count, not users. Each of 27 modules runs its own analysis, and the checks that cannot be cached (OpenGrep, which declares no outputs) grow linearly. CI runs a whole-repo build whenever a root file changes.

**Ceilings today**

- OpenGrep runs one module at a time (a shared service) but is cacheable, so unchanged modules are skipped
- A catalog, config or build-logic change triggers a full CI build
- One CI runner with a 30-minute timeout
- Test forks are limited by memory

**Levers today**

- Gradle build cache and parallel execution
- Path-filtered PR builds with buildDependents
- Test forks scaled to CPUs / 2

**Needs design work**

- Run OpenGrep once at the root or give it declared outputs
- Split a full build across runners if it nears the timeout
- Remote build cache for CI and laptops

</Accordion>
<Accordion title="Performance">
A local ./gradlew check is the developer's inner loop, so its time is what matters. Rules are heavy (five analysers, per-class coverage, a scan), and CLAUDE.md steers developers toward the smallest test scope.

**Ceilings today**

- Static analysis is not incremental across the board
- Coverage verification depends on every test finishing
- Configuration cache is off (Go tasks are incompatible)
- Test JVMs run at the lowest compiler tier

**Levers today**

- Build cache on; parallel on with 8 workers
- JaCoCo reports built only with -Pcoverage
- Tests in parallel forks, ParallelGC

**Needs design work**

- Turn on the configuration cache for modules that allow it
- Measure which gate dominates check time
- Exclude test sources from the slowest analysers if needed (judgement)

</Accordion>
<Accordion title="Availability">
Barely applies to production, since build-logic runs nowhere at run time. It matters for the availability of the build: a broken convention plugin stops everyone, and CI downloads tools and rules at run time.

**Ceilings today**

- One broken convention script fails every module
- CI depends on GitHub, Maven Central, the Gradle plugin portal and tool download sites
- No JDK 25 means no build

**Levers today**

- OpenGrep rules are local, so no rule download
- Pinned Action SHAs and a checked OpenGrep binary
- The wrapper jar is validated

**Needs design work**

- A mirror or cache for plugin and dependency downloads
- A toolchain resolver or documented JDK setup
- Dependency lock files to make restores deterministic

</Accordion>
<Accordion title="Security">
This is where build-logic earns its keep: it is the supply-chain control point. It bans four dangerous code patterns, enforces a licence list, pins CVE-affected versions, and CI pins tools by checksum or commit hash.

**Ceilings today**

- Locking is declared but no lock files exist, so resolved versions are not recorded
- Vulnerability scan blocks only on main, not on pull requests
- Four OpenGrep rules cover few risk patterns
- A stale Netty line remains in gradle.properties; the resolved version is not asserted

**Levers today**

- Local pinned OpenGrep rules with --error
- Licence allow-list with one per-artifact exception
- Netty BOM imported after Boot; plexus-utils pinned
- Secret scan blocking on every run; dependency review on PRs

**Needs design work**

- Commit lock files and enable the CI lock check
- Remove the stale Netty line and add a check of the resolved version
- More OpenGrep rules for the plugin sandbox and file access
- Legal sign-off for the nashorn-core exception

</Accordion>
<Accordion title="Operability">
Developer experience: clear failures, one command to fix formatting, and a documented way to add a module. The weak spots are silent skips and docs that disagree with the code.

**Ceilings today**

- Silent skip when opengrep is missing
- Docs say 90/85 while code enforces 100/100
- Adding a module needs edits in settings and two places in ci.yml
- Failure messages come from several tools in different styles

**Levers today**

- spotlessApply fixes formatting
- Reasoned coverage exceptions and stale-entry errors with clear messages
- CI lint reports a missing path filter by name

**Needs design work**

- Print a warning when OpenGrep is skipped
- Keep CLAUDE.md and guides in step with the code
- Generate the CI module list from settings.gradle.kts

</Accordion>
<Accordion title="Evolvability">
Good: rules are in one place, versions in one catalog, and the plugins are small and layered. The cost is that a rule change hits all 27 modules at once, and a few module-level escapes exist.

**Ceilings today**

- A new strict rule blocks every module at once
- spring-conventions is the de facto standard bundle (naming)
- Quality tooling is Java only
- Escape hatches in module build files

**Levers today**

- Layered plugins
- Reasoned exception DSL
- Config files separate from code

**Needs design work**

- A rollout path for new rules (warn first, then fail)
- A guard against disabling quality tasks
- A decision on how Kotlin build code is checked

</Accordion>
</AccordionGroup>

### Questions to settle

- **Security.** If the Netty override and the catalog disagree, how would you notice in a pull request, and what would you add to make it impossible? (risk `nettyTwoSources`)
- **Security.** Lock files are declared but absent. What would a locked build protect you from that BOM pinning does not? (risk `noLockfiles`)
- **Operability.** A new contributor never installs OpenGrep. What do you want to happen locally: nothing, a warning, an error, or an auto-download? (risk `opengrepSilentSkip`)
- **Governance.** Three modules disable some analysers with a 'temporarily disabled' comment. Who should own burning those down, and what would make the temporary disable expire? (risk `disabledTasks`)
- **Correctness.** 100% line and branch per class: what tests have you seen written only to reach a branch, and would you accept them? (risk `strict100`)
- **Governance.** Would you accept the nashorn-core exception for a native image without a written legal opinion? What is the smallest evidence you would want? (risk `legalSignoff`)
- **Performance.** Check time on a full repo is mostly waiting. Which gate would you measure first, and what would you change if OpenGrep were the slowest? (risk `opengrepEveryModule`)
- **Evolvability.** A new Checkstyle rule would fail 40 files in 10 modules. How should it be introduced without blocking everyone? (risk `advisoryTools`)
- **Availability.** GitHub or Maven Central is down for an hour. Which parts of the pipeline break, and which would you mirror first? (risk `fullBuildOnRoot`)
- **Operability.** If the CI module map were generated from settings.gradle.kts, what could still go wrong when someone adds a module? (risk `ciManualMap`)

### Build logic review

The convention plugins are well layered (`java`, then `spring`, then `library`, with `quality` and `jacoco` mixed in), the version catalog is shared with the main build, and the quality toolchain is unusually complete: Spotless, Checkstyle, PMD, SpotBugs, Error Prone, a licence allow-list, OpenGrep and JaCoCo with a per-class exception DSL. The review of 2026-10-09 found weak points in policy and enforcement (gates that could not fail, coverage exception sprawl, a broad licence allow-list). All of them are fixed, and the gates now fail the build. What remains open is the supply-chain and housekeeping list below, checked against `main` after PRs #373, #374 and #391 on 2026-10-15.

## CLI

### Evolution path

A practical order: fix what misleads users first, then close the gaps to the server, then make the link to the server self-checking.

1. **Today.** Five command groups (about forty commands, including watch, result, node retry, breakpoint and signal), 100% function coverage, pinned tools, releases with checksums. The first page of every list, no retries, no resume.
2. **Make it honest.** Done: `session apply` is registered. Next: refresh the README, fix the root description, silence the duplicate error output, add `yukta version`, and test that every written command is registered. Risks: `docsStale`, `errorNoise`, `noVersion`.
3. **Close the main gaps.** Paging flags, stop mode, idempotency key, empty reason fix, and the commands still missing (validate, versions, approvals, scheduler limits and priority, recover, supervisors). Done: events (`controlbus watch`), node retry, breakpoint, signal, result. Risks: `noPaging`, `stopMode`, `idemKey`, `emptyReason`, `missingCmds`.
4. **Robust in pipelines.** Opt-in retries, stream reconnect with Last-Event-ID, distinct exit codes, consistent -o, token safety warnings. Risks: `noRetry`, `streamLoose`, `outputUneven`, `tokenPlain`.
5. **Self-checking against the server.** A contract test (real server or OpenAPI) in CI, a registration test over the command tree, and a move off deprecated paths. Risks: `dtoDrift`, `legacyPaths`, `testsTwice`, `winBuild`, `fileOrJson`, `localTimestamps`, `keywordProblems`.

### Quality lenses

<AccordionGroup>
<Accordion title="Scalability">
A command-line client barely has a scaling story: one short-lived process, one request. What scales badly is not the program but its hand-written copy of the API (every new endpoint needs hand edits) and its inability to see past the first page of a long list.

**Ceilings today**

- Lists stop at the server's first page (500 by default, 1,000 at most) with no way to continue
- One hand-written function and command per endpoint: the work grows with the API
- A single stream event larger than 1 MB ends the stream
- Many parallel CLI calls from CI each open their own connection; no shared pooling

**Levers today**

- Streams do not buffer: events are printed as they arrive
- Static binaries scale to any number of build agents without installs

**Needs design work**

- --limit and --cursor flags or an automatic follow of X-Next-Cursor
- A generated client or a contract test to stop manual drift
- A larger or configurable line limit

</Accordion>
<Accordion title="Performance">
Start-up is fast because there is no runtime to boot: it is a static Go binary. The real latency is the network round trip and the server. Performance is not a concern of this module.

**Ceilings today**

- Each command pays one connection setup (and TLS handshake if https)
- Whole answers are read into memory before printing
- 30-second default limit may be too short for large answers

**Levers today**

- Milliseconds of start-up; no JVM
- Request body and flags are tiny
- No retries, so no hidden extra load on the server

**Needs design work**

- Nothing urgent. A batch mode could save reconnects if scripts call it hundreds of times

</Accordion>
<Accordion title="Availability">
The CLI is only as available as the server. It fails fast (30 s) and never retries, which is predictable but unforgiving for flaky networks and for the 'at limit' answer the server gives on purpose.

**Ceilings today**

- No retries or back-off on 429, 5xx or network errors
- Streams do not reconnect, and a clean close looks like success
- Exit code 1 for every failure, so scripts cannot react differently to each
- A hung stream with a silent server waits forever

**Levers today**

- A time limit on every normal call
- Ctrl-C always works on streams
- Clear 'request failed' versus 'API error' wording

**Needs design work**

- Opt-in retry for safe GETs and for starts with an idempotency key
- Reconnect with Last-Event-ID
- Distinct exit codes for usage error, server error and timeout

</Accordion>
<Accordion title="Security">
The CLI is a credential carrier. It sends a bearer token to whatever address it is given, and the server's API key is the only protection on an open server. The server's default is loopback only, and the CLI's default URL matches that.

**Ceilings today**

- Token sent over plain http with no warning
- `--token` on the command line is visible in shell history and the process list
- No control over TLS (custom CA, client certificates)
- Path escaping protects ids, but nothing validates the server's identity beyond normal TLS

**Levers today**

- Ids are escaped, so a hostile id cannot redirect a request
- Token read from the environment by default
- gosec and govulncheck run in the build; releases carry checksums and provenance
- User-named files are read deliberately and annotated for the scanner

**Needs design work**

- A warning (or refusal) when a token would go over http to a non-loopback host
- Documented advice to use YUKTA_TOKEN rather than --token
- A way to trust a private CA

</Accordion>
<Accordion title="Operability">
Easy to build and test, harder to support in the field. A user cannot tell which version they run, errors appear twice with help text, and the documentation describes commands and files that do not exist.

**Ceilings today**

- No version command and no embedded version
- Errors printed twice and wrapped in usage text
- README out of date: wrong binary names, a `goBuildDev` task that does not exist, a config file and `--file` flag that do not exist, `/api/v1` paths
- Windows developers need make and a POSIX shell

**Levers today**

- Release workflow with SHA256SUMS and provenance
- One source of truth for the build (the Makefile)
- Clear error prefixes: request failed versus API error

**Needs design work**

- A `version` command with ldflags
- Silenced duplicate error output
- Refresh the README and CLAUDE.md, add a test that every command listed in help is registered

</Accordion>
<Accordion title="Evolvability">
Adding a command is easy and cheap because of the shared builder, and the code is small and fully covered. The weakness is the link to the server: nothing breaks when the server changes, so the CLI quietly drifts.

**Ceilings today**

- Hand-written DTOs and paths with no contract test
- Server marks the paths the CLI uses as deprecated
- Registration by hand: a finished command can stay unreachable
- Shared package-level output variable

**Levers today**

- Generic Action helper keeps new simple commands to a few lines
- Tests use a real HTTP server, so refactors are safe
- 100% per-function coverage

**Needs design work**

- A contract test against the server's OpenAPI document or a real server in CI
- A test that walks the command tree and compares it with a list of supported endpoints
- Move to the non-deprecated paths with care for the session check

</Accordion>
</AccordionGroup>

### Questions to settle

- **Scope.** Is the CLI a full admin tool or a small CI helper? The answer decides whether the 12 missing endpoints matter. (risk `missingCmds`)
- **Correctness.** With more than 500 sessions, what should `session list` do? Truncate silently, warn, page, or fail? (risk `noPaging`)
- **Security.** Would you let a token go over plain http to a non-loopback address? What is the right default? (risk `tokenPlain`)
- **Reliability.** A pipeline starts a run and the call times out. What should it do next, and what does the CLI offer? (risk `idemKey`)
- **Availability.** The stream ends with no error and no final status. Is that success, failure or unknown? (risk `streamLoose`)
- **Evolvability.** How would you notice, today, that the server renamed a response field? Who finds out first? (risk `dtoDrift`)
- **Quality.** session apply was written, tested and promised by the README but not registered, and is registered now. What test would have caught it, and does one exist for the other commands? (risk `docsStale`)
- **Operability.** What exit codes would your automation want, and who should own that contract? (risk `errorNoise`)
- **Governance.** Where should the CLI documentation come from so it cannot go stale: Cobra itself, or the Makefile? (risk `docsStale`)
- **Migration.** The server plans to drop the session-qualified paths. What do you lose, and how would you keep the cross-session safety check? (risk `legacyPaths`)

### CLI review

The CLI was a clean, thin REST client with robustness and build-hygiene problems, and all 13 findings of the review of 2026-10-09 are fixed: paths are escaped, non-streaming requests time out (`--timeout`, default 30 s), the client can send a bearer token and a start payload, tools are pinned and the build is reproducible, and the test-only interfaces and the 612-line mock are gone (main code went from about 3.7k to 2.9k lines, tests from about 11.5k to 8.0k, and `build.gradle.kts` from 578 to 48 lines). Since then the CLI gained `controlbus watch`, `result`, `workflow node retry`, `breakpoint` and `signal`, and `session apply` is now registered. What is open is feature parity with the server (paging, stop mode, idempotency, reconnect, and commands for newer endpoints) and a few rough edges. The scorecard after the fixes is command design 4.5/5, correctness 4.5/5, server parity 4/5, build 4.5/5 and tests 4.5/5.

## MCP

### Evolution path

A suggested order, driven by risk rather than by size. The first steps are small and close the largest exposures.

1. **Today.** 23 tools, stateless /mcp, the same named keys and roles as REST (optional), per-tool role check, session-limited keys, ownership check, bounded log reader with a cursor, polling for progress.
2. **Close the cheap gaps.** Done: refuse non-loopback without a key. Next: make one setting cover REST and MCP, add idempotencyKey, payload and stop mode to the tools, fix both creation guides and test them, show config fields and config-aware ports in plugin details. Risks: `apiKeyOpen`, `noIdempotency`, `stopParity`, `sessionGuideWrong`, `pluginGuideWrong`, `portsNoConfig`, `configSchemaHidden`.
3. **Know who is calling.** Done: named keys with roles, sessions and an actor. Next: a rate limit, a log or counter for rejected calls, and a test that the role map covers every tool. Risks: `noActor`, `noRateLimit`, `bodyReparse`, `rejectsUnlogged`.
4. **Safer authoring and reading.** Overwrite flag and dry-run for create_session. Mark log lines as data. Paging for history, sessions and logs. Risks: `overwriteSession`, `logInjection`, `noPaging`.
5. **Live and cheap status.** A one-pass summary in core for the status tool. A way to wait for or subscribe to changes, so agents stop polling. Risks: `healthLinear`, `noPush`, `signalNotState`.
6. **Keep it honest.** Generate the tool table from annotations in a test, add a parity check with web, re-enable PMD on tests. Risks: `docsDrift`, `pmdTestOff`.

## Messaging

### Evolution path

1. **Today.** One immutable envelope, one pass-through channel, core stamps history and routes by port. Several fields carried but unused.
2. **Decide the unused fields.** For each unenforced field choose: enforce it (for example an expiry check), or remove it. Make `from` and `withPayload` use one copy path. Risks: `unenforced`, `copyDrift`, `wideContract`.
3. **Define the channel contract.** Write what a channel may do on failure, how it signals slowness, and fix the registration through auto-configuration. Done: a skipped processor now goes through the channel too. Risks: `channelErrors`, `conditionalOrder`, `edgeDropsUnseen`.
4. **Payload model.** Choose a payload story: a canonical JSON tree, an optional schema, and a claim check for large bodies. Risks: `payloadSize`, `untypedPayload`, `shallowImmutable`.
5. **Better lineage.** Carry history through split and aggregate, record truncation, and add a per-output id if needed. Risks: `historyCap`, `lineageReset`, `idNotUnique`.
6. **A real second channel.** Build one durable or remote channel to prove the SPI, and trusted-header rules for it. Risks: `remoteSpi`, `forgeable`, `wireFormat`.

<AccordionGroup>
<Accordion title="Scalability">

**Ceilings today**

- Copy cost is proportional to metadata size at every header change

- Singleton direct channel, no extra operators

<Accordion title="Performance">

- Each wither allocates a new 22-field record

**Levers today**

- **Operability.** How would you know which channel provider is active in production, and how would two providers be diagnosed? (risk `conditionalOrder`)

## Persistence PostgreSQL

### Evolution path

1. **Today.** Nine tables, seven stores, a lease. Statements are single and safe; recovery rewrites and multi-step operations are not atomic; the fencing number is unused.
2. **Make recovery safe.** Transactional rewrite of the log, durable start and end events, transactions for the multi-step operations. Risks: `logReplaceAll`, `logDropsEvents`, `noTransactions`.
3. **Fence the leader.** Pass the fencing token to the writes that matter and refuse older tokens in the statement. Risks: `fencingUnused`.
4. **Index and bound.** Index the event type and update time, stream the reads, make the KV cap and the clean-up honest, add a session delete. Risks: `compactionCost`, `readsWholeSets`, `historyTtlScan`, `kvCapRace`, `noDelete`, `noRetention`, `sessionConfigGaps`.
5. **Observe it.** Meters and a health check for the stores, a startup summary of which store is used, honest counters. Risks: `noStoreMetrics`, `halfDurable`, `heldBytesDrift`, `blockingCalls`.
6. **Operate it.** Separate accounts, an upgrade test on data, a documented backup and restore. Risks: `twoConnections`, `noMigrationPlan`.

### Quality lenses

<AccordionGroup>
<Accordion title="Scalability">
Fine for one control plane and a few hundred runs. The log has one writer thread, the lease is one row, and several operations load or scan whole tables.

**Ceilings today**

- One writer thread and one statement at a time for the execution log
- Compaction and recovery scan the whole log
- Reads of the log and of a node's output load everything into memory
- Per-session history and KV counts scan their tables

**Levers today**

- Batched inserts of up to 100 events
- Large messages are stored out of line by PostgreSQL
- Trim to the newest runs, never open ones

**Needs design work**

- Indexes for the ttl delete and the compaction query
- Stream reads (a cursor) instead of loading whole sets
- Partition or archive the log if runs are many

</Accordion>
<Accordion title="Performance">
Single statements are cheap. The costly parts are the one-by-one rewrite at recovery, blocking reads on the resume path, and queries that count or group whole tables.

**Ceilings today**

- replaceAll inserts events one per round trip
- isFinished and isComplete are one query each, per node, blocking
- getAllConfigs runs about seven queries for a session
- get reads every row of a node to return the last

**Levers today**

- Batch insert for the log
- Upserts in one statement for counters and history
- Timeouts on every blocking wait

**Needs design work**

- Batch or bulk the recovery rewrite
- Fetch only the last checkpoint row
- A benchmark for log append rate and resume time

</Accordion>
<Accordion title="Availability">
A crash is recoverable and a standby can take over, but the pieces that make this safe are the least protected: the rewrite is not atomic and the fencing number is unused.

**Ceilings today**

- The log can lose queued events with the process
- A crash inside replaceAll loses the log
- A paused leader can still write after a takeover
- The database is a single point of failure (no failover logic here)

**Levers today**

- Lease with an expiry from the database clock
- Local validity measured from the time of sending
- Release of the lease on graceful stop
- Takeover actions isolated from each other

**Needs design work**

- A transactional rewrite of the log
- Fencing checks on writes by the old leader
- Durable acknowledgement for the run-end event

</Accordion>
<Accordion title="Security">
No authentication of its own: it trusts the database account it is given. The data it stores can include payloads, definitions with literal secrets and chat history.

**Ceilings today**

- Definitions, payloads and chat turns are stored as plain JSON
- One database account for the application; Flyway may use the same
- No row-level separation between sessions
- Secrets typed into a workflow config are stored as written

**Levers today**

- Values are always bound as parameters; the few column names that are concatenated into a statement come from constants in the code
- A pinned, patched scram-client
- Constant statement timeouts

**Needs design work**

- Separate migration and runtime accounts, documented
- Encryption at rest and in transit settings in the setup text
- Redaction of secret-like config before storage (see web and plugins)

</Accordion>
<Accordion title="Operability">
Little visibility: one gauge for the leader and nothing for the stores themselves.

**Ceilings today**

- No metrics for append rate, queue depth, dropped events, statement time or lock waits
- No health indicator for the stores
- The checkpoint byte counter drifts and restarts at zero
- No tool to inspect or repair a damaged log

**Levers today**

- The yukta.leader gauge
- Log lines for dropped events, failed batches and failed trims
- Spring Boot's own R2DBC and Flyway integration

**Needs design work**

- Meters for queue depth, drops and write latency
- A health check that runs a trivial query
- A documented backup and restore procedure

</Accordion>
<Accordion title="Evolvability">
Easy to add a store (one class, one migration, one bean). Hard parts are changing a stored JSON shape and moving a deployment to a newer schema while it holds data.

**Ceilings today**

- Forward-only migrations
- Stored JSON shapes are the Java records; a rename changes what old rows mean
- Tests start from an empty schema

**Levers today**

- Small classes, one per interface
- JSONB keeps most changes out of migrations
- Auto-configuration with one switch per store

**Needs design work**

- A test that migrates a database holding V1 data to the latest version
- A version field inside stored documents
- A rule for removing a column or table

</Accordion>
</AccordionGroup>

- **Failure.** The server dies between the delete and the last insert of replaceAll. What can an operator still do, and what would they have needed? (risk `logReplaceAll`)
- **Reliability.** The log queue is full for ten seconds. Which events are lost, and which of them matter most? (risk `logDropsEvents`)

## Plugin API

### Evolution path

A suggested order. Step 1 comes first because it protects the ability to stop a run.

1. **Today.** A small, working SPI with 16 commands, a supervisor and control-plane SPI, an expression sandbox with a method allow-list, and shared helpers for run budgets and approval waits. Open work is mostly bounds on control calls and expressions, decoupling plugins from core, and tooling for authors.
2. **Bound the control path.** Add review and decide timeouts with a defined outcome, protect stop from being delayed, and align the two ordering rules. Risks: `reviewNoTimeout`, `decideStall`, `orderOpposite`.
3. **Make plugins independent of core.** Move the resolver and map helpers into plugin-api or a support module, expose the registry and tracker through small SPIs, and add an SPI version with a startup check. Risks: `coreDependency`, `noVersion`.
4. **Tools for plugin authors.** Ship test fixtures with a conformance suite, re-enable PMD for tests, and either call shutdown or remove it. Risks: `noTestKit`, `sharedInstance`, `pmdOff`, `shutdownNever`.
5. **Harden expressions and secrets.** Evaluation time budget (the method allow-list is done), parse outside the lock, a run budget that is reserved before the call, scoped and audited secret access, and a data-only UiDesign. Risks: `spelLimits`, `secretThin`, `uiHtml`, `budgetLedger`.
6. **Typed and reactive extension seams.** Non-blocking store calls (the PostgreSQL stores now make this concrete), declared node signals, and a decision on the directive layer and the unused optimiser hooks. Risks: `storeSync`, `onSignalLoose`, `directiveOnlyStop`, `deadHooks`, `eventsBestEffort`, `signalWaitsShared`.

### Quality lenses

<AccordionGroup>
<Accordion title="Scalability">
Barely applies to the module itself: it is interfaces and a few static helpers with no threads or I/O. What it does decide is the scaling shape of everything built on it: one shared plugin instance per type, streams per node, and a single in-process supervisor host.

**Ceilings today**

- One shared instance per type means plugin code must be safe under many concurrent nodes; a field-based cache becomes a contention point
- The expression cache has one lock around parsing and lookup, shared by every plugin in the process
- Supervisor events are handled one at a time per control-plane plugin
- Sync checkpoint calls (clear, isComplete, isFinished) would block threads on a remote store

**Levers today**

- Virtual-thread offload for blocking plugins through one flag
- Bounded expression cache (1000)
- Per-config timeout and buffer hooks

**Needs design work**

- A concurrency test kit that runs a plugin under many nodes
- A non-blocking checkpoint interface for database stores
- A cache with less lock contention if expression use grows

</Accordion>
<Accordion title="Performance">
The helpers sit on the hot path of every message that uses expressions, and parse-once-evaluate-many keeps that cheap. Everything else is interface calls; the cost is in the plugins.

**Ceilings today**

- Each evaluation builds a new evaluation context
- Cache miss parses under the cache lock
- No evaluation timeout: a heavy expression costs whatever it costs
- Messages are immutable; every with-er call copies the envelope

**Levers today**

- Pre-parse hook (preParse) and parse cache
- Default buffer size hook per plugin
- isBlocking keeps blocking work off reactive threads

**Needs design work**

- A benchmark of expression evaluation under load
- Optional per-evaluation time limit
- A guidance note on when to use preParse in prepare

</Accordion>
<Accordion title="Availability">
Not a runtime component, so it has no uptime of its own. It shapes availability through the supervisor SPI, where a hung reviewer or a slow decide() can stall command handling for a run or a plugin.

**Ceilings today**

- review() has no timeout, and commands of one run wait their turn
- decide() handled one event at a time per plugin; a hang stalls that plugin's feed
- Event feed is best effort and has no replay after a missed event
- shutdown is never called, so resources of shared plugins live until the process ends

**Levers today**

- A failing review counts as a denial instead of an allow
- Supervisor failures are retried with backoff and never stop runs
- A failing decide() counts as no opinion

**Needs design work**

- A review time limit with a defined outcome
- A stop that cannot be vetoed or delayed
- A documented bound for decide() enforced by the default supervise

</Accordion>
<Accordion title="Security">
This is where the module matters most: it holds the sandbox for user-written expressions, the veto on control commands, and the secret interface. Authentication itself is not here.

**Ceilings today**

- Expression evaluation has no time or size limit and can still call any public method of reachable objects
- SecretProvider has no caller identity, so it cannot scope secrets per plugin or session
- UiDesign is raw HTML supplied by plugin code and rendered by the UI
- Review vetoes depend on supervisors being present and correct

**Levers today**

- Restricted evaluation context: no static calls, constructors or bean references, with tests
- Breakpoint conditions are declarative, not code
- SECRET field type and decrypted:&lt;key&gt; convention
- Denial on review error

**Needs design work**

- An expression budget (time and size)
- Secret access scoped by plugin and audited
- A sanitising or sandboxed rendering of UiDesign HTML

</Accordion>
<Accordion title="Operability">
The module offers metrics hooks (a reporter interface) and an actor in the command audit, but ships no tooling for plugin authors: no test kit, no lifecycle that tells a plugin when to clean up.

**Ceilings today**

- No test fixtures for plugin authors
- pmdTest is disabled
- A plugin cannot know it is being stopped except by stream cancel
- Config schema and the code that reads it are kept aligned by hand

**Levers today**

- PluginMetricsReporter with a NOOP default and per-node OK/ERROR counts through PluginGuard
- Actor id in the command audit (ControlActor)
- Tests that pin defaults and sandbox rules

**Needs design work**

- A test kit (harness and message builders)
- A conformance test every plugin can run
- Re-enable pmdTest

</Accordion>
<Accordion title="Evolvability">
This is the module's biggest long-term risk: a wide set of defaults that every plugin silently relies on, no version marker, and plugins that also compile against core internals.

**Ceilings today**

- Adding an abstract method breaks every plugin; adding a command breaks every exhaustive switch
- No SPI version, so mismatches show up as runtime errors
- Plugins import VariableResolver, MapUtils, PluginRegistry and the tracker from core
- WorkflowDirective has one member, so its sealed hierarchy gives little extension room yet

**Levers today**

- Default methods for new hooks
- Sealed types that make missing handling a compile error
- Small module with few dependencies

**Needs design work**

- Move the shared helpers plugins need into plugin-api or a support module

## Plugins

### Evolution path

A possible order of work, safest edges first.

1. **Today.** 31 node types and four supervisor kinds on one JVM. Done since the first guide (PRs #373, #374): script sandbox with class allow-list and limits, command allow-list, env allow-list, restricted SpEL methods, LLM and MCP budgets, provider rate limit, tool approvals, PostgreSQL stores for KV_STORE and SESSION_MEMORY. Open: no host allow-list, plaintext secrets in config, no concurrency cap, memory-only defaults.
2. **Contain the sharp edges.** Done: script sandbox, command allow-list. Next: operator-set host and folder allow-lists, a max-concurrency setting, kill descendant processes on timeout, redact secrets in read APIs, make the agent guards a deployment default. Risks: `scriptHostAccess`, `ssrf`, `shellModel`, `orphans`, `fanout256`, `plaintextSecrets`, `fileSandbox`, `agentGuardsOptIn`.
3. **Bound memory and cost.** Evict caches and sessions, put LLM-backed decisions under the run budget (LLM_CALL and MCP_TOOL_CALL already are), derive timeouts for SQL and file plugins, add a connection pool, take SESSION_MEMORY off the reactive threads, truncate logged output. Risks: `unboundedMaps`, `sessionMemory`, `sqlTimeout`, `consoleLogs`, `sessionStoreBlocks`.
4. **Make state durable.** Done: PostgreSQL stores for KV_STORE and SESSION_MEMORY (opt-in). Left: make them the default or warn when memory-only, durable anomaly windows, a persistent scheduler, rules that reload. Risks: `kvVolatile`, `windowsPerRun`, `scheduleLost`.
5. **Clean the layering.** Move the resolver and helpers into plugin-api, validate loop targets, re-enable the gates, rename CONTENT-FILTER with an alias, make control planes optional. Risks: `coreLayering`, `gatesOff`, `loopSkipsValidation`, `loopEscalate`, `typeIds`, `optionalNotOptional`.
6. **Decide the oversight model.** Alert on 'no opinion' from the model plane, prefer rules-first, treat model verdicts as advice. Risks: `modelFailsOpen`, `promptInjection`.

### Quality lenses

<AccordionGroup>
<Accordion title="Scalability">
Per-message plugins scale with the JVM's threads and with the number of nodes, and most of the cost is waiting on outside systems. What does not scale is state: KV_STORE, SESSION_MEMORY and the control-plane windows live in one process.

**Ceilings today**

- Concurrency is per node (4 for process, 16 for HTTP, MCP, model and decision nodes, 1 for session memory); there is no limit shared across nodes or runs
- KV_STORE capped at 10,000 keys in one JVM; SESSION_MEMORY unbounded
- ModelControlPlane asks the model about each matching event, one at a time
- SQL_QUERY opens a connection per message

**Levers today**

- Caps on process output, file reads and SQL rows
- SPLITTER concurrency and AGGREGATE size are settings
- Optional modules keep unused code out of a build

**Needs design work**

- A max-concurrency setting on external plugins
- A store interface so KV_STORE and SESSION_MEMORY can be database-backed
- A connection pool for SQL_QUERY

</Accordion>
<Accordion title="Performance">
Pure plugins (FILTER, BRANCH, PROJECTION) are cheap and cache parsed expressions. The cost is in model calls and outside requests, which take seconds, not microseconds.

**Ceilings today**

- A model call per message (decision plugins, LLM_CALL) dominates latency and cost
- SCRIPT mode creates a fresh GraalJS context per message
- A Handlebars or SpEL parse is cached forever, so memory, not CPU, is the limit
- File and SQL work uses a shared pool for blocking work

**Levers today**

- Compiled scripts and templates are reused
- SpEL cache is a 1,000-entry LRU
- Model clients are reused per configuration
- Timeouts bound every external wait

**Needs design work**

- Rate limits for hosts and non-model plugins (model providers have yukta.llm.rate-limit)
- Budgets for LLM-backed decisions (LLM_CALL and MCP_TOOL_CALL have them)
- Benchmark figures (none were found in the module notes)

<Accordion title="Availability">
Plugins are as available as what they call. The module's job is to fail in a way the graph can handle: status ports, error ports, fallbacks. In-memory state does not survive a restart.

**Ceilings today**

- A failed model, webhook or database fails every message that needs it
- KV_STORE, session history and windows vanish on restart
- The model control plane fails open by design

**Levers today**

- failureMode CONTINUE with routeBy ports for fallback paths
- LLM_CALL passes the payload on for model failover
- Engine retry and dead-letter ports apply on top

**Needs design work**

- Durable session and KV stores
- A circuit breaker for repeated failures of one outside system
- Persistent schedules

</Accordion>
<Accordion title="Security">
This is the lens that matters most. Plugins turn author-written configuration into running code, network calls, file access and database queries. Several guards exist (restricted SpEL, bound SQL parameters, file path checks, https for webhooks), but several are absent.

**Ceilings today**

- JavaScript has a class allow-list, a statement limit and a time limit, but no memory limit

- File sandbox with link checks; SQL bound parameters; https-only webhooks

**Needs design work**

- Host and command allow-lists, set by the operator, not the author
- A memory limit for scripts and a host allow-list for outbound calls
- Secret redaction in read APIs
- A decision on who is trusted to author workflows

</Accordion>
<Accordion title="Operability">
Each external plugin counts successes and errors per node and publishes a usage description. MCP calls get a timer. Logging is uneven: some plugins log payloads and exception text in full.

**Ceilings today**

- Reloadable rules
- Cost and token metrics
- Redacted logging

**Ceilings today**

### Plugins review

The nine built-in plugin modules cover a useful set: triggers (API, one-shot, constants), routing (branch, recipient list, splitter, filter), transformation (mapper, content filter), loops, process execution, HTTP, LLM calls and chat memory, and the newer plugins are carefully written, with typed config records, explicit failure modes, port routing, output caps and good usage text. ## UI

### Evolution path

1. **Today.** A same-origin SPA served by boot. Streams and REST work with no key. Builder, plugins, history and control pages exist; unit tests run only by hand.
2. **Make it usable on a protected server.** Choose a browser auth model, make fetch and the streams carry it, and show a clear 'sign in' state instead of 'server not running'. Risks: `noAuthHeader`.
3. **Safer actions.** One idempotency key per click, no automatic retry of non-idempotent calls, per-run stop modes, a draft guard and a version check on save. Risks: `startRetryKey`, `stopAllRuns`, `noDraftGuard`, `wholeSessionSave`.
4. **Use the event model fully.** Resume streams with Last-Event-ID, switch to /api/executions/... paths and drive the Control page from the global event stream. Risks: `replayNoLastId`, `logDedupe`, `legacyAliases`, `pollControl`.
5. **Tighten the contract.** When core publishes a status enum, generate unions, take icons from plugin metadata and run the unit and type-drift checks in CI. Risks: `freeStatus`, `iconGap`, `noTestGate`, `deadSanitiser`.
6. **Close the REST gap.** Add delete, run search, paging and resume as operators ask for them (approvals and versions are done). Risks: `uiGaps`, `pagingCaps`.

## Web

### Evolution path

A suggested order, from cheap and safe to large. Each step names the risks it addresses.

1. **Today.** 16 controllers, four filters, one error handler. Loopback bind with a start-up guard, named keys with roles and session limits. Streams with ids and a heartbeat. Cursor paging over full lists. Run search, control audit and version endpoints added. Tests for every controller, mapper and filter.
2. **Close the doors.** Done: fail closed when the address is open and no key is set (but see the MCP-key case), guard the actuator. ## Workers

### Evolution path

1. **Today.** Placement by pool, free-slot choice, leases, drain, retry on another worker, optional mutual TLS, failover across several addresses. In-memory registry; plain TCP and one token by default.
2. **Make the link trustworthy.** Require TLS off loopback, per-worker credentials mapped to ids, and a decision on where secrets are resolved. Risks: `plainTokenDefault`, `sharedTokenIdentity`.
3. **Failover that works in the bad case.** Check leadership on every lease, reset the reconnect pause, close stale connections. Risks: `deposedKeepsWorkers`, `reconnectBackoff`, `staleConnections`.
4. **Make a placed node behave like a local one.** Map errors back, forward the log sink and trace context, count budgets on the control plane, enforce capacity, mark stateful plugins. Risks: `abortLostAcrossWire`, `liveLogsLost`, `noTraceContext`, `budgetPerJvm`, `capacityRace`, `statefulPlacement`, `perAttemptInit`.
5. **Handle data and upgrades.** A payload limit with a reference above it, a protocol version and a compatibility test. Risks: `payloadAsJson`, `wireVersion`.
6. **Verify the native path.** A native registration test in CI and a clear failure when the role switch is missing. Risks: `nativeUnverified`.
