<Info>
  **In plain terms:** use this when a person (or another system) must say "go ahead" before a job continues, such as approving a production deploy or a major dependency bump. The workflow stops at that step and waits. Answering its request releases it, or rejects it.
</Info>

A **signal** is the name of an answer a node waits for. The `WAIT_FOR_SIGNAL` plugin uses it for human-in-the-loop steps: it asks an input request and holds each message until the request is answered, then lets the message go on, drops it or fails, depending on the decision.

## Add a wait

```json
{
  "nodeId": "approve",
  "type": "WAIT_FOR_SIGNAL",
  "config": {
    "signal": "approve",
    "timeoutSeconds": 3600,
    "onTimeout": "FAIL",
    "onReject": "FAIL"
  }
}
```

| Option | Default | Meaning |
|---|---|---|
| `signal` | required | Name of the signal to wait for |
| `timeoutSeconds` | `3600` | Longest wait |
| `onTimeout` | `FAIL` | `FAIL` fails the node. `CONTINUE` lets the message go on with `signal.decision` set to `timeout` |
| `onReject` | `FAIL` | What to do for a `reject` decision. `FAIL` fails the node; `CONTINUE` drops the message |

Any decision other than `reject` lets the message through. The message is tagged with `signal.name`, `signal.decision` and `signal.data`, so a later [branch](/building/routing-and-branching) can route on `metadata.signal.decision`.

The engine's idle timeout for this node is the wait plus 30 seconds, so the node does not time out while it waits.

## Answer a wait

A wait is an [input request](/building/input-requests) of kind `APPROVAL` and risk `HIGH`, so only a person can answer it. List the open requests of a session and answer one by its id:

```http
GET /api/sessions/{sessionId}/inputs?state=OPEN
POST /api/executions/{executionId}/inputs/{requestId}/answer
Content-Type: application/json

{"decision": "approve", "text": "ok", "expectedVersion": 1}
```

| Field | Meaning |
|---|---|
| `decision` | Your answer, for example `approve` or `reject` |
| `text` | Optional free text; the message carries it as `signal.data` |
| `expectedVersion` | Optional; the `version` of the request you read, so a stale answer is refused |

The `signal` option of the node is the request name (`context.signal`). Answering needs the `OPERATOR` role and goes through the same ordering, review and audit as every other command. The same action is available as the MCP tool `answer_input` (list with `list_pending_inputs`), as `yukta inputs list|answer` in the CLI and as the Inputs panel on the workflow page. A request that is no longer open answers `409`.

## After a restart

The wait itself is held in memory. An answered signal is recorded with the node's checkpoint, so a [resumed](/operations/checkpoints-and-resume) execution reuses the answer for the same message instead of waiting again; this needs a file or PostgreSQL checkpoint store. A timeout is not recorded. A pending approval is not visible after a restart until its node waits again (the durable store of input requests is a PostgreSQL feature), and live waits are not carried over on a high-availability takeover.

## Limits and defaults

| Item | Value |
|---|---|
| Default wait | 3600 seconds |
| Placement | `WAIT_FOR_SIGNAL` cannot run on a remote worker |
