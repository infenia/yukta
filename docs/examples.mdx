Each example is a complete, small workflow for a common job. Find the one closest to yours, run it, then change it. They follow the same path as Yukta itself: plain automation first, then AI as a step, then AI driving the workflow.

<img className="yk-diagram block dark:hidden" src="/images/diagrams/examples-ci-gate.light.svg" alt="A CI gate: a trigger starts a command, and the command's exit code sends the run to a pass report or a fail report." loading="lazy" />
<img className="yk-diagram hidden dark:block" src="/images/diagrams/examples-ci-gate.dark.svg" alt="A CI gate: a trigger starts a command, and the command's exit code sends the run to a pass report or a fail report." loading="lazy" />

The picture above is example 03. Every example is a folder in the repository's [`examples`](https://github.com/infenia/yukta/tree/main/examples) directory with a `session.json` and a `run.sh` that applies the session, starts the run and prints `PASS` or `FAIL`.

## Run one

You need a running server, `curl`, `jq` and a copy of the repository.

```bash
git clone https://github.com/infenia/yukta.git && cd yukta
./examples/03-ci-pipeline/run.sh   # one example
./examples/run-all.sh              # all of them
```

<Note>
  Examples 01, 03, 04, 06, 07 and 08 run operating-system commands, which Yukta refuses by default. For a local trial, start the server with `YUKTA_PROCESS_ALLOW_ANY=true`. See [Security](/operations/security). Example 09 needs an LLM endpoint (OpenAI-compatible, Anthropic or Ollama). Set `YUKTA_API_KEY` if your server requires a key.
</Note>

## In the wild: Yukta checks itself

[Example 11](https://github.com/infenia/yukta/tree/main/examples/11-dogfood) is the workflow the Yukta team runs on its own code. It runs the full `gradle check` as a staged workflow. When a stage fails, a repair chain applies a formatter fix, then asks headless Claude Code for a fix, and runs the stage again. It needs a Yukta checkout and Claude Code, so it is a reference rather than a starter.
