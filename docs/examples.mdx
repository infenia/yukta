Each example is a complete workflow for a job you probably recognise: an agent that must not skip verification, a deploy that needs approval, a PR risk gate, a nightly event load that must reject bad rows. Find the one closest to yours, run it, then change it. The use-case examples are written to be copied: each README lists which nodes to change and which stand-in to swap for a model call.

Every example is a folder in the repository's [`examples`](https://github.com/infenia/yukta/tree/main/examples) directory with a `session.json` and a `run.sh` that applies the session, starts the run, answers any approval itself and prints `PASS` or `FAIL`. The examples are grouped by what they need to run.

## Categories

| Category | What you need | Examples |
|---|---|---|
| **1. Standalone** | Only the Yukta server. Allow the `sh` and `echo` commands. | Release approval, PR risk gate, dependency updates, model promotion, security findings, input pull, supervisor profiles, supervisor workflow, inbox notification, hello world |
| **2. Free dependencies** | Free tools on the machine (`git`, `python3`, `go`) or a stand-in for an outside service that the example starts itself. | Agent verification, alert triage, an MCP agent, supervisor agents |
| **3. Paid tools** | An AI agent CLI (Claude Code, Codex) or a hosted model. The examples run against a fake agent unless you configure the real tool. | Agent session walkthrough, agent console |

## Run one

You need a running server, `curl`, `jq` and a copy of the repository.

```bash
git clone https://github.com/infenia/yukta.git && cd yukta
./examples/1-standalone/03-pr-risk-gate/run.sh   # one example
./examples/run-all.sh 1                          # one category: 1, 2, 3 or all
```

<Note>
  Examples in categories 1 and 2 run operating-system commands, which Yukta refuses by default. Allow only what they need, for example `YUKTA_PROCESS_ALLOWED_COMMANDS=sh,echo`; each README names its set. Example 12 also needs `python3`; examples 18 and 19 need `git`, `uv` and `bun` or `node` (`YUKTA_PROCESS_ALLOWED_COMMANDS=git,uv,bun,node,npm` and `YUKTA_VARIABLES_ALLOWED=java.io.tmpdir`) and tell you in the inbox when one is missing. Set `YUKTA_API_KEY` if your server requires a key. See [Security](/guides/operate/secure-the-server).
</Note>

## How Yukta develops itself

The workflow the Yukta team runs on its own code lives in its own repository, [yukta-dogfood](https://github.com/infenia/yukta-dogfood). It runs the full `gradle check` as a staged workflow. When a stage fails, a repair chain applies a formatter fix, then asks headless Claude Code for a fix, and runs the stage again. It needs a Yukta checkout and Claude Code, so it is a reference rather than a starter.
