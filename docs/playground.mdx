Try a workflow before you install anything. Boxes on the path the run takes light up in order, and you can make one fail to see where the failure goes: a failure follows the error path you chose for it, and boxes on other paths stay dark.

## Try it

<Visibility for="humans">
  <WorkflowPlayground />
</Visibility>

<Visibility for="agents">
  The page shows an interactive, browser-only simulation of a Yukta workflow graph. No server is contacted and nothing is saved. Readers pick a preset, add nodes and edges, then step, pause or reset a simulated run, and can mark any node as failed to see which path the failure takes. The presets are:

  - **Linear**: `API_TRIGGER` → `HTTP_REQUEST` → `MAPPER` → `CONSOLE_TERMINAL`.
  - **Fan-out and aggregate**: a `RECIPIENT_LIST` sends each message to two `HTTP_REQUEST` nodes (ports `primary` and `backup`) and to a `CONSOLE_TERMINAL` audit log (port `audit`). An `AGGREGATE` node joins the two fetches, an `LLM_CALL` summarises them and a `NOTIFY_TERMINAL` reports the result.
  - **Error route**: `HTTP_REQUEST` (3 attempts, 200 ms backoff, `onError: ROUTE`) → `VALIDATE` → `MAPPER` → `CONSOLE_TERMINAL`. Invalid messages leave `VALIDATE` on its `invalid` port for a `rejected` terminal, and a fetch that still fails after its retries leaves on its `error` port for a `NOTIFY_TERMINAL` alert.
  - **Approval** (the default): an `LLM_CALL` classifies a ticket, `WAIT_FOR_SIGNAL` holds it until an `approve` signal arrives, then an `HTTP_REQUEST` updates the ticket. A failed classification follows its `error` edge to a dead-letter terminal.

  To build and run a real workflow, follow the [Quickstart](/quickstart).
</Visibility>

## What the simulation leaves out

<Warning>
  A green run here does not mean the real server will accept your workflow. The simulation leaves out plugin work, retries, time limits, message streams, approval waits and persistence, and a failed node fails at once and follows its `error` edge if it has one.
</Warning>
