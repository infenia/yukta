## Why Yukta exists

A lot of good work is a routine: build, test, scan, deploy; or read a request, decide, act, report. Routines carried in someone's head, or in an AI agent's prompt, work most of the time. Over hundreds of runs, small slips creep in quietly: a check skipped on a busy day, an agent that decides a step is not needed this time. Nobody notices until the result is wrong.

<Columns cols={2}>
  <Card title="Take the routine off memory" icon="list-check">
    Write the steps down once as a workflow. Yukta runs them from that definition, in order, on every run, whether a person, a script or an AI agent starts it.
  </Card>
  <Card title="Keep a hand on the controls" icon="sliders">
    Automation you cannot see into is hard to trust. In Yukta you watch every run live and can pause, step, stop, restart or retry it, down to a single node. Every command is ordered and audited.
  </Card>

## What a workflow looks like

A workflow is a flowchart written as JSON: a **directed acyclic graph (DAG)** of boxes joined by arrows. It can be three boxes or hundreds, with branches, fan-out, joins, retries and sub-workflows, and because it has no cycles it can never loop back by accident. Here, a job fetches data, tidies it up and sends a notification. If the call fails, the item is set aside for later.

<img className="yk-diagram block dark:hidden" src="/images/diagrams/workflow-anatomy.light.svg" alt="A trigger starts the flow, two processors call an API and transform the result, and terminals end each branch. A failed call goes to a dead-letter terminal." loading="lazy" />
<img className="yk-diagram hidden dark:block" src="/images/diagrams/workflow-anatomy.dark.svg" alt="A trigger starts the flow, two processors call an API and transform the result, and terminals end each branch. A failed call goes to a dead-letter terminal." loading="lazy" />

| Box | What it does | Example |
|---|---|---|
| **Trigger** | Starts the job | A request arrives, a timer fires |
| **Processor** | Does work or makes a choice | Run a command, call a web service, reshape data, ask an AI model |
| **Terminal** | Ends a path | Log the result, send a notification, keep a failed item |

The arrows are **edges**: "when this step is done, hand its output to the next." A step can have labelled exits, called **ports**, such as `success` and `error`, so good and bad outcomes take different paths. Each box is a **plugin**, a ready-made capability you configure, and you can [write your own](/plugins/writing-a-plugin) and add it at any time.

## What you can build

Start with plain automation and add AI only where it earns its place. The same engine, controls and audit trail carry you all the way.

<CardGroup cols={2}>
  <Card title="Pipelines that never skip a gate" icon="code-branch" href="/examples">
    Build, test, scan and deploy as plain command steps, routed on exit codes. Every gate runs on every change, and a failure stops the line. No AI required.
  </Card>
  <Card title="Pipelines that fix their own failures" icon="wand-magic-sparkles" href="/building/ai-and-agents">
    Put an AI step on the failure path. It reads the error, applies a fix and hands back to the check, with a fixed number of attempts so it can never spin forever.
  </Card>
  <Card title="Agents that work as a team" icon="users" href="/building/ai-and-agents">
    One agent drafts, another reviews, a third decides. Each is a step in the graph, so every hand-off is visible and any step can be restarted on its own.
  </Card>
  <Card title="Automation that keeps itself on track" icon="shield-halved" href="/running/supervisors">
    A supervisor watches every event and pauses or stops a run that loops or drifts. Use rules for what you can spell out, and a System One decision model or an LLM for the rest.
  </Card>
</CardGroup>

</Info>
