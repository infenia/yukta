Yukta runs **workflows**: graphs of small steps that pass messages to one another. You describe a workflow as JSON, store it on the server, and start it from anywhere that can make an HTTP request. While it runs you can watch it live, pause it, skip a step, approve a decision, retry a failure or stop it.

</Note>

## What a workflow looks like

<img className="yk-diagram block dark:hidden" src="/images/diagrams/workflow-anatomy.light.svg" alt="A trigger starts the flow, two processors call an API and transform the result, and terminals end each branch. A failed call goes to a dead-letter terminal." loading="lazy" />
<img className="yk-diagram hidden dark:block" src="/images/diagrams/workflow-anatomy.dark.svg" alt="A trigger starts the flow, two processors call an API and transform the result, and terminals end each branch. A failed call goes to a dead-letter terminal." loading="lazy" />

A **trigger** starts the flow, **processors** transform, route and call out, and **terminals** end each branch. Processors can have named output ports such as `success` and `error`, so one node can send messages down different paths.

## Why Yukta

<CardGroup cols={2}>
  <Card title="Workflows are data" icon="diagram-project">
    A workflow is a JSON graph. There is no language to learn, and a graph is easy for people, tools and AI agents to generate, diff and review.
  </Card>
  <Card title="One definition, many callers" icon="plug">
    Start the same workflow from the REST API, the web UI, the command-line client or an MCP client such as Claude.
  </Card>
  <Card title="Streaming, with back-pressure" icon="bolt">
    Messages stream through the graph. A slow node slows the nodes feeding it, so memory stays bounded without queues between steps.
  </Card>
  <Card title="Observable and steerable" icon="gauge">
    Live graph view, log and status streams, and run controls: pause, resume, step, breakpoints, skip, retry, restart and stop.
  </Card>
  <Card title="Failure is a first-class path" icon="shield-halved">
    Retries with backoff, error routing to dead-letter nodes, failure budgets and five independent time limits are built in around every node.
  </Card>
  <Card title="Safe to start with" icon="lock">
    The server listens on loopback only, refuses to run operating-system commands until you allow them, and requires an API key before it accepts remote connections.
  </Card>
</CardGroup>

## What it is good for

- **CI/CD and quality gates:** run build and test stages, route on exit codes, stop a pipeline on failure.
- **Data pipelines:** split a batch, filter, map and load, with retries and dead letters.
- **Operations automation:** health checks with alert paths, scheduled jobs, fan-out notifications.
- **AI agents:** model calls, tool use over MCP, per-user memory, approval steps and budgets that stop runaway loops.
