<Info>
  **In plain terms:** rule files let you write that safety net as data: "when this happens, do that" (a reaction) or "never allow this command" (a veto). Yukta checks the file when it loads, so a typo is caught before it can cause trouble.
</Info>

A rule file is a JSON document with a `rules` list. Each rule is either a **reaction** (`when` an event matches, `then` send a command) or a **veto** (`deny` a command). Rules are checked when the file is loaded, so a mistake such as an invalid condition or an unknown command stops the server from using the file and reports which rule is wrong.

```json
{
  "rules": [
    {
      "id": "pause-on-repeated-http-failure",
      "when": {
        "event": "NodeStatusChanged",
        "status": "FAILURE",
        "module": "HTTP_REQUEST",
        "count": 3,
        "withinSeconds": 60
      },
      "then": { "command": "PauseWorkflow" }
    },
    {
      "id": "stop-node-on-server-error",
      "when": { "event": "NodeStatusChanged", "status": "FAILURE", "if": "metadata['code'] == 500" },
      "then": { "command": "StopNode", "immediate": true, "reason": "server error" }
    },
    {
      "id": "no-kill",
      "deny": { "command": "StopWorkflow", "if": "mode == 'KILL'", "reason": "use DRAIN or CANCEL" }
    }
  ]
}
```

## Rule fields

| Field | Meaning |
|---|---|
| `id` | Names the rule in logs and errors |
| `when` | The events that trigger a reaction |
| `then` | The command to send when triggered, or the answer or escalation of an input request |
| `deny` | A command to refuse. A rule has either `when` and `then`, or `deny`, or `requireApproval` |
| `requireApproval` | A command to hold until someone approves it |

## `when`: which events

Every field you set must match. Omit a field to match any value.

| Field | Meaning |
|---|---|
| `event` | `NodeStatusChanged`, `WorkflowStatusChanged`, `ControlOutcome`, `LogLine`, `EventsMissed`, or an input request event: `InputRequested`, `InputEscalated`, `InputAnswered`, `InputExpired`, `InputCancelled` |
| `status` | The status, for status events, for example `FAILURE` |
| `module` | The node's plugin type, for node events, for example `HTTP_REQUEST` |
| `nodeId` | A specific node, for node and log events |
| `workflowId` | A specific workflow, for status events |
| `if` | A condition expression over the event's fields |
| `count` | How many matching events trigger the rule. Default `1` |
| `withinSeconds` | The window in which `count` events must occur, counted per execution. Default `60` |

### Event fields available to `if`

| Event | Fields |
|---|---|
| All events | `executionId` |
| `NodeStatusChanged` | `workflowId`, `nodeId`, `module`, `status`, `metadata` (a map, for example `metadata['code']`) |
| `WorkflowStatusChanged` | `workflowId`, `status` |
| `ControlOutcome` | `command`, `actor`, `applied`, `reason` |
| `LogLine` | `nodeId`, `line`, `level` (`DEBUG`, `INFO`, `WARN` or `ERROR`) |
| `InputRequested`, `InputEscalated` | `sessionId`, `workflowId`, `nodeId`, `requestId`, `status` (`INPUT_REQUESTED` or `INPUT_ESCALATED`), `kind`, `risk`, `state`, `tier`, `prompt`, `context` (a map: `context['environment']` or `context.environment`), `options` (the option ids), `requesterType` (the asking plugin, such as `ASK_INPUT`; also `requester`), `advice`; and `reason` for `InputEscalated` |
| `InputAnswered` | `workflowId`, `requestId`, `decision`, `responder`, `responderType` |
| `InputExpired`, `InputCancelled` | `workflowId`, `requestId`; and `reason` for `InputCancelled` |

Every event also has `sessionId`. The prompt and context of a request were written by the asking step, often an AI agent: compare them, but do not base an approval on their claims alone. `context['key']` is `null` when the key is missing; `context.key` cannot be evaluated then, so the condition does not match.

A condition that cannot be evaluated counts as not matching, so a faulty reaction never fires.

## `then`: which command

| Field | Meaning |
|---|---|
| `command` | `PauseWorkflow`, `ResumeWorkflow`, `StopWorkflow`, `PauseNode`, `ResumeNode`, `StopNode`, `Restart` or `RestartFromNode`. Node commands address the node that triggered the rule |
| `mode` | For `StopWorkflow`: `DRAIN` (default), `CANCEL` or `KILL` |
| `reason` | Recorded with a stop. Default `Stopped by rule` |
| `immediate` | For `StopNode`: interrupt instead of draining |
| `from` | For `RestartFromNode`: the node to restart from, as a literal or `metadata.<key>` of the event (for example `metadata.restartFrom` of an [`OUTCOME_TERMINAL`](/plugins/terminals)). `START`, or a key the event lacks, restarts the whole run. Default: the node that triggered the rule |

The command is addressed to the execution that produced the event. A restart starts a new run (the rule engine picks its id), and that run's events see `attempt`, the number of restarts the rules made to get there (0 for a run nobody restarted). Use `"if": "attempt < 2"` to bound a retry loop; when the budget is spent the rule stays silent and the last outcome is the signal for whoever watches the event stream. The count lives in memory (the newest 1,000 restarted runs): after a server restart, or once a chain has been pushed out by 1,000 newer restarts, it starts again at 0, so a retry chain gets a fresh budget.

## Answer and escalate input requests

Instead of a `command`, a rule's `then` can hold `answer` or `escalate`, which act on the [input request](/building/input-requests) of an `InputRequested` or `InputEscalated` event. Such a rule must name one of these events in `when.event`, or name none (it then matches only these two). A rule has exactly one of `command`, `answer` and `escalate`.

```json
{
  "rules": [
    {
      "id": "approve-low-risk-staging",
      "when": { "event": "InputRequested", "if": "risk == 'LOW' and context['environment'] == 'staging'" },
      "then": { "answer": { "decision": "approve", "rationale": "policy 7: low risk deploys", "confidence": 1.0 } }
    },
    {
      "id": "escalate-the-rest",
      "when": { "event": "InputRequested", "if": "not (risk == 'LOW' and context['environment'] == 'staging')" },
      "then": { "escalate": { "reason": "not covered by policy 7", "advice": "check the target environment" } }
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `answer.decision` | Required. The decision; for `APPROVAL` with options and for `CHOICE` it must be one of the request's option ids, or the answer is refused |
| `answer.text` | Free text, for `TEXT` requests |
| `answer.rationale` | Why. Recorded as `rule <id>: <rationale>` |
| `answer.confidence` | From 0 to 1. Default `1` |
| `escalate.reason` | Why it is handed up. Default `escalated by rule <id>` |
| `escalate.advice` | A recommendation for whoever answers next |

The answer names the version of the request the rule saw, so it is refused if the request changed in between. The server decides whether the answer counts: the supervisor needs a profile with `canAnswer: true` and a `maxRisk` that reaches the request's risk, and a request of risk `HIGH` is answered by people only. A rules file set with `yukta.supervisor.rules.file` or `yukta.control-plane.rules.file` can therefore escalate but never answer: attach the rules as a [profile](/running/supervisors#answer-input-requests) instead. When the rules contain an `answer` and the supervisor may not answer, a warning naming the rules is logged when they are loaded; their answers are denied and counted in `yukta.input.denied{rule}`.

Answer and escalation fields are checked when the rules are loaded: a missing `decision`, a confidence outside 0 to 1, an unknown field or an `answer` on another event kind stops the file from loading.

## `deny`: which commands to refuse

A deny rule makes the rule engine act as a [reviewer](/running/supervisors): matching commands are refused before they run.

| Field | Meaning |
|---|---|
| `command` | The command name, with or without the `Command` suffix, for example `StopWorkflow` |
| `if` | A condition over the command's fields. Omit it to always refuse |
| `reason` | Shown to the caller. Default `denied by rule <id>` |

Command fields available to `if`: `executionId`, `actor`, `nodeId`, `mode`, `reason` and `immediate`.

A deny condition that cannot be evaluated **refuses** the command, so a faulty rule never lets a forbidden command through.

## `requireApproval`: which commands to hold

A `requireApproval` rule parks matching commands until an input request is approved (see [Ask for approval](/running/supervisors#ask-for-approval)). A deny rule still wins over it.

| Field | Meaning |
|---|---|
| `command` | The command name, as in `deny` |
| `if` | A condition over the command's fields, which also include `workflowId`. Omit it to always ask |
| `risk` | `LOW`, `MEDIUM` or `HIGH`. Default `HIGH`, which only a person can approve |
| `route` | The input route that decides. Default: the default route |
| `reason` | Shown to whoever approves. Default `approval required by rule <id>` |

```json
{ "id": "prod-stop", "requireApproval": { "command": "StopWorkflow", "if": "workflowId == 'prod-deploy'", "risk": "HIGH", "reason": "production stop" } }
```

A bad `risk` or `route` stops the file from loading.

## Enabling a rule file

| To use it as | Set |
|---|---|
| A supervisor | `yukta.supervisor.rules.file` |
| A control plane | `yukta.control-plane.rules.file` |

Both read the same format.
