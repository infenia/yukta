<Info>
  **In plain terms:** a supervisor is an automatic operator that watches every run and steps in when something looks wrong, for example pausing a workflow after repeated failures. It is optional and off until you turn it on.
</Info>

A **supervisor** watches the live event feed of all executions and returns commands: pause a workflow after repeated failures, stop a node that returns a server error, refuse a dangerous stop. Supervisors are optional and off until you enable one.

## Choose a supervisor

A supervisor can be as simple as a few rules or as capable as an AI agent. Pick by how well you can describe the situations it should handle:

| Supervisor | Decides with | Use it when | See |
|---|---|---|---|
| Rule supervisor | A JSON rules file | You can state the situations and responses exactly | [Rule files](/running/rule-files) |
| Model control plane | A decision model: a System One model, or any LLM | You can describe the situations only in words | [Control planes](/running/control-planes#model-control-plane) |
| Rules-first control plane | Rules, then the model when no rule fired | Exact cases come first, the model covers the long tail | [Control planes](/running/control-planes#rules-first-control-plane) |
| An AI agent outside the server | Any agent that reads the event stream and sends commands over MCP or REST | You want open-ended judgement, or a person and an agent sharing the controls | [Supervisors outside the server](#supervisors-outside-the-server) |
| Your own code | A supervisor or control plane you write | None of the above fits | [Writing a plugin](/plugins/writing-a-plugin) |

All of them send commands through the same ordered, reviewed and audited pipeline as a person does, so a supervisor can never do anything you could not see afterwards.

## What a supervisor can do

- **React to events.** Receive every event (a node changed status, a workflow changed status, a command was applied or rejected, a log line was written) and answer with commands.
- **Veto commands.** A **reviewer** can refuse any command, from a person or a program, before it runs. The first refusal wins, and a reviewer that errors refuses. The caller gets `403` and the log records the rejection.

- **Limit what it watches.** A supervisor has a **scope**: all runs (the default), the runs of one session, or the runs of one workflow. It sees only the events of runs in its scope and is asked to review only their commands. A command that belongs to no run, such as changing the scheduler limits, is reviewed by global supervisors only. `GET /api/supervisors` reports each supervisor's `scope`, `scopeSessionId` and `scopeWorkflowId`.

Commands sent by a supervisor go through the same ordered, reviewed, audited pipeline as everyone else's. They are logged and audited with the supervisor's id as the actor.

## The built-in rule supervisor

The rule supervisor reads a JSON rules file. Enable it by setting the path:

```properties
yukta.supervisor.rules.file=/etc/yukta/rules.json
```

The rule format is in [Rule files](/running/rule-files).

## Safety

A supervisor can never hold up an execution:

| Protection | Behaviour |
|---|---|
| Failure isolation | A failing supervisor is resubscribed with backoff |
| Rate limit | At most `yukta.supervisor.max-commands-per-second` commands (default `20`) |
| Dry run | `yukta.supervisor.dry-run=true` records commands without applying them |
| No feedback loop | A supervisor never sees the outcome of its own commands |
| Slow consumers | Events reach a supervisor through a buffer (`yukta.supervisor.buffer-size`, default 10,000). Only when it overflows are events dropped (counted in `yukta.tracker.dropped` with `kind=supervisor`) instead of slowing the engine, and the supervisor then receives an `EventsMissed` event with the count |

Event delivery is best effort, but a gap is never silent: a rule that must not miss a case should treat `EventsMissed` (rule field `status=EVENTS_MISSED`, `missed` = count) as a reason to check the execution log or fail safe (for example pause). The notice arrives with the next event after the gap. Commands are rate limited, but a supervisor can still react to the state changes its own commands cause.

## Supervisors outside the server

You do not need to write code inside the server. The event feed is also a server-sent events stream, and external agents steer through the REST control endpoints or the MCP tools:

```http
GET /api/events/stream?executionId={id}&type={type}
```

## Inspect what is installed

```http
GET /api/supervisors
```

This reports every supervisor and control plane: its kind (`SUPERVISOR` or `CONTROL_PLANE`), order, dry-run flag and command counts. The web UI's Control page shows the same.

## Settings

| Setting | Default | Meaning |
|---|---|---|
| `yukta.supervisor.rules.file` | unset | Enables the rule supervisor and sets its rules file |
| `yukta.supervisor.max-commands-per-second` | `20` | Rate limit per supervisor |
| `yukta.supervisor.dry-run` | `false` | Record commands without applying them |
