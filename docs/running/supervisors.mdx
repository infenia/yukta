<Info>
  **In plain terms:** a supervisor is the one that is in charge of some part of your runs. It watches them, steps in when something looks wrong, and decides whether people may steer that part directly. It is optional: with no supervisor, people control everything, as before.
</Info>

A **supervisor** has two layers. The shell is what Yukta enforces: what it **owns** (its assignments), who it **reports to** (its parents), what it may send (`allowedCommands`, `initiative`) and whether people may steer through it (`operatorAccess`). The **engine** decides: it reads signals and returns directives, and the supervisor checks each one before it has any effect. See [Supervisor engines](/running/supervisor-engines) for the engines and the [supervisor contract](/running/supervisor-contract) for the rules.

All commands, a supervisor's and a person's, go through the same ordered, reviewed and audited pipeline, so nothing a supervisor does is hidden.

## Choose an engine

| Engine | Decides with | Use it when |
|---|---|---|
| `rules` | A JSON rules file; presets `failure-guard`, `stall-watchdog`, `approval-gate` | You can state the situations and responses exactly ([Rule files](/running/rule-files)) |
| `http` | An external system or AI agent: Yukta posts it each signal (`url`) or it reads them from `/api/agent/v1`, and it decides there | The logic lives in another service, or you want open-ended judgement |
| `workflow` | A workflow in an internal session | The decision should be visible and editable as a workflow |
| `process` | A program on the server | A script or binary already decides |

The model and rules-first control planes of earlier versions are gone. A stored supervisor of those types stays stored, does not start, and is named in a warning at start-up; use an `http` supervisor that calls your model.

## What a supervisor owns

An **assignment** says what a supervisor owns. The units are a node, the run level of a workflow, and the server.

| Target (text form) | Owns |
|---|---|
| `server` | Server-wide commands: scheduler limits, drain, recover |
| `session:<id>` | Every workflow of the session, run level and nodes |
| `workflow:<s>/<w>` | The run level and all nodes of one workflow |
| `run:<s>/<w>` | The run level only: start, pause, resume, stop, restart, priority |
| `workflow:<s>/<w>//<selector>,...` | Some nodes: a node id, `<prefix>.*`, or `group:<stage>` (the `group` a node declares, else the part of its id before the first dot) |

**One owner per unit.** A save that would give a unit to two supervisors is refused with `409 OWNERSHIP_CONFLICT`, naming the other supervisor and the units. Nothing is inherited and nothing is overridden: to give one node to a specialist, stop the main supervisor's assignment covering it first. A workflow definition that makes two selectors take one node is refused too. A `global` assignment owns nothing; it only observes.

**Units nobody owns** go to the default supervisor, which lets people act as before. `yukta.supervisor.default.enabled=false` turns that off, so each workflow must name its supervisor.

**People and owners.** A person's command goes to the owner of the unit. The owner's `operatorAccess` (a list of command names, default none) says which commands a person may send through it; any other is `409 CONTROLLED_BY_SUPERVISOR` naming the supervisor. A listed command is reviewed by the owner's engine. Reading is unrestricted. `GET /api/supervision` tells a client which commands are allowed before it sends them. `GET /api/supervision/summary` counts the workflows nobody owns (the default supervisor carries their run level and every node; internal sessions left out, the first 100 named) and the assignments start-up disabled as conflicts; the Control page's Supervisors tile shows both.

```bash
# the supervisor first, then what it owns
curl -X POST http://localhost:9858/api/supervisors -H 'Content-Type: application/json' -d @build-guard.json
curl -X POST http://localhost:9858/api/supervisors/build-guard/assignments/check -H 'Content-Type: application/json' \
  -d '[{"target":"workflow:s1/release//build.*"}]'
curl -X PUT  http://localhost:9858/api/supervisors/build-guard/assignments -H 'Content-Type: application/json' \
  -d '[{"target":"workflow:s1/release//build.*","locked":true}]'
```

A **locked** assignment changes only when the request asks to `unlock`, and only by a key listed in `yukta.supervisor.lock-holders` when that list is set. Setting assignments checks everything first and changes nothing if a check fails. `GET /api/supervisors/assignments?session=&workflow=` lists them; those from definitions (`DEFINITION`) and the server (`SYSTEM`) change only where they come from.

### Two supervisors on two stages

A release workflow `release` in session `s1` builds (`build.compile`, `build.test`) and deploys (`deploy.staging`, `deploy.prod`). One supervisor owns the build, another the deploy, a third the run level:

```json
{ "build-guard":   [{ "target": "workflow:s1/release//build.*" }],
  "deploy-guard":  [{ "target": "workflow:s1/release//deploy.*" }],
  "release-guard": [{ "target": "run:s1/release" }] }
```

`build-guard` may pause, skip or step the build nodes; a `PauseNodeCommand` it sends for `deploy.prod` is `not-owned`. A person pausing `deploy.prod` is reviewed by `deploy-guard` only; a person stopping the run is reviewed by `release-guard` only.

## Reporting to parents

A supervisor lists `parents` (zero or more; no cycle, at most four levels). When its own command needs approval, the parents are asked first, in the `delegation` mode for `APPROVAL`: `ORDERED` (default: one after the other, the first answer decides), `ALL` (all must allow) or `ANY` (the first answer decides). A refusal from any parent asked is final; when nobody decides, a person does. A parent needs no assignment. For input requests the route decides instead: the tier `supervisor:parent` sends an escalated request to the parents of the supervisor that escalated, with the tier's own mode, quorum and timeout (`CONSULT` questions are asked in their own mode, see the [contract](/running/supervisor-contract)). A supervisor approves another's parked command only from above it in the hierarchy, and never a `HIGH` risk request.

## Ask for approval

A review can also answer "yes, but only after someone approves". A custom supervisor returns `Decision.requireApproval(reason, new ApprovalNeed(risk, route, ttl))`; a `rules` supervisor has a `requireApproval` rule (see [Rule files](/running/rule-files)).

The command is not run and not refused. The server parks it in memory and raises an input request of kind `APPROVAL` (options `approve` and `reject`, risk `HIGH` unless the need says otherwise, so a person must answer) through the usual route. The server writes the prompt; the reviewer's reason is quoted as data. The caller does not wait: REST answers `202 Accepted` with `{"status": "AWAITING_APPROVAL", "requestId": "..."}`, and a supervisor's decision list shows `outcome=awaiting-approval` with the request id. The same command sent again while the request is open gets the same request.

- **Approved:** the command is sent again with its original sender. The supervisors that asked are satisfied for it; the owner reviews it again and a denial still applies. The run may have moved on, in which case the command fails as usual.
- **Rejected, expired or cancelled (the run ended):** the command is dropped, the log records `CONTROL_REJECTED` with the request id, and a `ControlOutcome` event is published.
- **Stops:** a stop sent by a person is never parked: it runs with a warning, as when a review times out. A stop proposed by a supervisor can be parked.
- **Who can approve:** not the sender of the command and not a supervisor that asked. A supervisor approves another supervisor's command only from above it in the hierarchy, and never a `HIGH` risk request.
- **Limits:** parked commands count against the open request caps (5 per run, 50 per session). They live in memory: a restart cancels the requests and the commands are not replayed. `yukta.control.approval.ttl` (default `10m`, never above `yukta.input.max-ttl`) is how long a request waits. Metric: `yukta.control.approval{outcome=requested|approved|rejected|expired|cancelled}`.


## The Supervisors page

`/supervisors` in the web UI is the home of supervisors (the Control page keeps a summary tile). **Catalog** lists the engines with their settings and an example; **Create supervisor** is a wizard that checks the settings before it saves. **Supervisors** lists what you configured and what the server configures itself (read-only, source `SYSTEM`); a supervisor's page shows its settings, what it owns and its decisions. **Decisions** shows what became of the newest commands. A session or workflow page shows **Supervision**: who owns what there.

## Declare ownership in a definition

A session or a workflow names its supervisors in an `assignments` block. They own what is declared from the moment the definition is saved, so imports, templates, MCP-created sessions and every saved version carry them.

```json
{
  "sessionId": "s1",
  "workflows": {
    "release": {
      "workflowId": "release",
      "assignments": [
        { "supervisor": "deploy-approval", "nodes": ["deploy.*"] },
        { "supervisor": "stall-watch", "enabled": false }
      ],
      "nodes": [ ... ],
      "edges": [ ... ]
    }
  }
}
```

- A session-level block covers the whole session. A workflow-level block covers the whole workflow, or only the listed `nodes` (ids, `<prefix>.*` or `group:<name>`). `enabled: false` declares it and keeps it off.
- The supervisor must exist when the definition is saved (an unknown one is refused with the field, `workflows.release.assignments[0].supervisor`), and the one-owner rule runs first: a definition that would give a node to a second supervisor is refused with `409` naming the other. A supervisor that a definition names cannot be deleted.
- The definition is the truth: saving takes up what is declared (source `DEFINITION`) and releases what is no longer declared, and never touches assignments made by hand. A declaration that cannot start right now is logged and retried at the next save.
- Rolling back a workflow version checks ownership with the restored version in place.

## Manage supervisors while the server runs

- `GET /api/supervisor-engines[/{type}]` lists the engines and gives the settings schema, default commands and an example; `/{type}/presets` the ready-made documents. `POST /api/supervisors/validate` checks a draft, including overlap, without saving.
- `PUT /api/supervisors/{id}` saves (admin key). Settings are checked against the engine: an unknown key or a wrong type is `400` with a `settings.<key>` field. A setting sent back as `***` keeps its stored secret. Saving restarts the supervisor. A supervisor that owns something, that a definition names, or that others report to cannot be deleted.
- Ids match `[A-Za-z0-9._-]{1,64}`: no `:` and no whitespace, so an id never looks like an actor such as `key:admin`.
- Settings can limit and empower the shell: `allowedCommands` (a supervisor sends nothing until it names some), `initiative` (the commands it may send with no triggering signal, default none, with `maxInitiativePerMinute`, default 10), `operatorAccess`, `canAnswer` (default `false`), `maxRisk` (`LOW`, `MEDIUM`; a `HIGH` request is answered by people only), `readNodeOutputs` (default `false`).
- `GET|PUT /api/supervisors/{id}/engine/rules` reads and replaces the rules document of a `rules` supervisor (its other settings stay). `GET /api/supervisors/{id}/versions` and `POST .../rollback?version=` use the newest 20 saved states (kept in PostgreSQL when configured); `POST .../replay` shows what rules would have done on a past run, in dry run.
- At most `yukta.supervisor.max-attachments` assignments (default 200). Changes are recorded in the execution log under the run id `supervisors`, with the caller as actor. Settings under secret-looking keys (`key`, `secret`, `token`, `password`) read as `***`.
- Supervisors and assignments are kept in memory and are gone after a restart, unless the server uses PostgreSQL (`yukta.session.store-type=postgres`).
- `GET /api/supervisors/decisions?supervisor=&limit=` lists what became of the newest commands since startup (`applied`, `rejected`, `dry-run`, `rate-limited`, `forbidden`, `not-owned`, `reason-required`, `initiative-not-allowed`, `precondition-failed`), newest first, at most 500. `GET /api/supervisors/status` shows what runs.
- The MCP tools `list_supervisor_engines`, `get_supervisor_engine`, `list_supervisors`, `get_supervisor`, `save_supervisor`, `check_assignment`, `set_assignments`, `delete_supervisor` and `get_supervision` do the same for agents; the CLI has `yukta supervisors ...`.

## Presets of the rules engine

`failure-guard`, `stall-watchdog` and `approval-gate` are ready-made rule documents (`GET /api/supervisor-engines/rules/presets`), filled in with a few parameters. Supervisors of those types stored by earlier versions become `rules` supervisors at start-up.

### `failure-guard`

Acts after nodes failed a number of times within a window, counted per run: `failures` (3), `withinSeconds` (60), `nodes` (all), `errorContains` (any), `action` (`PAUSE_WORKFLOW`, `STOP_WORKFLOW` or `PAUSE_NODE`). It may send only the command of its action.

### `stall-watchdog`

Acts on a node that has run too long or written no log line for a while: `maxRunningSeconds`, `maxSilenceSeconds` (at least one), `nodes`, `action` (`PAUSE_NODE`, `STOP_NODE`, `PAUSE_WORKFLOW`, `STOP_WORKFLOW`), `once` (true). It is a timed rule, so it acts on its own: its command must be in the supervisor's `initiative` list.

### `approval-gate`

Holds the chosen commands (`StopWorkflowCommand`, `RestartCommand`, `RestartFromNodeCommand`, `SkipNodeCommand`, `StopNodeCommand`, `SetLimitsCommand`) until a person approves them: `commands` (required), `nodes`, `risk` (`HIGH`: only a person), `route`, `ttl`, `reason`. A stop sent by a person is never held, so a person can always stop a run (it runs with a warning); the gate holds what supervisors send and the other commands of a person.

## Answer input requests

An [input request](/building/input-requests) is a question a running step or AI agent asks. Supervisors receive it as an `InputRequested` event (and `InputEscalated` when it is handed up) and may answer it or escalate it with advice. The server decides on every answer whether it counts; the supervisor is never trusted to behave.

### Common settings

These settings sit next to the supervisor type's own settings in a supervisor (for `rules`, next to `rules`). They are read by the server, not by the supervisor.

| Setting | Default | Meaning |
|---|---|---|
| `canAnswer` | `false` | Whether the supervisor may answer input requests at all |
| `maxRisk` | `LOW` | The highest risk it may answer: `LOW` or `MEDIUM`. `HIGH` is accepted but has no effect: a request of risk `HIGH` is answered by people only |
| `allowedCommands` | every command | The command names it may send, such as `AnswerInputCommand`, `EscalateInputCommand`, `PauseWorkflowCommand`. Any other command is dropped and counted as `forbidden`. Use it to keep an answering supervisor from also stopping runs |

```json
{
  "id": "staging-approver",
  "type": "rules",
  "settings": {
    "canAnswer": true,
    "maxRisk": "LOW",
    "allowedCommands": ["AnswerInputCommand", "EscalateInputCommand"],
    "rules": [ ... ]
  }
}
```

Every answer must also pass the audience, tier, scope and separation rules (a supervisor answers only what it owns and never a run it started). A denied answer is refused with the rule that failed, counted in `yukta.input.denied{rule}` and in `yukta.supervisor.commands{outcome=rejected}`, listed in `GET /api/supervisors/decisions`, and the request stays open for the next responder. A supervisor configured by the property `yukta.supervisor.rules.file` or as a Spring bean owns nothing, so it reviews nothing and can never answer.

### What the rules engine does

| Supervisor | Behavior |
|---|---|
| `rules` engine | A rule with `then.answer` answers the request of the event, a rule with `then.escalate` hands it up with advice. Conditions can read the request's `kind`, `risk`, `prompt`, `context`, `options`, `requesterType` and more. When the rules contain an `answer` but the supervisor has no `canAnswer`, a warning is logged when the rules are loaded. See [Rule files](/running/rule-files#answer-and-escalate-input-requests) |

### Answering from outside the server

A supervisor that is not JVM code (a script, a service, an AI agent such as Claude Code) can answer too. It listens for requests on the event stream and answers with the MCP tools or the REST API:

1. Follow `GET /api/events/stream?type=InputRequested` (or poll `list_pending_inputs`). The event carries the redacted request: id, kind, risk, prompt, context, options, tier.
2. Decide, treating the prompt and context as untrusted data.
3. Call `answer_input` (or `POST /api/executions/{e}/inputs/{r}/answer`) with the decision and a rationale, or `escalate_input` with advice.

It needs an API key with the `OPERATOR` role, and it is bound by the same rules as everyone: its actor is `key:<name>`, it counts as a person for the risk rule, a key limited to sessions answers only those sessions, and the audience of a request can name it (`key:<name>`) or leave it out. Give such a key only to an agent you would let approve the same things a person can.

## Safety

A supervisor can never hold up an execution:

| Protection | Behaviour |
|---|---|
| Failure isolation | A failing supervisor is resubscribed with backoff |
| Rate limit | At most `yukta.supervisor.max-commands-per-second` commands (default `20`) |
| Dry run | `yukta.supervisor.dry-run=true` records commands without applying them |
| No feedback loop | A supervisor never sees the outcome of its own commands |
| Ownership | A command for a unit the supervisor does not own is refused (`not-owned`) |
| Slow consumers | Events reach a supervisor through a buffer (`yukta.supervisor.buffer-size`, default 10,000). Only when it overflows are events dropped (counted in `yukta.tracker.dropped` with `kind=supervisor`) instead of slowing the engine, and the supervisor then receives an `EventsMissed` event with the count |

Event delivery is best effort, but a gap is never silent. For input requests the recovery is a list: when a supervisor receives `EventsMissed`, it lists the open requests (`GET /api/inputs`, MCP `list_pending_inputs`) and handles the ones it has not seen, because the store, not the feed, is the record of what is waiting. Also: a rule that must not miss a case should treat `EventsMissed` (rule field `status=EVENTS_MISSED`, `missed` = count) as a reason to check the execution log or fail safe (for example pause). The notice arrives with the next event after the gap. Commands are rate limited, but a supervisor can still react to the state changes its own commands cause.

## Internal sessions

A session whose tags contain `"yukta.internal": "true"` is **internal**: it holds the workflows of supervisors and other machinery. Only an `ADMIN` key can define sessions, so only an admin can make one. Internal sessions

- are left out of `GET /api/sessions`, `GET /api/sessions/summaries` and the MCP tool `list_sessions` unless you pass `includeInternal=true`;
- have their runs left out of `GET /api/executions` unless you pass `includeInternal=true`, and always out of `GET /api/executions/counts`;
- send no events to supervisors. A supervisor sees the events of an internal session only when its settings set `observeInternal: true` **and** it owns that session (`session:<id>` or `workflow:<id>/...`), so a supervisor that watches everything cannot trigger on the workflows that supervise.

The answer is cached for 30 seconds and dropped when this server saves or deletes the session. A session that cannot be read counts as internal.

## Workflow supervisors

A supervisor of type `workflow` makes a supervisor out of a workflow in an [internal session](#internal-sessions). For each event of a listed type the server starts the workflow with the event (secrets masked), the request if the event has one, and the supervisor id, then reads how it ended. See `examples/17-supervisor-workflow`.

| Setting | Meaning |
|---|---|
| `sessionId` | An internal session; checked when the supervisor is saved and before each run |
| `workflowId` | A workflow of that session; must exist when the supervisor is saved |
| `events` | Event types that start it, such as `InputRequested` |
| `maxConcurrent` | Runs of this supervisor at once; default 2, at most the reserved slots |
| `timeout` | Seconds one run may take, 1 to 600; default 60 |
| `when` | Optional read-only SpEL condition over the event (secrets masked), for example `request.spec.risk == 'LOW'`. The run starts only when it holds; a condition that cannot be evaluated does not match. A condition that is not valid SpEL is refused when the supervisor starts |
| `allowedCommands`, `canAnswer`, `maxRisk` | As for any supervisor. A workflow supervisor may send **no** command until `allowedCommands` names some |

How the run ends decides what happens: `SUCCESS` with `{"commands": [...]}` sends them (at most 10 per run), `ESCALATE` hands the request in the event up with the reason as advice, `RETRY` runs once more, and a failure, a timeout or a result that cannot be read is no opinion (`yukta.supervisor.workflow{outcome}`). `AnswerInput`, `EscalateInput`, `PauseWorkflow`, `ResumeWorkflow`, `PauseNode`, `ResumeNode` and `SetPriority` can always be mapped; `StopWorkflow`, `StopNode`, `SkipNode`, `Restart`, `RestartFromNode`, `SetLimits` and `SetBreakpoint` only when `allowedCommands` names them; other types are dropped. The commands still pass the ownership check, `allowedCommands` and the answer rules.

Guards against loops and deadlocks:

- Events of internal sessions do not reach supervisors unless the supervisor sets `observeInternal`.
- A run carries `yukta.supervisor.depth` and `yukta.supervisor.id`. Supervisors nested deeper than `yukta.supervisor.max-depth` (2) are refused. An input request raised by such a run goes only to people and to the parents of the supervisor that started it, so it never waits for itself.
- A supervisor may not answer a request raised by a run it started.
- Runs take no slot of the normal pool, so a saturated server still runs its supervisors; they hold one of `yukta.supervisor.reserved-slots` (4) slots of their own, so they cannot starve normal work. A run that finds no free slot within its timeout is skipped.

## A supervisor that flaps

Two supervisors never fight over a node (one owner per unit). What is left to guard is one supervisor flapping against itself: one that turns a target around (pause then resume, skip then unskip, step on then off, priority) more than `limit` times in `period` is blocked from turning it around for `cooldown` (`flapping-blocked` in the decision list and the control audit).

| Setting | Default | Meaning |
|---|---|---|
| `yukta.supervisor.max-attachments` | `200` | Most assignments at once |
| `yukta.supervisor.turn-around.period` | `60s` | The period in which turn-arounds are counted |
| `yukta.supervisor.turn-around.limit` | `4` | Most turn-arounds of one target in the period |
| `yukta.supervisor.turn-around.cooldown` | `5m` | How long a supervisor over the limit is blocked |
| `yukta.supervisor.default.enabled` | `true` | Turns on Direct control: people and agents control what no supervisor owns. Turn it off in production |
| `yukta.supervisor.lock-holders` | any admin | Keys that may change a locked assignment |
| `yukta.supervisor.rules.file` | unset | Starts a rule supervisor from a file; it owns nothing, so it reviews nothing |
| `yukta.supervisor.max-commands-per-second` | `20` | Rate limit per supervisor |
| `yukta.supervisor.dry-run` | `false` | Record commands without applying them |

## Supervisors outside the server

An application can be a supervisor: use the `http` engine ([Supervisor engines](/running/supervisor-engines)). An agent that only observes can follow `GET /api/events/stream` and steer with the REST or MCP control endpoints as an `OPERATOR` key, which makes it a person for the risk rule and subject to the owner's `operatorAccess`.
