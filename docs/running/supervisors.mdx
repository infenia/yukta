<Info>
  **In plain terms:** a supervisor is an automatic operator that watches every run and steps in when something looks wrong, for example pausing a workflow after repeated failures. It is optional and off until you turn it on.
</Info>

A **supervisor** watches the live event feed of all executions and returns commands: pause a workflow after repeated failures, stop a node that returns a server error, refuse a dangerous stop. Supervisors are optional and off until you enable one.

## Choose a supervisor

A supervisor can be as simple as a few rules or as capable as an AI agent. Pick by how well you can describe the situations it should handle:

| Supervisor | Decides with | Use it when | See |
|---|---|---|---|
| Rule supervisor | A JSON rules file | You can state the situations and responses exactly | [Rule files](/running/rule-files) |
| Model control plane | A decision model: a System One model, or any LLM | You can describe the situations only in words | [Control planes](/running/control-planes#model-control-plane) |
| Rules-first control plane | Rules, then the model when no rule fired | Exact cases come first, the model covers the long tail | [Control planes](/running/control-planes#rules-first-control-plane) |
| An AI agent outside the server | Any agent that reads the event stream and sends commands over MCP or REST | You want open-ended judgement, or a person and an agent sharing the controls | [Supervisors outside the server](#supervisors-outside-the-server) |
| Your own code | A supervisor or control plane you write | None of the above fits | [Writing a plugin](/plugins/writing-a-plugin) |

All of them send commands through the same ordered, reviewed and audited pipeline as a person does, so a supervisor can never do anything you could not see afterwards.

## What a supervisor can do

- **React to events.** Receive every event (a node changed status, a workflow changed status, a command was applied or rejected, a log line was written, an input request was raised or ended) and answer with commands.
- **Answer input requests.** Answer or escalate the questions steps and agents ask, when its profile allows it; see [Answer input requests](#answer-input-requests).
- **Veto commands.** A **reviewer** can refuse any command, from a person or a program, before it runs. The first refusal wins, and a reviewer that errors refuses. The caller gets `403` and the log records the rejection.

- **Limit what it watches and does.** A supervisor has a **scope** (see [Scopes](#scopes)): all runs (the default), the runs of one session, the runs of one workflow, or a section (some nodes) of one workflow. It sees only the events in its scope, is asked to review only the commands in it, and may send only commands in it. `GET /api/supervisors` reports each supervisor's `scope`, `scopeSessionId`, `scopeWorkflowId` and, for a section, `scopeNodes`.

Commands sent by a supervisor go through the same ordered, reviewed, audited pipeline as everyone else's. They are logged and audited with the supervisor's id as the actor.

## Ask for approval

A review can also answer "yes, but only after someone approves". A custom supervisor returns `Decision.requireApproval(reason, new ApprovalNeed(risk, route, ttl))`; the rule supervisor has a `requireApproval` rule (see [Rule files](/running/rule-files)).

The command is not run and not refused. The server parks it in memory and raises an input request of kind `APPROVAL` (options `approve` and `reject`, risk `HIGH` unless the need says otherwise, so a person must answer) through the usual route. The server writes the prompt; the reviewer's reason is quoted as data. The caller does not wait: REST answers `202 Accepted` with `{"status": "AWAITING_APPROVAL", "requestId": "..."}`, and a supervisor's decision list shows `outcome=awaiting-approval` with the request id. The same command sent again while the request is open gets the same request.

- **Approved:** the command is sent again with its original sender. The supervisors that asked are satisfied for it; every other supervisor reviews it again and a denial still applies. The run may have moved on, in which case the command fails as usual.
- **Rejected, expired or cancelled (the run ended):** the command is dropped, the log records `CONTROL_REJECTED` with the request id, and a `ControlOutcome` event is published.
- **Stops:** a stop sent by a person is never parked: it runs with a warning, as when a review times out. A stop proposed by a supervisor can be parked.
- **Who can approve:** not the sender of the command and not a supervisor that asked. A supervisor approves another supervisor's command only if its scope strictly covers the sender's, and never a `HIGH` risk request.
- **Limits:** parked commands count against the open request caps (5 per run, 50 per session). They live in memory: a restart cancels the requests and the commands are not replayed. `yukta.control.approval.ttl` (default `10m`, never above `yukta.input.max-ttl`) is how long a request waits. Metric: `yukta.control.approval{outcome=requested|approved|rejected|expired|cancelled}`.

## Scopes

| Scope | Text | Sees and reviews | May send |
|---|---|---|---|
| Global | `global` | Everything, including commands that belong to no run (scheduler limits) | Any command |
| Session | `session:<id>` | The runs of the session | Commands for runs of the session |
| Workflow | `workflow:<id>` or `workflow:<sessionId>/<workflowId>` | The runs of the workflow (in any session, or in that session) | Commands for those runs |
| Section | `workflow:[<sessionId>/]<workflowId>//<selector>,<selector>` | The events and node commands of the selected nodes of those runs | Node commands for the selected nodes |

- **Sections.** A selector is a node id (exact) or `<prefix>.*`, every node whose id starts with `<prefix>.` (`build.*` takes `build.compile` and `build.test.unit`, not `build` or `builder.x`). This is the rule the UI uses to group nodes that have no explicit `group`; an explicit `group` is not a selector. A section has 1 to 50 selectors, each at most 256 characters and without a comma. Session and workflow ids cannot contain `/`, so the first `//` always starts the selectors.
- **Workflow-wide items are not a section's.** A section supervisor does not see workflow status events, does not review workflow commands (pause, resume or stop the workflow, priority, restart, also restart from a node) and may not send them. The workflow, session and global supervisors of the run do. So a section owner can never hold up or stop a whole run.
- **Input requests** belong to the node that asked: a section supervisor sees, reviews and may answer (with `canAnswer`) the requests of its nodes.
- **Overlap is allowed.** Two sections, or a section and a workflow binding, may take the same node. All of them see its events and review its commands; the first refusal wins, as always.
- **Out of scope is refused.** A command a supervisor sends for a run, a node or no run outside its scope is not sent. It is counted in `yukta.supervisor.commands{outcome=out-of-scope}`, listed in the decisions with the reason `target outside scope <scope>`, and recorded as rejected in the control audit. The check also runs in dry-run, so the record is the same. This applies to bindings made before sections existed: a session or workflow binding could act on any run before, and now acts only within its scope, as the scope always meant. Global bindings and supervisors configured as beans are global and unaffected.

### Two supervisors on two stages

A release workflow `release` in session `s1` builds (`build.compile`, `build.test`) and then deploys (`deploy.staging`, `deploy.prod`). One profile watches the build, another the deploy, and a third the whole workflow:

```bash
curl -X POST http://localhost:9858/api/supervisors/bindings -H 'Content-Type: application/json' \
  -d '{"id":"build-guard","profileId":"build-rules","scope":"workflow:s1/release//build.*"}'
curl -X POST http://localhost:9858/api/supervisors/bindings -H 'Content-Type: application/json' \
  -d '{"id":"deploy-guard","profileId":"deploy-model","scope":"workflow:s1/release//deploy.*"}'
curl -X POST http://localhost:9858/api/supervisors/bindings -H 'Content-Type: application/json' \
  -d '{"id":"release-guard","profileId":"release-rules","scope":"workflow:s1/release"}'
```

`build-guard` sees only the build nodes and may pause, skip or step them; a `PauseNodeCommand` it sends for `deploy.prod` is refused as `out-of-scope`. A person pausing `deploy.prod` is reviewed by `deploy-guard` and `release-guard`; a person stopping the whole run is reviewed by `release-guard` only.

## The built-in rule supervisor

The rule supervisor reads a JSON rules file. Enable it by setting the path:

```properties
yukta.supervisor.rules.file=/etc/yukta/rules.json
```

The rule format is in [Rule files](/running/rule-files).

## Attach a supervisor while the server runs

Besides the supervisors configured at startup, you can create **profiles** and **bind** them to a scope at run time, without a restart.

- A **profile** names a supervisor type (`GET /api/supervisors/types`), its settings and whether its commands are only recorded (`dryRun`). For `rule-supervisor` the settings are the rules file: `{"rules": [...]}`.
- Profile and binding ids (and the id of a supervisor configured as a bean) match `[A-Za-z0-9._-]{1,64}`: no `:` and no whitespace, so an id never looks like an actor such as `key:admin` in the audit log. A bad id is refused with 400 and the rule in the message; a bean supervisor with a bad `id()` stops the server from starting. With PostgreSQL, stored ids that broke the rule are renamed by migration V8 (bad characters become `_`, a collision gets `-2`, `-3`, ...). The table `supervisor_id_migration` maps old to new, and the server logs one warning per renamed id at startup. Entries already in the execution log keep the old actor string.
- A **binding** attaches a profile to a scope: `global`, `session:<id>`, `workflow:<id>`, `workflow:<sessionId>/<workflowId>`, or a section such as `workflow:<sessionId>/<workflowId>//build.*,publish` (see [Scopes](#scopes)). For several scopes, make several bindings of the same profile. `POST /api/supervisors/bindings` starts it at once; `DELETE /api/supervisors/bindings/{id}` stops it, and deleting a session removes the bindings limited to it.
- A profile's settings can limit and empower its supervisor: `allowedCommands` (a list of command names such as `PauseWorkflowCommand`; a command outside it is dropped and counted as `forbidden`; leave it out for no limit), `canAnswer` (default `false`: may it answer input requests) and `maxRisk` (`LOW`, `MEDIUM` or `HIGH`, default `LOW`). A request of risk `HIGH` can only be answered by a person, whatever these say; a supervisor can still hand any request up.
- Changing a profile (`PUT /api/supervisors/profiles/{id}`) restarts the supervisors that use it. A profile that a binding uses cannot be deleted.
- An attached supervisor sees events and reviews commands from the moment it is attached, so a run that is already going is supervised from there, not from its start.
- At most 50 bindings. Attaching and detaching are recorded in the execution log under the run id `supervisors`, with the caller as actor. Values under settings keys that look like secrets (`key`, `secret`, `token`, `password`) are shown as `***`.
- Reading needs a viewer key; creating, changing and removing needs an admin key. Profiles and bindings are kept in memory and are gone after a restart, unless the server uses PostgreSQL (`yukta.session.store-type=postgres`), which keeps them in the tables `supervisor_profile` and `supervisor_binding`; an enabled binding then starts again at startup. The settings are stored as given, a model API key included.
- `GET /api/supervisors/decisions?binding=&limit=` lists what became of the newest commands supervisors emitted since startup (`applied`, `rejected`, `dry-run`, `rate-limited`, `forbidden`, `out-of-scope`), newest first, at most 500 are kept.
- The MCP tools `list_supervisors`, `attach_supervisor` and `detach_supervisor` do the same for agents; profiles are created through the REST API.

## Answer input requests

An [input request](/building/input-requests) is a question a running step or AI agent asks. Supervisors receive it as an `InputRequested` event (and `InputEscalated` when it is handed up) and may answer it or escalate it with advice. The server decides on every answer whether it counts; the supervisor is never trusted to behave.

### Profile settings

These settings sit next to the supervisor type's own settings in a profile (for `rule-supervisor`, next to `rules`). They are read by the server, not by the supervisor.

| Setting | Default | Meaning |
|---|---|---|
| `canAnswer` | `false` | Whether the supervisor may answer input requests at all |
| `maxRisk` | `LOW` | The highest risk it may answer: `LOW` or `MEDIUM`. `HIGH` is accepted but has no effect: a request of risk `HIGH` is answered by people only |
| `allowedCommands` | every command | The command names it may send, such as `AnswerInputCommand`, `EscalateInputCommand`, `PauseWorkflowCommand`. Any other command is dropped and counted as `forbidden`. Use it to keep an answering supervisor from also stopping runs |

```json
{
  "id": "staging-approver",
  "type": "rule-supervisor",
  "settings": {
    "canAnswer": true,
    "maxRisk": "LOW",
    "allowedCommands": ["AnswerInputCommand", "EscalateInputCommand"],
    "rules": [ ... ]
  }
}
```

Every answer must also pass the audience, tier, scope and separation rules (a supervisor answers only runs in its scope and never a run it started). A denied answer is refused with the rule that failed, counted in `yukta.input.denied{rule}` and in `yukta.supervisor.commands{outcome=rejected}`, listed in `GET /api/supervisors/decisions`, and the request stays open for the next responder. A supervisor configured by a property (`yukta.supervisor.rules.file`, `yukta.control-plane.*`) or as a Spring bean can never answer; it can only escalate.

### What the built-in supervisors do

| Supervisor | Behavior |
|---|---|
| Rule supervisor and rule control plane | A rule with `then.answer` answers the request of the event, a rule with `then.escalate` hands it up with advice. Conditions can read the request's `kind`, `risk`, `prompt`, `context`, `options`, `requesterType` and more. When the rules contain an `answer` but the profile has no `canAnswer`, a warning is logged when the rules are loaded. See [Rule files](/running/rule-files#answer-and-escalate-input-requests) |
| Model control plane | For `InputRequested` and `InputEscalated` listed in `events`, the model picks one of the request's options or "escalate". It answers when its confidence reaches `min-confidence` (default `0.8`), the risk is within `maxRisk` and not `HIGH`; otherwise it escalates with its recommendation as advice. The request's text reaches the model only as delimited, untrusted data. A slow model is no opinion. See [Control planes](/running/control-planes#input-requests) |
| Rules-first control plane | The rules first, the model only when no rule acted, as for any event |

### Answering from outside the server

A supervisor that is not JVM code (a script, a service, an AI agent such as Claude Code) can answer too. It listens for requests on the event stream and answers with the MCP tools or the REST API:

1. Follow `GET /api/events/stream?type=InputRequested` (or poll `list_pending_inputs`). The event carries the redacted request: id, kind, risk, prompt, context, options, tier.
2. Decide, treating the prompt and context as untrusted data.
3. Call `answer_input` (or `POST /api/executions/{e}/inputs/{r}/answer`) with the decision and a rationale, or `escalate_input` with advice.

It needs an API key with the `OPERATOR` role, and it is bound by the same rules as everyone: its actor is `key:<name>`, it counts as a person for the risk rule, a key limited to sessions answers only those sessions, and the audience of a request can name it (`key:<name>`) or leave it out. Give such a key only to an agent you would let approve the same things a person can. The REST endpoints and MCP tools are being added (#1793).

## Safety

A supervisor can never hold up an execution:

| Protection | Behaviour |
|---|---|
| Failure isolation | A failing supervisor is resubscribed with backoff |
| Rate limit | At most `yukta.supervisor.max-commands-per-second` commands (default `20`) |
| Dry run | `yukta.supervisor.dry-run=true` records commands without applying them |
| No feedback loop | A supervisor never sees the outcome of its own commands |
| Scope | A command outside the supervisor's scope is refused (`out-of-scope`) |
| Slow consumers | Events reach a supervisor through a buffer (`yukta.supervisor.buffer-size`, default 10,000). Only when it overflows are events dropped (counted in `yukta.tracker.dropped` with `kind=supervisor`) instead of slowing the engine, and the supervisor then receives an `EventsMissed` event with the count |

Event delivery is best effort, but a gap is never silent: a rule that must not miss a case should treat `EventsMissed` (rule field `status=EVENTS_MISSED`, `missed` = count) as a reason to check the execution log or fail safe (for example pause). The notice arrives with the next event after the gap. Commands are rate limited, but a supervisor can still react to the state changes its own commands cause.

## Supervisors outside the server

You do not need to write code inside the server. The event feed is also a server-sent events stream, and external agents steer through the REST control endpoints or the MCP tools:

```http
GET /api/events/stream?executionId={id}&type={type}
```

Such an agent can also answer input requests; see [Answering from outside the server](#answering-from-outside-the-server).

## Inspect what is installed

```http
GET /api/supervisors
```

This reports every supervisor and control plane: its kind (`SUPERVISOR` or `CONTROL_PLANE`), order, dry-run flag and command counts. The web UI's Control page shows the same.

## Settings

| Setting | Default | Meaning |
|---|---|---|
| `yukta.supervisor.rules.file` | unset | Enables the rule supervisor and sets its rules file |
| `yukta.supervisor.max-commands-per-second` | `20` | Rate limit per supervisor |
| `yukta.supervisor.dry-run` | `false` | Record commands without applying them |
