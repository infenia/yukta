<Info>
  **In plain terms:** a control plane is the simplest kind of supervisor: for each event it answers one question, "do nothing, pause, or stop?" Choose one when you want a basic safety net without writing logic.
</Info>

<Tip>
  **Why a model here?** Rules cover situations you can state exactly. A decision model covers the rest: it reads each event and picks one of your options (continue, pause or stop) with a calibrated probability, and acts only when it is sure. A System One model keeps that cheap enough to judge every event; the same job on a chat model would be slower and cost more tokens. Set `backend` to `LLM` if you prefer one.
</Tip>

A **control plane** is a supervisor that decides what to do about **one event at a time**. Where a [supervisor](/running/supervisors) may keep state and emit any commands, a control plane answers a single question per event: nothing, pause, or stop. Control planes are optional and off until enabled. They share the hosting, auditing and rate limiting of supervisors.

Three control planes are built in.

| Control plane | Decides with | Enabled by |
|---|---|---|
| Rule control plane | The same JSON rules as the rule supervisor | `yukta.control-plane.rules.file` |
| Model control plane | A small model asked a multiple-choice question | `yukta.control-plane.model.name` |
| Rules-first control plane | Rules first; the model only when no rule fired | `yukta.control-plane.rules-first.model.name` |

## Rule control plane

Uses the format described in [Rule files](/running/rule-files):

```properties
yukta.control-plane.rules.file=/etc/yukta/rules.json
```

## Model control plane

For each event the model is asked a question with a fixed set of answers. Each answer maps to a command: nothing (`NONE`), pause the workflow (`PAUSE`) or drain and stop it (`STOP`).

It acts **only when it is sure**. An answer less probable than the minimum probability, an unknown answer, a failing or slow model and an unreadable reply all count as no opinion, so the model can never hold up the control bus. By default it can only pause; a stop has to be configured.

```properties
yukta.control-plane.model.name=my-model
yukta.control-plane.model.backend=SYSTEMONE
yukta.control-plane.model.timeout=2s
yukta.control-plane.model.min-probability=0.6
```

| Setting | Default | Meaning |
|---|---|---|
| `yukta.control-plane.model.name` | required | Model name. Setting it enables the plane |
| `yukta.control-plane.model.backend` | `SYSTEMONE` | `SYSTEMONE` uses a local Ollama constrained-answer endpoint with calibrated probabilities. `LLM` prompts any chat model (OpenAI-compatible, Anthropic or Ollama) to answer as JSON |
| `yukta.control-plane.model.provider` | unset | Required for backend `LLM` |
| `yukta.control-plane.model.base-url` | `http://localhost:11434` for `SYSTEMONE` | Model endpoint |
| `yukta.control-plane.model.keep-alive` | unset | `SYSTEMONE` only. How long Ollama keeps the model loaded (`30m`, `-1`), so the first event after an idle spell does not pay the load |
| `yukta.control-plane.model.num-ctx` | unset | `SYSTEMONE` only. Context size to load the model with; a few thousand tokens is enough |
| `yukta.control-plane.model.api-key` | unset | Key for the provider |
| `yukta.control-plane.model.timeout` | `2s` | Longest the model may take; slower counts as no opinion |
| `yukta.control-plane.model.min-probability` | `0.6` | Below this the answer is ignored |
| `yukta.control-plane.model.instructions` | built in | The question asked about each event |
| `yukta.control-plane.model.options` | `continue` and `pause` | Map of answers: each has a `description` of when it applies and a `command` (`NONE`, `PAUSE`, `STOP`). At least two are required |
| `yukta.control-plane.model.events` | `NodeStatusChanged`, `WorkflowStatusChanged` | Event kinds the model is asked about. Add `InputRequested` (and `InputEscalated`) to have it judge [input requests](#input-requests) |
| `yukta.control-plane.model.min-confidence` | `0.8` | An input request is answered only when the model's confidence reaches this; below it the request is escalated with advice |
| `yukta.control-plane.model.max-calls-per-minute` | `0` (no limit) | Most model calls per minute. An event over the limit gets no opinion at once (counted as `skipped`) instead of waiting for the model. Keep must-not-miss cases in a rule of the rules-first plane |

The default answers are `continue` (normal operation, a success, a retry that may still succeed, or an execution that already finished) and `pause` (repeated failures, exhausted retries, authentication errors or resource exhaustion that will not fix themselves, so a person must look). Write option descriptions explicitly: a small model needs them.

When the model is down, slow or unsure, the plane returns no commands, so oversight silently stops. It counts every answer in `yukta.plugin.events{plugin=model_control_plane}` with the outcome `decided`, `skipped` (over `max-calls-per-minute`), `no_opinion` (unknown answer or below `min-probability`) or `model_error` (down, slow or unreadable). Alert on a rise of `model_error`, and on `no_opinion` becoming most of the answers. For anything that must not be missed, keep a rule for it in the rules-first plane.

## Input requests

When `events` lists `InputRequested` or `InputEscalated`, the model control plane judges [input requests](/building/input-requests) instead of mapping them to the options above. Only requests with options are judged (`APPROVAL` and `CHOICE`); for `TEXT`, `STRUCTURED` and `QUERY` it has no opinion.

**What the model sees.** The request was written by the asking step, often an AI agent, so it is treated as hostile:

- The question the model is asked is fixed text. The request's options are offered under neutral keys (`option_1`, `option_2`, ...) plus `escalate`, so nothing the request says can change the question.
- The prompt, options, labels, risk, kind and (already redacted) context are passed as one line of JSON between two marker lines that carry a fresh random value, under a note that the block is untrusted data and must not be followed. Control characters are replaced and long text is cut; a request too large even without its context gets no opinion.
- The chat backend sends that state in the user turn, never in the system prompt.

**What it does with the answer.** The model's output is a choice with a confidence, nothing else. A choice that is not one of the offered keys, an unreadable answer, a probability outside 0 to 1, a model error or a model slower than the decision timeout (10 seconds) is **no opinion**: the request stays where it is, with its tier, until someone else answers it or its deadline passes. Otherwise:

| Situation | Result |
|---|---|
| Confidence at least `min-confidence`, risk within the profile's `maxRisk`, risk not `HIGH` | An answer with the chosen option id, the confidence, and the rationale `model <name>: chose '<id>' with confidence <c>` |
| Confidence below `min-confidence` | An escalation with the advice `Model <name> recommends '<id>' (confidence <c>); ...` |
| Risk `HIGH`, risk above `maxRisk`, or no `canAnswer` | An escalation with the same advice, so the person who answers sees the recommendation. The model never answers `HIGH` (and the server would refuse it) |
| The model chose `escalate` | An escalation saying the model recommends that a person decides |
| The request was already escalated | An answer if the model may and is sure; never a second escalation |

A model control plane configured by properties may never answer, so it only escalates with advice; to let it answer, attach it as a profile with `canAnswer: true` and a `maxRisk` (see [Supervisors](/running/supervisors#answer-input-requests)). Input requests count toward `max-calls-per-minute`. The outcomes are counted in `yukta.plugin.events{plugin=model_control_plane}` as `answered`, `escalated`, `no_opinion`, `invalid_answer`, `unsupported`, `timeout` and `model_error`.

## Rules-first control plane

Combines both. Rules decide first; the model is asked only when no rule fired. Use it to handle the cases you can state exactly with rules and leave the long tail to the model. It takes the rules file and the same `model.*` settings under its own prefix:

```properties
yukta.control-plane.rules-first.rules-file=/etc/yukta/rules.json
yukta.control-plane.rules-first.model.name=my-model
```

## Attaching a control plane at run time

Each of the three can also be made from a profile (`POST /api/supervisors/profiles`) and attached to a scope without a restart; see [Supervisors](/running/supervisors). The profile `type` and `settings` are:

| `type` | `settings` |
|---|---|
| `rule-control-plane` | the rules file as JSON: `{"rules": [...]}` |
| `model-control-plane` | the keys of `yukta.control-plane.model.*` (`name`, `backend`, `provider`, `instructions`, `options`, `events`, `min-probability`, ...), with the same defaults |
| `rules-first-control-plane` | `{"rules": [...], "model": {...}}`: the rules, and the model keys as above |

Each also takes the capability settings `canAnswer`, `maxRisk` and `allowedCommands` at the top level of `settings`, which decide whether its rules and model may answer input requests (for `rules-first-control-plane` they apply to both parts). The model types need the decision plugin. A wrong value is reported by its key and never repeated, because it may be a secret; `api-key` is shown as `***` when profiles are listed.

## Choosing

| If you can... | Use |
|---|---|
| State the situations and responses exactly | Rule control plane (or just the rule supervisor) |
| Describe situations only in words | Model control plane |
| Do both, with exact cases taking priority | Rules-first control plane |

## Writing your own

A control plane implements one operation: decide what to do about an event, within a bounded time. An error counts as no opinion. See [Writing a plugin](/plugins/writing-a-plugin).
