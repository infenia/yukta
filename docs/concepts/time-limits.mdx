A stuck job should end, not hang forever. A single timeout cannot do that well, because "too long" means different things: too long waiting in line, too long overall, too long doing nothing, too long on one attempt. Yukta therefore runs five independent clocks. Each answers a different question.

| Clock | Question it answers | Ends with |
|---|---|---|
| **Queue wait** | How long may a start wait for a slot? | The start times out. Off by default |
| **Run deadline** | How long may the whole run take? | The run ends `TIMED_OUT`. One hour by default |
| **Node idle** | How long may a node sit with no activity? | The node ends `TIMED_OUT` |
| **Element timeout** | How long may one attempt at one message take? | The attempt fails, so retry and error routing apply |
| **Node deadline** | How long may a node live from its first activity? | The node ends `TIMED_OUT` |

## Why five

Consider a node that calls an LLM. You want a call that has hung for a minute to be abandoned and retried (element timeout). You do not want the node as a whole to wait forever for a model that never returns (node deadline). You also want a safety net over the entire run in case something else goes wrong (run deadline). One number cannot be right for all three.

The clocks also differ in whether they reset. The **idle clock** resets on any input, output, retry attempt or heartbeat: it measures silence, not duration. The **run deadline** never resets: it is the net under everything and the right place to say "this should always finish within two hours".

## Defaults that fit the work

The idle clock is a node's `timeoutSeconds`. If you do not set it, the plugin supplies a default that fits what it does: a process node uses its own timeout plus a margin, a model call covers every attempt plus backoff, a sub-workflow its own limit plus a margin, and anything else thirty seconds. This keeps the common case right without configuration, and it is why you usually adjust a node's own timeout and let the idle clock follow.

A timeout that is an expression is unknown until a message arrives, so the node starts with the default and is re-timed on its first message.

## Silent work and heartbeats

A node that works for a long time without producing output would trip its idle clock. A plugin can send a **heartbeat**, which restarts the clock. Remote workers send them automatically while an attempt runs. Heartbeats exist so that "busy but quiet" is distinguishable from "hung", which is the whole point of an idle clock.

## Pausing is safe

All five clocks are pause-aware. Pausing a run freezes them, and paused time is excluded from a node's deadline. A pause therefore never causes a timeout. The consequence: a run you paused and forgot about will wait indefinitely. Time limits protect against hanging, not against forgetting.

## When a clock is not enough

Time limits stop a step; they do not say why it was slow. For that, a supervisor can watch a run for stalls and act, and [observability](/guides/operate/observe-runs) shows where the time went. A timeout is also a failure like any other, so retry and error routing apply to the element timeout. See [The failure model](/concepts/failure-model).
