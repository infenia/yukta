<Info>
  **In plain terms:** a sub-workflow is a workflow used as a single step inside another one, like calling a reusable procedure. Use it to avoid copying the same steps into several flowcharts, or to let a step decide at run time which workflow to run.
</Info>

The `SUB_WORKFLOW` processor runs another stored workflow of the **same session** for each message it receives. Use it to compose small workflows into larger ones, to share a reusable sequence between several workflows, or to build agent-style plans where a step decides which workflow to run.

## Behaviour

- The child is a normal execution with its own execution id. It is tracked, logged and audited like any other.
- The child's terminal nodes feed a result collector. The sub-workflow node emits one message with `{ "executionId": ..., "results": [...], "status": ..., "outcome": ..., "reason": ... }`: `outcome` and `reason` come from the [outcome terminal](/plugins/terminals) the child reached, and are absent when it reached none.
- A failing child fails the node, so the parent's [failure policy](/concepts/failure-handling) applies to it: retries, error routing and timeouts all work as for any node.
- With `routeByOutcome: true` the node routes on how the child ended instead: the message leaves on `success`, `failure`, `retry` or `escalate`, and a failed or timed-out child goes to `failure` rather than failing the node. This is how a parent branches on a child's result, for example to retry a stage or hand it to a person.
- The child's start payload is the `payload` option, whose values may use variables, or else the message payload. Inside the child every node can read it as `${start.<field>}`, so a parent can pass on its own start values with `"payload": {"project": "${start.project}"}`.
- The child's start payload carries two labels, `yukta.depth` and `yukta.parentExecutionId`, so a child can tell how deep it is and who started it.
- The child runs inside the parent node. Cancelling or stopping the node cancels the child (`CANCELLED`).

## Concurrency

When `yukta.execution.max-concurrent` is set, a child runs on the slot its parent already holds. Children are therefore not counted against the limits or the running-executions gauge, which prevents a parent that waits for its children from starving them.

## Example

A parent workflow that calls a reusable `notify` workflow for every ticket:

```json
{
  "nodeId": "notify-each",
  "type": "SUB_WORKFLOW",
  "config": { "workflowId": "notify" }
}
```

A parent that branches on the outcome of a reusable `check` workflow, run on the checkout the parent was started with:

```json
{
  "nodeId": "check",
  "type": "SUB_WORKFLOW",
  "config": {
    "workflowId": "check",
    "payload": { "project": "${start.project}" },
    "routeByOutcome": true,
    "timeoutSeconds": 3600
  }
}
```

Edges with `sourcePort` `success` and `escalate` then lead to the next step and to a person.

See [Routing and flow control](/plugins/routing-and-flow) for the node's full option list.

## Limits and defaults

| Item | Value |
|---|---|
| Maximum nesting depth | 5 |
| Scope | The child must be a workflow of the same session |
| Placement | A `SUB_WORKFLOW` node cannot be placed on a remote worker |
| Run history | The parent-child link is carried in the child's start payload and its start entry in the execution log |
