# Supervisors (rule engine, AI or custom code on the control bus)

Reference for `ExecutionSupervisor`, `ControlReviewer` and the event feed. Moved from `core/CLAUDE.md`.

### Supervisors (rule engine / AI / custom code on the control bus)
A supervisor implements `ExecutionSupervisor` (plugin-api) and is registered as a Spring bean:
- `supervise(Flux<ExecutionEvent>)` receives the global event feed (`ExecutionEventFeed`, fed by the
  tracker and by command outcomes; best effort, never blocks a run) and returns the
  `ExecutionControlCommand`s to apply. `SupervisorHost` subscribes each supervisor once, applies its
  commands through `DirectiveDispatcher` with the supervisor id as actor (Reactor context key
  `ControlActor.CONTEXT_KEY`), and isolates it: failures resubscribe with backoff, commands are
  limited to `yukta.supervisor.max-commands-per-second` (default 20), `yukta.supervisor.dry-run=true`
  only records them, and a supervisor never sees the outcome of its own commands.
- `review(ControlRequest)` can refuse any command, human or automated, before it runs
  (`ControlReviewer`; first refusal wins in the order asked; an erroring reviewer refuses). The caller gets
  `ControlRejectedException` (HTTP 403) and the log gets `CONTROL_REJECTED`.
- Commands sent by a supervisor are logged as `PauseWorkflowCommand [by <id>]`.
- `ExecutionEventFeed.events()` gives every subscriber its own buffer (10 000, overflow counted in
  `yukta.tracker.dropped{kind=feed}`) on `boundedElastic`, so none runs on the tracker's thread. On top of that each supervisor gets its events through a
  bounded buffer (256) on `boundedElastic`; a slow or blocking supervisor drops events (counted in
  `yukta.tracker.dropped{kind=supervisor}`) and never holds the tracker up.
- The feed is exposed at `GET /api/events/stream` (SSE; filters `executionId`, `type`). External
  agents can supervise through it and the REST/MCP control endpoints without JVM code.
- `SupervisorHost.status()` (REST `GET /api/supervisors`, shown on the UI Control page) reports each supervisor's kind (`CONTROL_PLANE` or `SUPERVISOR`), dry-run flag and command counts from `yukta.supervisor.commands`.
- Reference implementation: `plugins/supervisors/rules` (JSON rules + SpEL, enabled with
  `yukta.supervisor.rules.file`). Metrics: `yukta.supervisor.commands{id,outcome}`.
- **Run-time supervisors**: a `Supervisor` (id, type, settings, dry-run, description) plus a `SupervisorAttachment` (supervisor, `SupervisorScope`, enabled, `SupervisorSource` `MANUAL`/`DEFINITION`/`SYSTEM`, origin) made through `SupervisorService` start a `BoundSupervisor` in `SupervisorHost.attach`; `AttachedSupervisors` is the set `ControlReviewer` also asks. Factories (`SupervisorFactory` beans: `rule-supervisor`, `rule-control-plane`, `model-control-plane`, `rules-first-control-plane`) turn a supervisor into the running one. The store (`SupervisorStore`) is in memory, or PostgreSQL (V7). At most `yukta.supervisor.max-attachments` attachments; attach/detach are audited under run id `supervisors`; `SessionService.deleteSession` removes the session's attachments; `SupervisorHost.decisions` keeps the newest 500 command outcomes.
- **Id rule**: supervisor ids, attachment ids and bean `ExecutionSupervisor.id()` match `SupervisorIds.RULE` (`[A-Za-z0-9._-]{1,64}`, plugin-api; no `:` or whitespace, so an id never looks like `key:<name>`). Enforced in `SupervisorService.save`/`attach` (400 through `IllegalArgumentException`), `SupervisorHost.start` (bean with a bad id fails start-up) and `restore` (a stored bad attachment fails its own restore: WARN, counted as failed). Not in the record constructors: stores rebuild stored rows before migration V8 (`supervisor_id_migration` keeps old to new) has run.
- **Capabilities** (`SupervisorCapabilities.from(supervisor, factory.defaultAllowedCommands())`, read when a supervisor is saved (an unknown command name is refused) and when its attachment starts; carried on `BoundSupervisor`): `allowedCommands` (`null` = every command, the default of every shipped factory), `canAnswer` (default false) and `maxRisk` (default LOW). `SupervisorHost` drops a command whose simple class name is not allowed before the rate limit, counts it `yukta.supervisor.commands{outcome=forbidden}` and records it in the decisions with the reason. Bean supervisors are unrestricted and can never answer input requests.
- **Scopes** (`SupervisorScope`, plugin-api): `Global`, `Session`, `Workflow`, `Section(workflowId, sessionId, nodes)`. Text form `workflow:[<s>/]<w>//<sel>,<sel>` (ids cannot contain `/`, so the first `//` starts the selectors; they may contain `#`, which is why `#` is not the separator); a selector is a node id or `<prefix>.*` (node ids starting with `<prefix>.`), 1 to 50, at most 256 chars, no comma. Stored as the same text (no migration). `matches(session, workflow, node)` (the default ignores the node); `Section.matches(session, workflow)` is false, so a section never sees or reviews workflow-wide items (workflow events, `Pause/Resume/StopWorkflowCommand`, priority, restarts). `covers` / `strictlyCovers` (covers and not covered back; a strict partial order) are for composites, holds and escalation.
- **Node of an item**: `ExecutionControlCommand.nodeId()` (node commands; null for workflow and scheduler commands, also `RestartFromNodeCommand`), `ExecutionEvent.nodeId()` (`NodeStatusChanged`, `LogLine`, the input events, `ControlOutcome`), `ControlRequest.nodeId` (the four-argument constructor takes the command's). `DirectiveDispatcher.target(command)` returns the `CommandTarget` (session, workflow, node; the node of an `AnswerInput`/`EscalateInput` comes from its stored request of the same run).
- **Scope enforcement**: `SupervisorHost.apply` checks, after `allowedCommands` and before the rate limit (also in dry-run), that the supervisor's scope matches the command's target; otherwise `outcome=out-of-scope`, reason `target outside scope <key>`, audited as not applied. `Global` needs no lookup; a lookup error counts as outside. `SetLimitsCommand` is in scope for `Global` only.
- **Turn-around guard** (`TurnAroundGuard`, `yukta.supervisor.turn-around.*`; replaces the command arbiter, S2b): `SupervisorHost.apply` asks it after `allowedCommands` and the scope check and before the rate limit. A supervisor that turns one target around (pause/resume, skip/unskip, step on/off, priority) more than `limit` times in `period` is blocked on that target for `cooldown` (`flapping-blocked`). There is no `order()`, window, coalescing or cross-supervisor arbitration: a unit has one owner.
- **Actor kind**: `SupervisorHost` writes `ControlActor.KIND_KEY = SUPERVISOR` next to the supervisor id; input authorisation reads the kind, never the actor string.
- **Approval-gated commands**: `Decision.requireApproval(reason, ApprovalNeed(risk, route, ttl))` (plugin-api; `allowed()` is false, check `approval()`). `ControlReviewer.verdict(request, satisfied)` returns a `ReviewVerdict` (`Allowed`, `Denied`, `NeedsApproval`); a denial wins over needs, needs merge into one (highest risk, first route, shortest ttl, reasons joined, `askedBy` listed), and `review(...)` still treats a need as a refusal. A stop from a non-supervisor sender with a need is allowed with a warning. `DirectiveDispatcher.audited` hands `NeedsApproval` to `ParkedCommands.park`, which raises an `APPROVAL` request through `InputBroker.raise` (server-bound identity, requester `control:<Command>`, key from execution, command and askers) and fails the call with `ControlAwaitingApprovalException` (REST 202 `AWAITING_APPROVAL`, host outcome `awaiting-approval`). Approval re-dispatches through `dispatchOrdered` with the sender's context plus a private `Grant` under `ControlActor.APPROVED_REQUEST` (checked by identity, used once); reject, expiry and cancel log `CONTROL_REJECTED` and publish `ControlOutcome`. `DefaultAnswerAuthorizer` (via `CommandProposals`): the sender and the askers cannot answer (`separation`), a supervisor needs a strictly wider scope than the proposing supervisor (`rank`), HIGH is human only. In memory; not replayed after a restart. Metric `yukta.control.approval{outcome}`; `yukta.control.approval.ttl` (10m).
- **Input requests** (Epic #1787; broker, commands and authoriser in `input-requests.md`): supervisors get `InputRequested`, `InputEscalated`, `InputAnswered`, `InputExpired` and `InputCancelled` on the feed (scope-filtered by the request's session and workflow) and answer with `AnswerInputCommand` or hand up with `EscalateInputCommand` (reason, advice). Both go through `SupervisorHost.apply` like any command (`allowedCommands`, rate limit, dry run), then `DirectiveDispatcher` and `DefaultAnswerAuthorizer`: a denied answer is `InputForbiddenException`, counted in `yukta.input.denied{rule}` and `yukta.supervisor.commands{outcome=rejected}`, and the request stays open. `HIGH` is never answered by a supervisor; a bean supervisor (no supervisor record) has `canAnswer=false`. An escalation of an already escalated request changes nothing (the broker moves only `OPEN`).
- **Shipped supervisors and input requests**: `rule-supervisor` and `rule-control-plane` rules take `then.answer {decision, text, rationale, confidence}` (rationale recorded as `rule <id>: ...`, confidence default 1, `expectedVersion` = the event's version) and `then.escalate {reason, advice}`, only for `InputRequested`/`InputEscalated`; `Fields` exposes `kind`, `risk`, `state`, `tier`, `prompt`, `context`, `options`, `requesterType`, `advice`, `sessionId`. Their factories pass `SupervisorCapabilities.from(supervisor)` and strip the capability keys before the strict rules read (`RuleSupervisor.read(Map)`); `answer` rules without `canAnswer` log a warning at load. `ModelControlPlane` judges the two input events only when listed in `events`: `InputPrompt` (fixed question with neutral keys `option_N` and `escalate`; request as one JSON line between nonce markers in the state, never in instructions) and `InputAdvisor` (answer when confidence >= `min-confidence` (0.8), risk within `maxRisk` and not `HIGH`; otherwise escalate with the recommendation as advice; invalid output, error or `decisionTimeout()` is no opinion; rationale prefixed `model <name>`). A property-configured plane uses `PROPERTY_CAPABILITIES` (cannot answer, only advises). Outcomes in `yukta.plugin.events{plugin=model_control_plane}`: `answered`, `escalated`, `no_opinion`, `invalid_answer`, `unsupported`, `timeout`, `model_error`, `skipped`.
- **External supervisors**: a non-JVM supervisor follows `GET /api/events/stream?type=InputRequested` (or MCP `list_pending_inputs`, phase 5a) and calls `answer_input`/`escalate_input` (or REST `/api/executions/{e}/inputs/{r}/answer|escalate`) with an `OPERATOR` key; its actor is `key:<name>`, kind `KEY`, so it is a human for the risk rule and bound by audience, tier and the key's sessions.
- **Internal sessions** (#1798, `InternalSessions`): a session with tag `yukta.internal=true` (cached 30 s, `SessionService` invalidates on apply/delete, an unreadable session counts as internal). `SessionService.getSessionIds(includeInternal)` backs `GET /api/sessions[/summaries]?includeInternal=` and MCP `list_sessions`. `SupervisorHost.withoutOwnOutcomes` drops events of internal sessions unless the `BoundSupervisor.observeInternal` (setting `observeInternal: true`) is set and its scope's session is that session.
- **Composite supervisors** were removed in S7: their review `ALL`, `ANY` and `MAJORITY` are the delegation modes of `parents` (`DelegationChain`). `SupervisorResolver` (`hierarchy`) is only the copy of the stored supervisors that `SupervisorService` refreshes for parent lookups.
- **Workflow supervisors** (#1798, `service/supervisor/workflow/`): supervisor type `workflow` (`WorkflowSupervisorFactory`; `defaultAllowedCommands()` is empty). `WorkflowSupervisor` is a `ControlPlanePlugin`: `decide` starts the workflow per listed event type (deduped by a bounded set of event keys, `maxConcurrent` semaphore, session re-checked internal), `SupervisorWorkflowRunner` runs it as a child run through `SubWorkflowRunner` (no pool slot) under its own `yukta.supervisor.reserved-slots` (default 4, polled for up to the run timeout, gauge `yukta.supervisor.workflow.slots.used`) with `yukta.supervisor.depth`/`yukta.supervisor.id` in the payload (`yukta.supervisor.max-depth`, default 2). `SupervisorResultMapper` maps the terminal `{commands}` by an allow-list (always: AnswerInput, EscalateInput, Pause/Resume Workflow/Node, SetPriority; opt-in by `allowedCommands`: Stop*, SkipNode, Restart*, SetLimits, SetBreakpoint; max 10; the rest dropped). `ESCALATE` becomes `EscalateInputCommand`, `RETRY` runs once more. `WorkflowSupervisorChecks` (save time: internal session, workflow exists). `SupervisorService.start` calls `bindTo(attachmentId)` so the actor and the starter key are the attachment id. Broker guard: `EligibleSupervisors.mayReceive`, `AttachedSupervisorsDirectory` lets a request raised by a run with `yukta.supervisor.depth > 0` reach only supervisors whose scope strictly covers the starter's (a gone starter: people only). `when` (optional read-only SpEL, `SimpleEvaluationContext` + `MapAccessor`, over the redacted event map; parsed in `WorkflowSettings.read`; an unevaluable condition does not match). Run search (`GET /api/executions`, `includeInternal` default false) and `/executions/counts` leave internal sessions out. The UI session list hides system sessions (tag `yukta.internal`) behind a "System" toggle (`?system=1`). `examples/17-supervisor-workflow` is run by `boot` `WorkflowSupervisorAcceptanceTest`.
- **Catalog** (#1996): `SupervisorFactory.describe()` returns a `SupervisorDescriptor` (type, display name, description, `SupervisorCategory`, icon) and `getConfigSchema()` the settings (`ConfigField`s) next to `SupervisorCommonSettings`; `SupervisorSettingsValidator` checks them when a supervisor is saved (`SettingsValidationException` carries the field errors, HTTP 400). REST `GET /api/supervisor-types[/{type}]` (`SupervisorTypesController`), `/api/supervisors`, `/attachments`, `/decisions`, `/validate` (`SupervisorsController`; settings under secret-looking keys leave as `***` through `SupervisorSettingsMask`); MCP `SupervisorProvider`. The UI lives in `ui/src/features/supervisors`; the Control page has only `SupervisorsTile`.
- **Definition-declared supervisors**: a session (`supervisors`) or workflow (`supervisors`, optional `nodes`, `enabled`) names supervisors; `DefinitionSupervisors` (also the `DefinitionUsage` that stops a used supervisor being deleted) reconciles on save: attaches with source `DEFINITION`, id `def-` + 16 hex of SHA-256(session, workflow, supervisor, sorted nodes), detaches what is no longer declared, never touches `MANUAL` attachments; an attach that fails is logged and left for the next reconcile, it never fails the save. An unknown supervisor is refused with the field `workflows.<w>.supervisors[i].supervisor`.
- **Generic types** (`plugins/supervisors/guards`, `.../webhook`): `failure-guard`, `stall-watchdog`, `approval-gate` and `callout` (was `webhook`, S7; reactive only, its commands carry cause `event`; egress through `EgressPolicy`/`HostAllowList`; replies pass `SupervisorResultMapper`'s allow-list).

### Control entry inventory (S1, #2146)
`SupervisedControl` (`service.control`) is the only entry that applies a control command or a start for people and engines. It writes `ControlActor.CHANNEL_KEY` (`OPERATOR`, `ENGINE`, `SYSTEM`; none counts as `SYSTEM`) next to the actor and its kind, which `ApiKeyFilter`, `McpEndpointFilter`, `TokenAnswerService` and `SupervisorHost` write. `AuditRecord`, the `CONTROL_*` log payload (`channel`) and `ControlOutcome` carry it. The ArchUnit rules `ControlEntryRules` (module `architecture`) fail the build if a class outside `service.control..` and `service.supervisor..` calls a `ControlBusGateway` command method or `DirectiveDispatcher.dispatchOrdered/dispatch`, or if `service.supervisor..` does.

A start is `StartWorkflowCommand(sessionId, workflowId, payload, idempotencyKey)` (`executionId()` is `start`; the target is the workflow). The gateway reviews it with `ControlReviewer.review` inside the idempotency window, so a repeated `Idempotency-Key` returns the first run without a second review or audit record; a start that needs approval is refused (there is no run to park the request on yet). It is audited under the new run's id. It does not go through `dispatchOrdered` (that refuses it) and publishes no `ControlOutcome`.

Internal starts and their authority. They run through `WorkflowOrchestrator` and never through `startWorkflow`, so they are not reviewed as starts and cannot be reviewed twice:
- **Sub-workflow** (`SubWorkflowRunner`): a node of an already admitted run starts the child, so it inherits that run's authority; stopping the parent stops the children.
- **Supervisor workflow** (`SupervisorWorkflowRunner`): started by the engine on a supervisor's signal, in an internal session with reserved slots and a depth limit; the commands it returns go through `SupervisorHost` and `SupervisedControl.engine`.
- **Restart** (`RestartCoordinator`): reviewed as `RestartCommand`, once; the new run inherits the old one.
- **Recovery** (`ExecutionResumer`): after a takeover it is SYSTEM and continues runs that were already admitted; operator recovery goes through `SupervisedControl.recover`.

### Owner-only review (S2b, #2147)
`ControlReviewer.verdict` no longer asks every matching supervisor. It reads the channel (`ControlActor.CHANNEL_KEY`) and:
- **`OPERATOR`** (people through REST, MCP, CLI, UI): finds the one owner, the attached supervisor whose scope takes the command's node, run level or the server (`Run` takes the run level only; `Section` the nodes only; `Workflow` and `Session` both; `Global` and bean supervisors own nothing). No owner: allowed if `yukta.supervisor.default.enabled` (default `true`), else `ReviewVerdict.Controlled` (`ControlledBySupervisorException`, HTTP 409 `CONTROLLED_BY_SUPERVISOR`). An owner whose `operatorAccess` (new common setting, a list of command names, default none) does not list the command: `Controlled`, naming the supervisor. Listed: the owner reviews it through `ask` and its answer applies (allow, deny, require approval).
- **`ENGINE`** (a supervisor's own directive; the host already checked scope) and **`SYSTEM`** (no channel): allowed, not reviewed.
- Two owners can only come from legacy data; the lowest id answers and a WARN is logged.
`ask(reviewers, request, satisfied, byPerson)` is the answer pipeline (first refusal wins, needs for approval merge, timeouts, dry run) and will ask a chain of parents in S3. `PipelineReviewer` (test fixtures) asks every matching supervisor so that pipeline is tested on its own. `recover` and `drain` have command types now (`RecoverCommand`, reviewed as a server-level command because the aborted run is not live; `DrainCommand`) and go through `ControlBusGateway.reviewedAdmin`. Exclusivity at save (`OwnershipValidator`), the arbiter removal and the `assignments` block come in the next steps.

### Overlaps at start-up and group selectors (S2)
`SupervisorService.restore` first runs `markConflicts`: among the enabled stored attachments (by id) the first keeps a unit; an attachment that overlaps one already kept is saved disabled with `conflict = true` (`SupervisorAttachment.asConflict()`, PostgreSQL V12 `supervisor_attachment.conflict`) and a WARN names the overlap. Nothing is merged and start-up never fails on it; the administrator resolves the conflict. A legacy `Global` attachment owns nothing (decision E1) and is left as an observer: it gets events but reads no executions or inputs (`SupervisorQueries`) and its commands are refused. Ownership is `SupervisorScope.owns`: a server-level command (`ExecutionControlCommand.serverLevel()`: limits, drain, recover) belongs only to a `Server` scope, which owns nothing else, and a command whose run cannot be looked up is owned by nobody. `group:<name>` selectors (decision E4: a node's group is its `group`, else the part of its id before the first dot) are matched at run time through `NodeGroupIndex`: `DefinitionSupervisors` refreshes it from the stored definitions on every reconcile (session save, rollback, start-up) and `SupervisorService.regroup` restarts the attachments whose groups now name other nodes. `SupervisorService.start` binds `BoundSupervisor.scope()` to the resolved section (`Section.groupMembers`, never stored, not in `key()`). A group selector needs the session (`GROUPS_NEED_SESSION`); the definition check refuses a group that names no node.

### Parents and delegation (S3, #2148)
A supervisor lists `parents` and, per kind (`APPROVAL`, `INPUT`, `CONSULT`), a delegation mode (`ORDERED` default, `ALL`, `ANY`) and a timeout (`Supervisor.delegationFor`). Saving checks them (`SupervisorHierarchy`: parent exists, not itself, no cycle, at most four levels); deleting a supervisor that others report to is a 409. `DelegationChain.resolve` asks the parents in the mode: a refusal from a parent that was asked is final, `ORDERED` falls through silent parents, `ALL` needs everyone, `ANY` takes the first decisive answer, and when nobody decides a person does, with the chain (`parent:ALLOW|DENY|NO_OPINION|silent`) recorded. **Wired so far: `APPROVAL` in `ControlReviewer`**: when an owner's review answers "needs approval" and the owner supervisor has parents, the parents are asked first (a parent is asked through the attached supervisor of its id, any scope; one that is not running is silent). One that allows lets the command through, one that refuses denies it as `<parent>: <reason>`, otherwise the need stays for a person with the chain in its reason. A `HIGH` risk need is never delegated. A sibling that is not a parent is never asked. **`INPUT`** goes through the route: the tier `supervisor:parent` (replaces `supervisor:above`) targets the parents of the supervisor that escalated (or of the previous tier's supervisors), each of which must also watch the request; the tier's own `mode`, `quorum` and `timeout` decide how they are asked (the `delegation.INPUT` mode of the supervisor is not read for input requests). A supervisor may approve another supervisor's parked command only if it stands above it in the hierarchy (`EligibleSupervisors.outranks`, up to four levels; rule `rank`), and a request raised by a supervisor's run reaches only the parents of the starter. `strictlyCovers` is no longer used for ranking. `CONSULT` needs the engine `Delegate` directive and is not done.

### Engines (S4, #2149)
`SupervisorEngine` (plugin-api, `plugin.control.engine`) turns `Flux<Signal>` into `Flux<Directive>`; it reaches nothing but its `EngineContext`. Engines run as `EngineBackedSupervisor` (made by `EngineSupervisorFactory`) inside `SupervisorHost`; every `Directive.Command` passes `DirectiveGate` (enabled, in `allowedCommands`, the target is owned, and for a tick or an initiative a reason, an entry in `initiative` and `maxInitiativePerMinute`; dry run records and applies nothing). An engine failure resubscribes with backoff; the review and directive sinks are multicast without auto-cancel so a resubscribed engine still gets reviews and agent directives. A review the engine cannot take (more than `MAX_OPEN_REVIEWS` open) or does not answer in time is an error, so `ControlReviewer` refuses it (a stop still passes); `NoOpinion` allows. An attached `Global` scope owns nothing: it observes, and its commands are refused as `not-owned` (a bean supervisor keeps its legacy reach).

### Directive gate, reads and the rules engine (S4/S5)
A supervisor that implements `DirectiveSupervisor` (plugin-api; `EngineBackedSupervisor` and `RuleSupervisor`) returns `Directive.Command`s with a key, a cause and a reason. `SupervisorHost.commandsOf` checks each with `DirectiveGate` (a reason and an `initiative` entry for a tick or initiative cause, `maxInitiativePerMinute`, scope, `allowedCommands`), applies a key once (newest 1000 remembered), applies an `answers:<id>` cause once (`answer-repeated`), and records a refusal as `reason-required`, `initiative-not-allowed`, `initiative-rate-limited`, `not-allowed` or `not-owned`. `ifStatus` is checked against the run's status (see Engine leftovers). A supervisor that implements `ReadsAware` gets `EngineReads` from `SupervisorService.start` (`SupervisorQueries.readsFor(scope)`: owned executions and open input requests, newest first, at most 200; a section sees the runs of its workflow; no node output). `SupervisorService` keeps the newest 20 saved states of each supervisor (`SupervisorVersions`, in memory); `GET /api/supervisors/{id}/versions` and `POST .../rollback?version=` use them.
Rules (`rule-supervisor`): `schemaVersion` 1; a rule with `when.every` (`30s`, `5m`, `2h`; at least 1s; no `event`; needs `then.command` and `then.reason`) runs on a timer over the owned executions (`when.status`, `workflowId`, `if` match each; the `if` also sees `read.<STATUS>` counts, 0 for none), with cause `tick`, so it needs the command in the supervisor's `initiative` list. Presets (`RulePresets`: `failure-guard`, `stall-watchdog`, `approval-gate`) and a dry-run replay over a past run (`ReplayEvents`) exist; `read.inputs` does not.

### The `http` engine and the agent API (S6)
Supervisor type `http` (`HttpEngineFactory` wrapped by `EngineSupervisorFactory`, bean in `AgentEngineConfiguration`) makes an application the decision maker. `AgentHub` holds one `Channel` per running supervisor: the signals (best effort, `directBestEffort`: an agent that is away misses them and reads the executions to catch up), the directives the agent posts and its `EngineReads`. `AgentCredentials` keeps one credential per supervisor as a SHA-256 hash (`yag_` + 32 random bytes, shown once; issue again to rotate, revoke to cut; optional expiry and source address list; stored in PostgreSQL V14/V15 when configured). A revoke or rotation ends the open `/events` streams of that supervisor (`AgentHub.credentialChanges`), and deleting a supervisor revokes its credential. `AgentCredentialFilter` (web, order +3) guards `/api/agent/v1/**` with that credential only; `ApiKeyFilter` leaves the path to it, so no human key works there and a credential works nowhere else (an ambiguous spelling of the path is a 400). The caller is the supervisor with actor kind `SUPERVISOR`; responses carry `Yukta-Supervisor-Contract: 1`. `AgentApiController`: `GET /self`, `GET /events` (SSE of `{kind, signal}`, limited per caller by `SseStreams`), `GET /executions`, `GET /inputs`, `POST /directives` (`{key, cause, reason, ifStatus, command{type, executionId, ...}}` turned into a command by `SupervisorResultMapper`; a cause `event:<id>` must name a signal sent to that supervisor (`Channel.sent`), otherwise 400, so an agent cannot pass initiative off as a reaction, and `answers:<id>` must name an open review or delegation and is taken once (`Channel.claimAnswer`; late, unknown or repeated is 409; the same holds for `POST /reviews/{id}` and `/delegations/{id}`); the host's directive gate then checks it), `POST /reviews/{id}` and `POST /delegations/{id}`. `AgentCredentialController`: `POST|DELETE /api/supervisors/{id}/credential?ttlHours=` (ADMIN; only for a supervisor of type `http`) and `GET` (metadata: issued, expiry, addresses, last use and address; never the secret). The per-credential limits `yukta.agent.*` are Spring settings. An agent stream (`/events`, `/signals`) reports a cursor older than the 1000 remembered signals, or a reader that falls more than `AgentHub.LIVE_BUFFER` behind, as an `EventsMissed` event. Also `GET /snapshot`, `GET /signals?after=&wait=` (long poll) and `/api/agent/v1/mcp` (the same operations as MCP tools).

### Engine leftovers (S4)
`ifStatus` on a directive is checked by the host against the run's status (`SupervisorQueries.statusOf`, from the run history; a mismatch or an unknown run is `precondition-failed`). `HoldLedger` (in the host) remembers the runs a supervisor paused until anyone resumes or stops them or the run ends (the host follows `ControlOutcome` and `WorkflowStatusChanged` on the feed; at most 1000, the oldest dropped first); `SupervisorHost.held(id)` takes a supervisor or an attachment id. Detaching a supervisor closes it when it is `AutoCloseable` (an engine). The agent API's `command.target` is `execution:<id>`, `workflow:<id>`, `owned.running` or `held`, expanded to at most 200 runs, each sent as its own directive with the key `<key>#<execution>`. The catalog is also served at `/api/supervisor-engines` (the same controller as `/api/supervisor-types`). An engine's first signal is `Started` (reason `first`, then `resubscribe` after a restart) with the owned executions and open inputs (at most 200 each), the hold ledger (`EngineReads.held`) and the cursor of the newest event; a read that fails leaves its part empty. The agent `GET /snapshot` carries `held` too. Closing the engine (detach or disable) completes its channel, so an open `/events` stream ends and the next agent call is 404. Engines take ticks from `EngineContext.ticks(period)`. Group selectors are resolved per session (see Overlaps at start-up and group selectors).

### Workflow engine nodes (S9)
The `workflow` supervisor type is the workflow engine. Two nodes make a decision workflow readable: `SUPERVISOR_SIGNAL` (`plugins/triggers/api-trigger`; emits the payload the supervisor started the run with; optional `signals` list checked against EVENT, TICK, REVIEW, DELEGATED, STARTED) and `SUPERVISOR_DECISION` (`plugins/terminals/outcome-terminal`; takes the exits of `OUTCOME_TERMINAL`, default SUCCESS, and fails the run when a `commands` list holds more than 10 entries or an entry the contract cannot read). `examples/17-supervisor-workflow` uses them; its section supervisor lists `low-risk-workflow` as parent for the `supervisor:parent` tier. `SUPERVISOR_READ` is not built (spike in the plan).
