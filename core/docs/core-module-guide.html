Core module guide

core is Yukta's engine. It turns a JSON workflow definition (nodes plus edges) into a graph of Project Reactor streams, runs it, tracks per-node status and logs, and exposes runtime controls: pause, resume, stop, skip, step and restart. REST (web), MCP (mcp) and the UI all reach it through WorkflowService, SessionService and ControlBusGateway.

Design in one paragraph

A WorkflowDefinition is prepared once: it's validated, plugins are looked up and initialised, nodes are topologically sorted, and the definition is compiled into a WorkflowTemplate holding one NodeAssembler per node. The prepared workflow is cached per session + workflow in Caffeine. Each execution creates an ExecutionControl (stop sinks, pause valves, flags), runs every assembler in topological order to wire the streams, then subscribes to all terminal nodes in one Mono.using. Status and log events go through batched sinks into DefaultTaskTrackerService, which feeds the SSE status and log streams.

Runtime model

How a node stream is wired

  1. Merge parents: StreamTopologyDecorator.mergeParentStreams merges each parent's hot flux, stamps sourceNodeId, and filters on sourcePort when the edge sets one.
  2. Pre-controls: ExecutionControl.applyPreProcessingControls applies the node's safe-stop (takeUntilOther).
  3. Plugin: NodeMessageChannel.inbound → process() / consume() → outbound. Blocking plugins run with subscribeOn(virtualThreadScheduler).
  4. Tracking: StreamBuilder adds an idle timeout and emits RUNNING, then SUCCESS or FAILURE.
  5. Post-controls: the node and global pause valves (filterWhen) and the node immediate-stop.
  6. Broadcast: history stamp → checkpoint → payload echo to the log → a multicast sink. A connector subscribes it when the run starts.

Control commands

A command goes from ControlBusGateway to ControlBusService (a batched sink), then DirectiveDispatcher, then a *CommandProcessor, which mutates the run's ExecutionControl. The "Effective?" column records whether the mutation reaches the running stream.

Status model

The tracker parses every workflow status with TaskStatus.valueOf. Green values are enum members. Red values are emitted somewhere in core but aren't members, so they throw and drop the rest of the event batch (finding C1).

Extending core

Add a plugin

Implement TriggerPlugin, ProcessorPlugin or TerminalPlugin from plugin-api and register it as a Spring bean. PluginRegistry keys plugins by getType().

  • Keep instances stateless. One bean serves every node and every workflow (C9).
  • Read config from the config argument of start/process/consume, not from initialize.
  • Return isBlocking() = true for I/O. Note the current pool limit (P1).
  • Override getDefaultTimeout() / getDefaultBufferSize(). Node config keys timeoutSeconds and bufferSize take precedence.

Swap a store

  • ExecutionControlStore: @ConditionalOnMissingBean in AppConfiguration.
  • SessionConfigStore: file or memory via SessionConfigStoreConfiguration.
  • WorkflowDefinitionStore: via WorkflowDefinitionStoreConfiguration.
  • PluginLogStore (reader and writer): memory or file via LogStoreAutoConfiguration.
  • NodeCheckpointStore: in-memory today. If you persist it, switch the save to concatMap (P4).
