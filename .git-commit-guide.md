# Git Commit Message Guide for Yukta

## Overview

This project uses **Conventional Commits** to standardize commit messages across the repository. This improves code readability, enables automated changelog generation, and facilitates better collaboration.

## Format

```
<type>(<scope>): <subject>

<body>

<footer>
```

### Components

#### 1. Type (required)
Specifies the nature of the change. Must be lowercase.

- **feat**: A new feature
- **fix**: A bug fix
- **docs**: Documentation changes
- **test**: Test additions or modifications
- **refactor**: Code refactoring without behavior change
- **chore**: Build process, dependencies, tooling (non-code)
- **style**: Code style changes (formatting, missing semicolons, etc.)
- **perf**: Performance improvements
- **ci**: CI/CD configuration changes
- **build**: Build-related changes (gradle, plugins, etc.)

#### 2. Scope (optional but recommended)
The area/module affected by the change. Enclose in parentheses. Use kebab-case.

Common scopes for Yukta:
- `cli` - Go CLI
- `core` - Core orchestration engine
- `web` - REST controllers and web layer
- `ui` - Frontend (JTE templates, Tailwind)
- `plugin-api` - Plugin abstractions
- `plugins` - Plugin implementations (processors, triggers, terminals)
- `mcp` - MCP server
- `messaging` - Messaging abstractions
- `boot` - Spring Boot application entry point
- `build-logic` - Gradle build conventions
- `deps` - Dependency updates (automated)

#### 3. Subject (required)
A concise summary of the change.

**Rules:**
- Use imperative mood: "add", not "added" or "adds"
- Do NOT capitalize the first letter
- Limit to **50 characters** (hard limit)
- Do NOT end with a period
- Be specific and descriptive

#### 4. Body (optional but recommended for non-trivial changes)
Detailed explanation of the *what* and *why*, not *how*.

**Rules:**
- Wrap at 72 characters
- Separate paragraphs with blank lines
- Use bullet points for multiple changes
- Explain the motivation behind the change
- Reference related documentation or issues if applicable

#### 5. Footer (optional)
References to issues, breaking changes, or related metadata.

**Formats:**
- `Fixes #123` or `Closes #456` - closes associated issue
- `Refs #789` - references an issue without closing
- `BREAKING CHANGE: description` - documents breaking API changes

## Examples

### Simple Feature
```
feat(cli): add workflow status command

Add a new `status` subcommand to fetch the current execution state
of a workflow with human-readable formatting including node progress,
timestamps, and error details if present.

Fixes #142
```

### Bug Fix with Scope
```
fix(core): prevent race condition in plugin lifecycle

Synchronize ActivePluginRegistry state transitions with a read-write
lock to avoid stale-workflow cleanup interfering with concurrent
plugin registration and execution.

Add comprehensive unit tests covering:
- Concurrent registration and deregistration
- Cleanup timing relative to execution start
- Error handling during state transitions

Fixes #156
```

### Refactor with Breaking Change
```
refactor(plugin-api): rename ExecutionContext to WorkflowContext

This better reflects that the context represents workflow-level state,
not just individual task execution.

BREAKING CHANGE: ExecutionContext is renamed to WorkflowContext.
Update all plugin implementations to use the new name.

Refs #203
```

### Dependency Update (Automated)
```
build(deps): bump spring-boot from 4.0.0 to 4.1.0

Automated dependency update via Dependabot. Contains performance
improvements and new features in Spring Boot 4.1.0.
```

### Formatting/Style
```
style(web): apply spotless formatting to ControlBusController

No functional changes; formatting only.
```

### Documentation
```
docs(readme): clarify plugin development workflow

Add section on step-by-step plugin creation with examples for
Processor and Trigger plugin types.
```

## Anti-Patterns

### ❌ DON'T do this:

```
# Capitalized subject
Feat: Add workflow status command

# No scope or generic scope
feat: improvements to CLI

# Period at end
feat(cli): add workflow status command.

# Too long (>50 chars)
feat(cli): add a new workflow status command to the cli

# Present tense instead of imperative
feat(cli): adds workflow status command

# Multiple unrelated changes (should be separate commits)
feat(cli): add status command and fix bug in parser
```

### ✅ DO this:

```
# Concise, imperative, scoped
feat(cli): add workflow status command

# Clear body explaining why
fix(core): prevent race in plugin lifecycle

Synchronize state transitions with a mutex to avoid cleanup
interfering with concurrent executions.

# Reference to issue in footer
Fixes #142

# Separate commits for separate concerns
feat(cli): add workflow status command
feat(cli): improve output formatting
fix(parser): handle edge case in arguments
```

## Commit Message Validation

The `.git/hooks/commit-msg` hook validates every commit message before it's created. If your message violates the format, the commit will be rejected with helpful feedback.

Example validation failure:
```
❌ COMMIT MESSAGE FORMAT ERROR

Expected format: type(scope): subject
Example: feat(cli): add workflow status command

Types: feat, fix, docs, test, refactor, chore, style, perf, ci, build
Subject: max 50 chars, imperative mood, no period

Your subject: 'Feat: Add workflow status command'
```

## Using the Template

When you run `git commit`, the message template will be shown in your editor:

```bash
git commit
# Opens editor with .gitmessage template
```

The template includes:
1. Format specification
2. Type definitions
3. Rules for each component
4. Real examples you can reference
5. Common scopes for this project
