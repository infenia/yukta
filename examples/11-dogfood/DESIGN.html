Developing Yukta with Yukta

Every build of Yukta runs as a Yukta workflow.

Yukta runs jobs as step-by-step flowcharts. Its own team uses it to check Yukta's code (dogfooding), and when a check fails, AI helpers try to repair it, cheapest first, before a person has to step in. New here? Start with the 6-step story ↓

Builds, tests and checks run on a local dev server that is itself built from origin/main. One command, yk, is the only entry point, and every run ends in one machine-readable RESULT line.

heal_workflow unrolls check; heal_subflows makes heal and fix-from-*; issue_workflows and epic_workflows add the issue layers.

session apply, workflow start

The CLI uploads one session JSON, then starts one workflow. yk watch follows it.
Two kinds of session. yk check / yk gradle apply a session per checkout, check-<branch>-<hash of path>, with the project path baked in. yk run issue|epic apply the shared session yukta-dev, where the project is a start variable (start.project) so the same check serves any worktree.

Design decisions worth knowing

One execution per check
The whole gate, heals included, is one run, so yk watch, yk tree and yk retry steer a single thing.
Route by exit code
Stage nodes use failureMode: CONTINUE + routeByExitCode, so a failing stage takes a failure edge instead of killing the run.
Escalation is composition
check calls heal, which calls fix-from-<effort> as SUB_WORKFLOWs. Cheap and deterministic first, then Claude haiku → sonnet → opus.
Fixers are judged by the check
After every attempt the failing stage's own command re-runs. A guard rejects edits to config, build, CI, added suppressions or removed assertions. Fixers never commit.
One fixer at a time
Analyzers run in parallel, but a single analyzers.heal fixes all failures, so two models never edit the tree together. Gradle nodes share a concurrency group (2).
Nothing outward-facing by itself
before-pr fails the run if nobody answers. before-implement merely continues after an hour.
Server from main, workflows from your checkout
The server swaps to a newer main only while idle, so a run never changes under itself.
Every step is logged
One append-only heal-events.jsonl feeds yk heal report and analyze, which is how the heal itself gets improved.

What's happening, in plain words

Dev server and a yk check run

In plain words

The dev server is the engine that actually runs the flowcharts: a private copy of Yukta on the developer’s own computer, always rebuilt from the latest approved code (main). It never swaps itself out in the middle of a job. yk is the remote control: it starts the server if needed, sends the flowchart, follows it, and prints the result.

The dev server: yk up

One server per machine, always built from origin/main into ~/.local/state/yukta-dev/builds/<sha> (three kept), on 127.0.0.1:9858. It needs an API key because it runs arbitrary processes.

Monitoring: events, report, analyze

In plain words

Every repair attempt is written down in a diary file on your computer: what failed, which AI tried, how long it took, what it cost. Two reports read that diary: one shows where the time and money went, the other points out what keeps going wrong. That is how the repair process itself gets better over time.

Every step appends one JSON line to heal-events.jsonl. The log outlives the per-run heal dir and holds log text, so it stays on your machine. This is the improvement loop for heal.

How the triage prompt was chosen

Measured on 54 real failures of this repository's CI, labelled by reading (eval/triage). Seven levels with long descriptions: 19 exact, 35 s a call. Three levels with the problem lines alone: 33 exact, 50 within one level, 7 s a call. The brief stays near 1000 characters because System One reads about 50 tokens a second without a big GPU and Ollama cuts a call off at 60 s.

Inside Claude Code

In plain words

Claude Code is an AI coding assistant. In this project it follows house rules, set by small automatic scripts (hooks): it may not run builds directly but must go through yk, and before it finishes it is reminded to run the checks. The AI repairers are separate, stripped-down Claude sessions that can edit files but can never publish anything.

The repo wires Claude Code to the dev loop through .claude/settings.json and .claude/hooks/yk-hook.sh. YUKTA_DOGFOOD=off turns all of it off.

SessionStart
Records the uncommitted changes the session began with, runs yk up --background, puts yk on PATH and tells Claude to build and test through it.
UserPromptSubmit
When a prompt is about building, testing or checking, adds one line naming the yukta skill.
PreToolUse (Bash)
Denies ./gradlew, gradle and go test|vet, and names the yk command instead. bootRun stays allowed; the self-heal fixer (YUKTA_HEAL_FIXER=1) is exempt.
PostToolUse
Records the Gradle module of every file the session edits.
Stop
Asks once for yk check -m <changed modules> unless a check already passed on exactly the current changes (.yukta-dev/last-result).
Status line

The headless Claude sessions heal and implement run

  • Launched through one slim launcher (yk_claude): none of your plugins, skills, settings or MCP servers; a fixed tool list; acceptEdits; no git commit or push.
  • The system prompt is the constant fixer-rules.md (or implementer-rules.md plus nav/rules-<backend>.md). Everything that varies goes in the user prompt, so every attempt shares one cached prefix.
  • Fixers are fresh sessions chosen by the triage. They do not resume the implementer.
  • Budgets: YUKTA_HEAL_BUDGET per attempt (per effort in heal.json), YUKTA_IMPL_BUDGET $5 for the implementer, YUKTA_BUDGET_ISSUE and YUKTA_BUDGET_EPIC as overall caps. Over a budget a step refuses to start.

Engine concepts used here

In plain words

Every Yukta flowchart is built from a handful of kinds of box. This is the parts list: a box that runs a command, a box that starts another flowchart, a box that waits for a person, a box that asks a small AI to choose, and boxes that end the run.

The Yukta node types and routing flags that the dogfood workflows rely on.

node typeused for in dogfood
CONSTANT_SOURCEThe trigger at the start of each workflow.
PROCESS_EXECUTORRuns a command (gradle, yukta-heal.sh <action>, yukta-issue.sh <action>). With failureMode: CONTINUE and routeByExitCode, exit 0 leaves by port success, non-zero by failure. With failureMode: ERROR a non-zero exit fails the node and the run.
SUB_WORKFLOWCalls another workflow with a payload (read there as start.*) and waits. routeByOutcome routes on how the child ended: success, failure, escalate, retry. concurrency: 2 in run-epic runs two children at once.
CLASSIFYThe triage: asks the System One model one question and routes by label (routeByLabel). engine.onError: ROUTE sends a failed call to port error.
WAIT_FOR_SIGNALCheckpoints (before-implement, before-pr, between-issues, before-opus). Answered with yk approve|reject. onTimeout is CONTINUE or FAIL.
SPLITTER, AGGREGATEFan out a JSON list of issues; collect results (the analyzers join, the epic's ok / bad / bad-count counters).
BRANCHanalyzers.gate: an expression over the join's items, port fail if any item has success == false, else pass.
CONSOLE_TERMINALEnds a run in success (done).
OUTCOME_TERMINALEnds a run with a named outcome. escalate makes RESULT status=ESCALATE even though the engine run itself succeeded.

Concurrency and limits

  • Gradle nodes are in the server's gradle concurrency group (YUKTA_DEV_GRADLE_PARALLEL, default 2): the parallel analyzers wait QUEUED instead of each starting a 4 GB daemon.
  • Only one check per checkout (.yukta-dev/check.lock).
  • Fixers and the gate nodes are time-boxed: stage nodes 3600 s, sub-workflows 14400 s, implement 14400 s, whole issue run 28800 s.

The RESULT line

RESULT status=<SUCCESS|FAILURE|ESCALATE> failed_node=<stage|-> healed=<stage:step[/effort],..|-> execution=<id> session=<id>

Exit code 0 only on success. yk watch prints problems only: NODE, ERROR|WARN <node>: <line>, CONTROL, HEAL, WORKFLOW, SLOW (stage over 15 s and 1.5x its median), APPROVAL for a waiting checkpoint, then RESULT.
