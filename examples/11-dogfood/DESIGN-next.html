Redesign draft · developing Yukta with Yukta

Every build of Yukta runs as a Yukta workflow.

Yukta is a workflow server: a workflow is a graph of nodes (steps) joined by edges, stored as JSON and run by the server. The Yukta team builds and tests Yukta itself with Yukta workflows (dogfooding). When a quality check fails, a repair workflow (heal) asks Claude models to fix the code, starting with the cheapest model, before a developer has to step in.

Builds, tests and checks run on a local dev server that is itself built from origin/main. One command, yk, is the only entry point, and every run ends in one machine-readable RESULT line.

This is the redesign draft. Every section describes the redesigned dogfood loop: a small library of reusable workflows instead of graphs generated per run. No code has been changed for it yet. The current design stays unchanged in DESIGN.html. Start with Workflow library, then who calls whom and the simulator.

Design decisions worth knowing

Reuse through SUB_WORKFLOW
Each job is written once and called: check calls gradle once per stage, attempt calls gradle, tool and claude, implement-issue calls claude and check. A change to how Gradle starts is made in one place.
A failure is data
Library workflows end a failure at an OUTCOME_TERMINAL FAILED and process nodes use failureMode: CONTINUE + routeByExitCode, so a caller gets the output on its failure port instead of a crash.
Cheapest first
The free automatic fix, then the triage picks the first rung, then haiku → sonnet → opus, each with effort low → medium → high, each attempt with its own time box and budget.
Fixers are judged by the recheck
After every attempt the failed stage runs again through gradle (and tool). A guard rejects edits to config, build, CI, added suppressions or removed assertions. Fixers never commit.
One fixer at a time
Analyzers run in parallel, but one analyzers.heal fixes all failures, so two models never edit the tree together. The gradle group allows 2 builds and the claude group 3 sessions, server-wide.
Nothing outward-facing by itself
before-pr fails the run if nobody answers within 4 hours. before-implement continues after an hour.
Server from main, library from main
The server swaps to a newer main only while idle, so a run never changes under itself; the library is uploaded again after a swap.
Every step is logged
Script steps append to heal-events.jsonl; the triage answer and the stage times come from the executions. Both feed yk heal report and analyze.

Workflow library

Today yk generates one large workflow per run with jq and starts Gradle and Claude in several different ways. The redesign keeps a small set of reusable workflows instead. Each one does one job and is called by the others through a SUB_WORKFLOW node. For example, check does not run Gradle itself; it calls gradle once per stage. A change to how Gradle is started is then made in one place and every caller gets it.

Each workflow below has a contract: the start payload keys a caller must pass, the ports the caller can route on, and the result it gets back. Click any node in a graph to see what it does, why it is configured that way, and its exact JSON config. Nothing on this page has been implemented yet.

Choices made in the redesign

Nesting depth

Every SUB_WORKFLOW call starts a child execution one level deeper. The engine refuses a child deeper than MAX_DEPTH = 5 (SubWorkflowGateway.java:22); the execution started by yk is depth 0. Each reusable layer costs one level, which is why D1 raises the limit.

Time limits

A SUB_WORKFLOW node waits at most timeoutSeconds for its child; this is a wall clock around the whole child. When it runs out, the node fails unless it routes errors (G8). The caps below are safety limits, not expected durations: the real limits per attempt are the effort's time box and budget.

Gaps: what the engine cannot do yet

Each row is something the reusable design needs. The workaround is how this draft works on today's engine; the proposed change would remove the workaround later.

How the triage prompt was chosen

Measured on 54 real failures of this repository's CI, labelled by reading (eval/triage). Seven levels with long descriptions: 19 exact, 35 s a call. Three levels with the problem lines alone: 33 exact, 50 within one level, 7 s a call. The brief stays near 1000 characters because System One reads about 50 tokens a second without a big GPU and Ollama cuts a call off at 60 s. The redesign keeps the prompt and the three levels unchanged.

The headless Claude sessions of attempt and implement-issue

  • Every session is one call to the claude workflow, which runs scripts/claude.sh: none of your plugins, skills, settings or MCP servers; a fixed tool list; acceptEdits; no git commit or push. The server allows 3 sessions at once (the claude group).
  • The system prompt is the constant fixer-rules.md (or implementer-rules.md plus nav/rules-<backend>.md). Everything that varies goes in the user prompt, so every attempt shares one cached prefix.
  • Fixers are fresh sessions chosen by the triage. They do not resume the implementer.
  • Budgets: per attempt by effort (heal.json efforts: $0.50, $1, $2), $5 for the implementer (implBudget), and the issue and epic caps (budgetIssue, budgetEpic). Over a budget, prepare or implement-prep refuses to start a session.

Engine concepts used here

The node types and settings the redesigned workflows rely on, in one line each. Every type has a full card under Building blocks.

node typeused for in the redesign
CONSTANT_SOURCEThe trigger of every workflow. It also copies start payload values into the message when a BRANCH or a script step needs them (G10).
PROCESS_EXECUTORRuns a command: Gradle in gradle, a tool in tool, Claude in claude, and the script steps (yukta-heal.sh, yukta-issue.sh). With failureMode: CONTINUE and routeByExitCode, exit 0 leaves by port success, non-zero by failure, with the output kept. inputMode: STDIN hands structured data to a script; outputFormat: JSON parses what it prints.
SUB_WORKFLOWEvery call between library workflows. Its payload becomes the child's start payload; routeByOutcome routes on how the child ended (success, failure, escalate, retry); engine.onError: ROUTE adds error for the node's own timeout; concurrency: 2 in run-epic.
MAPPERUnwraps a child's result (results[0]) into the flat payload the next call needs (fix-from and heal).
CLASSIFYThe triage: asks the System One model one question and routes by label.
WAIT_FOR_SIGNALApprovals: before-implement, before-pr, between-issues, approve-model. Each sits behind a BRANCH on its start payload switch.
BRANCHSwitches (heal on or off, automatic fix or not, triage on or off, pause or not, start effort) and the analyzers gate.
SPLITTER, AGGREGATEOne message per issue of an epic; the analyzers join and the epic's ok and bad collectors.
CONSOLE_TERMINALEnds a workflow normally (done, ok).
OUTCOME_TERMINALEnds a workflow with outcome FAILED (every library workflow's failed end) or ESCALATE (run-issue, run-epic). The caller routes on it; yk prints it as the RESULT status.

Concurrency and limits

  • Concurrency groups, server-wide: gradle (2 builds at once, YUKTA_DEV_GRADLE_PARALLEL) and claude (3 sessions). A node over the limit waits QUEUED.
  • Only one check per checkout (.yukta-dev/check.lock), because fixers edit the working tree.
  • Nesting depth up to 7 (an epic), which needs the configurable limit of 8 (D1).
  • Time caps on every SUB_WORKFLOW call, from 2000 s (claude in attempt) to 86400 s (an issue); see the time table in the library. The dev server ends any execution after 24 hours.

The RESULT line

RESULT status=<SUCCESS|FAILED|FAILURE|ESCALATE> failed_node=<stage|-> healed=<stage:step[/effort],..|-> execution=<id> session=yukta-dev

FAILED is the outcome of a workflow that ended at its failed terminal (a stage that could not be fixed); FAILURE means an execution itself failed (a crash or a cap). Exit code 0 only on success. yk watch prints problems only: NODE, ERROR|WARN <node>: <line>, CONTROL, HEAL, WORKFLOW, SLOW (stage over 15 s and 1.5x its median), APPROVAL for a waiting checkpoint, then RESULT.
