2. What was tested

The question, in plain words

Yukta can run a whole software task as an automated workflow: start a fix, run quality checks, repair what fails, and open a pull request. Claude Code can use Yukta in two ways, and the question is which one wastes fewer "tokens" (the unit AI models are billed in; see the glossary).

Arm A: do it yourself

One Claude Code session reads the code, edits it, and fixes whatever fails. Yukta is only the inspector: it runs the checks and reports pass or fail. It never fixes anything.

Like one contractor who does the repair and calls an inspector at the end.

Arm B: orchestrate

The same Claude Code session does not touch the code. It starts one Yukta workflow (yk run issue) and waits. Yukta runs a separate implementer, checks the result, and sends in separate "fixer" Claude sessions when a check fails.

Like a site manager who hires a crew and a repair team, each billing separately.

The test subject

Issue #1207 is a small, real bug in the Go command-line tool: when it shows only the problems in a failed step, a step with many warnings uses up the 20-line limit and the one error that actually failed the step is cut off. The expected fix: warnings and errors get separate limits. It is a good test because it is small, clearly right or wrong, and touches only one module (cli).

How fairness was kept

  • Same start. Both arms get the same issue text, the same model (Opus), the same tools and the same $5 spending cap. The only difference is who does the work.
  • Same code. Each run starts from a fresh copy of the exact same commit, main@{{BASE}}.
  • No side effects. Every run happens in a throw-away copy. GitHub writes (claiming the issue, project board, opening a PR) are replaced by a stub that only records them. Issue #1207 stayed untouched.
  • Independent grading. After each run, a hidden test (never shown to Claude) checks that the error line survives a flood of warnings, that output stays bounded, and that nodes do not affect each other. The existing test suite must also pass.
  • Everything billed counts. Arm B's total includes the main session and every sub-flow Claude session it started, split out separately.

4. Why arm B cost more

This is the heart of the evaluation, so here is the chain of events, in order:

  1. The implementer changes problems.go and its test (cost: $0.20 to $0.34, cheaper than all of arm A's session).
  2. Yukta runs the quality check, and because nothing tells it otherwise, it runs the whole repository's check, including Java modules the change cannot affect (#1233).
  3. Two Java tests fail: BeanInventoryTest and ConcurrencyGroupsTest. They fail because the dev server's own environment variables (YUKTA_CONCURRENCY_GROUPS_GRADLE, YUKTA_SUPERVISOR_RULES_FILE) are inherited by the test processes and change how those tests behave (#1232). Nothing about #1207 causes this.
  4. A fixer is started. To save tokens, Yukta resumes the implementer's Claude session, so the fixer is an Opus session carrying the whole earlier conversation. Each attempt costs $0.72 to $1.37.
  5. The first fixer often says, correctly, "this failure is not caused by this branch" and changes nothing. It still bills for reading its context. A second attempt then either gives up (B2) or edits the two Java test files (B1, B3).
  6. Those Java edits are committed into the issue's branch next to the real fix (#1234), and the final result line does not even mention that fixers ran (#1235).
What this meansThe comparison measured two things at once: the cost of the approach (orchestration plus sub-flows) and the cost of a defect in the environment. The defect dominates. Fixing #1232 and #1233 should remove most of arm B's extra spend, but that has to be measured, not assumed.

5. Token efficiency

Tokens, not dollars, are the unit this evaluation was asked about. Each bar below is one run's total tokens, split by how the model was billed for them.

{{TOK_CHART}}
{{TOK_LEGEND}}
  • Most tokens are re-reads, and that is good. Claude re-sends the whole conversation on every turn; a cache makes those re-reads about ten times cheaper. Cache reads were {{CACHE_MIN}} to {{CACHE_MAX}} of tokens in all runs, above the plan's 70% target. The slim, byte-identical prompt prefix the sub-flows share is doing its job.
  • The orchestrator pattern shrinks the main conversation. The main session in arm B ended after 2 to 5 turns and a median {{B_MAIN_TOK}} tokens, versus {{A_MAIN_TOK}} in arm A. If the main conversation is the expensive or limited resource (for example a long-lived session you keep working in), this is a real benefit.
  • But total tokens were higher. Median total: {{B_TOK}} for arm B against {{A_TOK}} for arm A. Without the fixer attempts, arm B's median is {{B_CORE_TOK}}.
  • The cost target for a fix attempt was missed. The plan says a typical heal attempt should cost under $0.30. In arm B they cost $0.72 to $1.37, because they resume an Opus session that carries the earlier conversation (up to 650k tokens re-read in one attempt). A cheap model on a fresh, small prompt would cost a fraction of that, and an attempt that is not about the implementer's files does not need the implementer's context at all (see next steps).

How the prompt cache was used

Every turn re-sends the whole conversation. The provider keeps a copy of the unchanged beginning (the "prefix"), so the repeat costs about a tenth. If anything near the start changes, such as the tool list, the system prompt or an earlier message, everything after it counts as new and is written again.

  • Inside one session the cache works. Implementer sessions read 87% to 92% of their tokens from cache, and so did the fixers once running.
  • The first fixer turn does not reuse the implementer's conversation. It reads only the small shared start (6.4k tokens, or nothing in B1) and writes the rest again:
{{REWRITE_ROWS}}
SessionPause since last turnTokens written againTokens read from cache

It is not cache expiry: the pauses were 89 to 276 seconds, and a later 313-second pause in B1 still hit the cache. Only the first fixer attempt after the implementer re-writes; the second and later attempts of the same run do not, because they share the fixer's settings.

What causes it (tested)

I first suspected the different instructions each role appends to the system prompt. A small experiment ruled that out and found the real cause. Each row is one conversation with a tool call, resumed in a copy (claude -p --resume --fork-session), on Sonnet unless noted.

The answer format is added to the model as a tool, and tools sit at the very front of the cached text, so changing it invalidates everything behind it. The implementer and the fixers use different formats, which is filed as #1248. One run per row on a small conversation, so this confirms the mechanism, not the exact size.

How much it matters here: each run re-wrote 17k to 27k tokens once. At the prices the experiment implies that is roughly $0.1 per run, under 5% of a run and far below the $0.72 to $1.37 a fixer attempt costs. The fix is cheap and worth doing, but it is not where the money went.

  • The orchestrator's efficiency did not come from tools. In arm B it did no code navigation at all, because its prompt told it not to edit code. It was cheap because it did almost nothing: 2 to 5 turns, $0.20 to $0.29.
  • In this evaluation neither arm had an IDE index or CodeGraph. A fresh clone is not an open IDE project, the project's own MCP servers are not loaded for an untrusted workspace, and the CodeGraph index is not in git. I also did not find a tool called "ponytail" in the plugin, skill or MCP lists of either session. If it is part of your daily setup, this evaluation did not include it.
  • What the implementers really used (4 sessions, B1 to B3, implementer plus fixers): Bash 138, Edit 36, Grep 36, Read 34, structured answers 22, Write 8, Glob 4, CodeGraph 0. Bash is mostly Gradle and Go test runs. The rule "run codegraph explore once before reading files" had no effect, because codegraph explore answers "CodeGraph isn't available here" in a worktree without an index.

The main session's full set (30 servers, 51 skills) is the 23k to 29k start-up you see above. Whether a navigation tool saves more turns than it costs is not measured. The implementer was already inexpensive ($0.20 to $0.34, against $0.35 to $0.58 for arm A's whole session on the same fix), so the likelier gain is in the fixers' investigation turns.
  • How to test it: an arm C that gives the sub-flows a working code index (built by you, since indexing is your decision) and compares tokens with arm B. cache_trace.py and the tool counts above are the measurements to use.

6. Correctness and delivery

  • The code was right in all six runs. The hidden test and the full existing suite passed every time. All fixes use the same idea (a separate limit for warnings, about 10, next to 20 for errors) and add a regression test.
  • Arm B did not always deliver. B1 and B3 ended SUCCESS. B2 ended ESCALATE: the orchestrator ran the flow twice, as instructed, and both runs stopped at the same unrelated Java failures. The correct fix was sitting in the worktree, but no branch was committed. A reader who only looked at the hidden test would call B2 a success; the workflow did not.
  • B1 and B3 delivered more than the fix. Their branches also contain edits to BeanInventoryTest.java and ConcurrencyGroupsTest.java. The edits look reasonable (they stop the dev environment leaking in), but they are unrelated to the issue and would reach a reviewer inside the PR (#1234).
  • Arm A's changes were exactly the issue. Each run changed two files in cli/ (the fix and its test) and nothing else.

B2's recorded cost is a lower bound.The orchestrator ran the flow twice, and the second run overwrote the first run's record files (they are named by attempt number; #1250). The first run is still in the session transcripts: {{B2_LOST_TOK}} cache tokens. Scaling the recorded second run's sub-flow cost to that gives about {{B2_EST}} for B2 instead of the recorded {{B2_REC}}. The tables and charts use the recorded figures, so they understate arm B; counting the lost run moves arm B's median to about {{B_COST_CORR}} ({{RATIO_CORR}}× arm A).
The cache experiment is small.Each row of the cache table is one conversation on Sonnet (the same-rules check also on Opus), and the answer-format result is one pair. It shows that the answer format breaks the cache and that different appended instructions do not. It does not give an exact saving.
Different check scope.Arm A was told to finish with the check on the cli module. Arm B's flow ran the whole repository (#1233). This asymmetry is exactly what drove the cost gap; it is a finding, not an accident of the test, but it means the arms did not run an identical gate.
Projection is not a measurement."About {{B_CORE_COST}} without the unrelated repairs" adds the measured orchestrator and implementer costs. It assumes the implementer would still get it right first time and that no other failures would appear. Only a re-run after fixing #1232 and #1233 can confirm.

9. Next steps

  1. Fix #1232 (make the two tests independent of the host environment, or strip those variables from the Gradle stages). This alone removes the failure that every arm-B run hit.
  2. Fix #1233 (scope the issue flow's check to the modules the implementer touched).
  3. Re-run arm B three times. About $2 per run if the projection holds. That turns the estimate in this report into a measurement. Arm A does not need re-running.
  4. Rethink the fixer's model for out-of-scope failures (part of #1234). A failure outside the implementer's files does not benefit from resuming the implementer on Opus. Options: stop and escalate at once, or use a cheap rung (Haiku or Sonnet) on a small fresh prompt. The no-change attempts alone cost {{NOOP_COST}}.
  5. Fix #1248 (one answer format for the implementer and every fixer) and check with cache_trace.py that no turn re-writes the implementer's conversation. Fix #1250 so budgets and yk stats count every attempt of an issue.
  6. Let workers share what is already known (#1249): compare a failing stage with a result for the base commit before starting a fixer, and when the orchestrator has analysed something, put it in the brief file for the implementer.
  7. Test navigation tooling for the sub-flows (#1251). Run an arm C where the implementer and fixers have a working code index, or drop the dead CodeGraph rule if it does not pay.
  8. Optional follow-ups for a fuller picture: a second issue with a different shape (a Java change, so the scoped check matters), an orchestrator on a cheaper model (Sonnet) for arm B, and two issues in parallel (an epic) to measure what parallel workers share.

C. Method

  • Base. Every run clones the repository, creates a bare origin and points its main at {{BASE}}. Arm B's flow creates its own worktree yukta-issue-1207 beside the clone, as it does in real use.
  • Server. Arm B used the standard dev server on port 9858, built from main@{{BASE}} through yk up. The yk scripts came from the same commit.
  • Main session launch (both arms): claude -p … --model opus --permission-mode acceptEdits --max-budget-usd 5 --max-turns 60 --output-format json, with tool permissions limited to file tools, yk, go, read-only git and codegraph; git commit, git push and gh were refused.
  • Sub-flow launch (arm B): the dev loop's own slim launcher (yk_claude): project settings only, no MCP servers, fixed tool list, constant system prompt, $5 cap, Opus implementer. In issue runs the fixers resume the implementer's session.
  • Stubs. gh serves a saved copy of the issue and logs everything else; the project-status command only logs. YUKTA_WARM_DELAY=0 and YUKTA_CHECK_EXTRAS=off were set.
  • Grading. hidden_test.go is copied into cli/internal/commands/controlbus after the run and run with go test -run TestHidden; then go test ./... for the whole cli module. The hidden test was first checked to fail on the unfixed code and pass with a reference fix.
  • Where the numbers come from. Main session: the usage and total_cost_usd of claude -p --output-format json. Sub-flows: implement.json and the heal/check/*-N.json records the workflow writes. The dollar value is each session's own total_cost_usd.

Glossary

Token
The unit an AI model reads and writes: roughly three-quarters of a word. Models are billed per token, at different rates for different kinds.
Cache read / cache write
Claude re-reads the whole conversation on every turn. The first time it stores that text (a cache write, a little dearer than normal input); later turns re-read the stored copy (a cache read, much cheaper). A high cache-read share means the model is not paying full price to repeat itself.
Orchestrator
A Claude Code session that only starts and watches other workflows and does not do the detailed work itself.
Sub-flow
A workflow started by another one. Here, the implementer and the fixers are sessions run inside Yukta's issue workflow.
Implementer / fixer
The implementer makes the change the issue asks for. A fixer is started when a quality check fails and tries to repair that failure.
Check / gate
The automated quality run: formatting, compiling, tests, test coverage, code-style tools (Checkstyle, PMD, SpotBugs), licence and security scans.
PMD / Checkstyle
Tools that read code for style and quality problems without running it.
ESCALATE
Yukta's way of saying "I could not finish this by myself": a person needs to look.
Worktree
An extra working copy of the same repository, so several tasks can be edited side by side.
Dev server
The local Yukta server the dev loop runs its workflows on (port 9858), built from main.
Dogfood finding
A defect in Yukta found while using Yukta to build Yukta; filed as a GitHub issue with the evidence.
Hidden test
A test the grader adds after a run, never shown to Claude, so it cannot be tuned for.
